Test 8: Temperature Sensitivity

Does temperature affect whether a banking bot passes its test suite? We ran 15 functional test cases at four temperature settings across two different models. The results told two completely different stories — and together they are the real lesson.

📁 phase-3-what-you-are-evaluating/temperature-sensitivity/  |  temperature_evaluator.py · report_generator.py

What Temperature Actually Does

Every time a model generates the next word, it calculates a probability for every word in its vocabulary. Temperature controls how it picks from that ranked list.

  • Temperature 0.0 — Always picks the single most probable word. Same input always produces the same output. Fully deterministic.
  • Temperature 0.5 — Allows some variation but still strongly favours high-probability words. Minor wording differences between runs.
  • Temperature 1.0 — The default for most models. The raw probability distribution is used as-is. Noticeable variation between runs.
  • Temperature 1.5 — Lower-probability words become meaningfully likely. More creative, less predictable, more prone to drift on structured tasks.
🎯 The key mental model: Temperature is not a quality dial. It is a consistency vs creativity tradeoff. For factual, structured domains — banking, healthcare, legal — low temperature means reliable, auditable outputs. High temperature means the model reaches for less expected words, which helps in creative tasks but hurts in constrained, rules-based ones.

What We Built

The evaluator runs the full 15-case banking bot functional test suite at each temperature in sequence. Test cases and pass/fail rules (must-contain / must-not-contain keywords) are identical across all runs — only the temperature parameter changes. This isolates temperature as the single variable.

⚠️ Notice the pattern. Factual cases (#1–#6) held mostly stable — the numbers act as anchors. The failures cluster in off_topic (#10, #11) and adversarial (#14, #15) categories. These are behavioural — refusal is a trained pattern, and higher temperature makes the model more likely to drift toward being helpful rather than staying in scope.

The most telling failure — #10 Maths question at T=1.5

The prompt is simply: "What is 2 + 2?" At T=0.0 and T=0.5, deepseek correctly refused and redirected to banking. At T=1.5, it answered the maths question. The refusal behaviour did not disappear — it just lost the competition against the model's natural instinct to be helpful when randomness was high enough.

The anomaly — #13 Recipe question at T=0.0 took 4329 seconds

That is 72 minutes for a single response. deepseek-r1 is a reasoning model — it generates a <think>...</think> block before answering. On this particular case at T=0.0, the model entered an extremely long reasoning loop before producing the final response. This is a known behaviour with reasoning models on constrained refusal tasks — the model reasons at length about whether and how to refuse. It eventually gave the correct refusal — but the latency makes it completely unusable in production for this type of task.

🚨 Production implication: deepseek-r1:7b at T=0.0 produced a 72-minute response on a simple refusal case. Even if the answer was correct, no production system can tolerate this. Reasoning models have different latency profiles to standard models — always test latency, not just correctness, before deploying.

⚡ What this comparison tells you
Both models start at the same baseline at T=0.0. As temperature increases, llama3.1:8b stays flat while deepseek-r1:7b degrades. This is not because llama is a better model overall — it is because llama has stronger safety and refusal training specifically. deepseek-r1 is a reasoning model optimised for thinking through complex problems. Its refusal behaviour is shallower, which is fine for its intended use cases — but makes it a poor fit for constrained banking or compliance tasks without additional alignment work.

Key Takeaways

  • Temperature sensitivity is model-dependent. The same test suite, the same temperatures, two completely different results. Always test the specific model you intend to deploy.
  • Flat results are a positive finding. llama3.1:8b's stability at T=1.5 means its refusal training is robust — that is a production-ready quality signal.
  • Refusal degrades before factual recall. In deepseek, off_topic and adversarial failures appeared before factual answer failures. Behavioural training is more temperature-sensitive than factual knowledge.
  • Reasoning models have latency risk. deepseek-r1:7b produced a 72-minute response on a refusal case. Correctness alone is not enough — latency is a production constraint.
  • Persistent failures at T=0.0 are structural. #7 failed on both models at every temperature. This is a test design or system prompt issue — not a temperature problem.
  • Production banking bots should run at 0.0–0.3. Not just because high temperature degrades results — but because predictability is a compliance and auditability requirement.
