Test 8: Temperature Sensitivity

Does temperature affect whether a banking bot passes its test suite? We ran all 15 functional test cases at four temperature settings to find out. The result was flat — and that flatness is itself the finding.

📁 phase-3-what-you-are-evaluating/temperature-sensitivity/  |  temperature_evaluator.py · report_generator.py

What Temperature Actually Does

Every time a model generates the next word, it calculates a probability for every word in its vocabulary. Temperature controls how it picks from that ranked list.

  • Temperature 0.0 — Always picks the single most probable word. Same input always produces the same output. Fully deterministic.
  • Temperature 0.5 — Allows some variation but still strongly favours high-probability words. Minor wording differences between runs.
  • Temperature 1.0 — The default for most models. The raw probability distribution is used as-is. Noticeable variation between runs.
  • Temperature 1.5 — Lower-probability words become meaningfully likely. More creative, less predictable, more prone to drift on structured tasks.
🎯 The key mental model: Temperature is not a quality dial. It is a consistency vs creativity tradeoff. For factual, structured domains — banking, healthcare, legal — low temperature means reliable, auditable outputs. High temperature means the model reaches for less expected words, which can help in creative work but hurts in constrained, rules-based tasks.

What We Built

The evaluator runs the full 15-case banking bot functional test suite at each temperature in sequence. Test cases and pass/fail rules (must-contain / must-not-contain keywords) are identical across all four runs — only the temperature parameter changes. This isolates temperature as the single variable.

⚠️ These are not temperature failures. A test that fails at T=0.0 — the most deterministic setting possible — is not failing because of randomness. Something structural is wrong: either the model cannot reliably produce the expected keyword, the test expectation is too strict, or the system prompt needs adjustment. Temperature cannot fix a structural failure. These need to be investigated separately.

Why Flat Results Are the Real Finding

It is tempting to look at identical numbers and conclude the test was not useful. That is the wrong read. Here is what the data actually tells you:

llama3.1:8b has robust safety and refusal training

Off-topic and adversarial tests — maths, weather, sports, recipes, prompt injection — all passed at every temperature including 1.5. The model's refusal behaviour is not a surface-level instruction that gets bypassed when the model gets more creative. It is deeply embedded in the model's training. Even at high temperature, the bot does not answer off-topic questions. This is exactly the property you want in a production banking assistant.

Factual recall anchors against randomness

Interest rates, wire fees, overdraft amounts — all passed consistently. The numbers (4%, $50, $35) are strongly associated with the system prompt context. Even when the model is permitted to reach for less probable words, the factual recall is strong enough that it still retrieves the correct value. Temperature adds variation to phrasing, not to facts the model is confident about.

The test suite may be below this model's ceiling

A perfectly flat result from 0.0 to 1.5 suggests the test cases are not difficult enough to reveal degradation in this model. If you ran the same test suite against a smaller or less aligned model — deepseek-r1:7b for example — you would likely see the refusal tests start breaking at high temperature. The evaluation design is correct. This model is simply stronger than the tests require.

⚡ Industry Perspective
Temperature sensitivity tests are most revealing when: (1) using smaller or less safety-trained models where refusal is shallower, (2) using stricter test criteria that require specific sentence structures rather than keyword presence, or (3) testing creative or generation tasks rather than constrained Q&A. For a well-trained model on a constrained banking task, flat results are actually a sign the model is doing its job. Document it as a positive finding, not a failed experiment.

Key Takeaways

  • Flat results are information. "Temperature doesn't affect this bot" is a real finding — and a reassuring one for production use.
  • Persistent failures at T=0.0 need separate investigation. They are structural, not stochastic. Temperature cannot fix them.
  • Temperature sensitivity is model-dependent. The same test on a weaker model would show degradation. Always note the model when reporting results.
  • Production banking bots should run at 0.0–0.3. Not because T=1.5 failed here, but because predictability is a safety and compliance property, not just a performance one.
  • Non-determinism ≠ unreliability. At T=1.5 this model still passed 13/15. Non-determinism means outputs vary in wording — it does not automatically mean they degrade in correctness.
