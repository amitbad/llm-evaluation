# LLM Evaluation Engineering course audit

## Executive summary

**Maturity — a substantial hands-on lab collection with uneven teaching depth.** Six phases contain 15 numbered experiments, 14 corresponding HTML lessons, and reusable datasets and output samples. A learner with Python and QA experience can follow much of the offline evaluation journey. An absolute beginner needs a smaller, verified entry path. An instructor can demonstrate several strong cases today, but would need to create exercises, answers, and assessment criteria to teach the full course. Production coverage currently consists of production-style experiments and an observability lab.

**Strengths.** The course makes evaluation failures visible with concrete examples. Test 0 illustrates a check that passes a bad answer. Test 4 gives learners prompts and a reason to form their own verdict. Tests 6–7 distinguish similarity from source support and expose a lenient judge. Test 9 makes retrieval and generation observable and shows a wrong answer with strong proxy scores. Tests 12–13 provide replayable agent traces. Test 14 explains traces and spans through an end-to-end setup. These are useful foundations for a concept-first course.

**Weaknesses.** Many modules stop at running a script and reading someone else's results. Same-response annotation, gold labels, statistical uncertainty, and release gates are missing or underdeveloped. Some scoring code can convert infrastructure failures into quality failures or let incorrect behaviors pass. Data and sample artifacts frequently lack sufficient run provenance. A clean, fully offline beginner path has yet to be assembled.

### Ten teaching improvements to make first

1. Give learners a fixture-only first lab with a visible input, expected output, and one deliberate false positive.
2. Add per-lab prerequisites, an entry checkpoint, runtime and cost expectations, and a short replay path.
3. Explain the first Python and JSON task line by line, using one case per example.
4. Give each lab a worked example, an independent variation, and a solution or invariant learners can verify.
5. Practice scoring the same frozen responses with anchored rubrics before any judge or leaderboard appears.
6. Demonstrate error, missing evidence, valid failure, and correct abstention as distinct outcomes.
7. Pair aggregate score examples with case-level evidence, slice sizes, and a decision learners must justify.
8. Give instructors a demo script, prediction questions, known-good artifacts, timing, and a fallback plan.
9. Add a short mastery check to each phase, with observable competencies and a capstone assessment.
10. Repair conflicting examples, run commands, and lesson entry points, particularly the missing Test 10 page and the two Test 2 input snapshots.

## 3. Technical and evaluation findings

**Confirmed** describes a checked-in observation or a code path visible in source. Conditional impacts are reasoned from those paths. Severity reflects measurement validity, ability to complete the lab, or handling of learner data. **High** findings can invalidate a main lesson result, expose sensitive information if the lab is reused with real data, or block a supported path. **Medium** findings materially limit interpretation or reliability. **Low** findings are narrower. No Critical finding was confirmed through static inspection.

## 8. Proposed end-to-end curriculum

| Order / module | Objective and prerequisites | Practical experiment and verification | Entry and learner competency |
|---|---|---|---|
| Beginner 1 / Evaluation from first principles | Define user objective, risk, unit, expected behavior, quality dimension, model inputs/outputs and evaluation mode. No prior LLM evaluation, optional Python starter | Reuse Test 0's joke, summary and arithmetic, and show gold spans with a local benchmark fixture. Compare normalized exact match, rule outcomes and human judgment on frozen cases. Add Test 1 as a single-model live smoke test | Standalone. Learner writes a test case and explains why a reproducible checker can yield an incorrect quality decision. |
| Beginner 2 / Human judgment and deterministic regression | Basics, simple spreadsheets and JSON. Learn capture vs scoring, rubric anchors and dataset labels | Reuse Tests 2 and 4. Score the same anonymous responses, reconcile with a partner, and implement a targeted rule with positive and negative controls | Can start with frozen outputs. Learner distinguishes ambiguous labels from failure, saves replayable cases and explains class-level errors. |
| Intermediate 3 / Data and metrics | Prior case design, annotation and simple Python | Version a golden set with slices and a holdout. Extend Tests 3 and 6 with correct paraphrases, incorrect close answers, field-level assertions and threshold tuning. Explain BLEU and ROUGE by hand and use library implementations after | Independent overlap or embeddings lab with supplied data. Learner chooses a metric aligned with one objective and defends its limitations. |
| Intermediate 4 / Judges, pairwise and experimental design | Human labels, metric families and dataset splits | Rework Tests 5, 7 and 8 around frozen examples, structured reasons, blind pairwise and order swaps, then compare two prompt versions with repeated paired observations and uncertainty | Judge and statistics labs can be taken independently using labeled fixtures. Learner calibrates a judge, interprets a confusion matrix and justifies improvement, neutrality or an inconclusive comparison. |
| Advanced 5 / RAG diagnosis | Embeddings/ranking, validated metrics and paired designs | Reuse Test 9 documents and chunker. Label passages and claims, compute rank metrics, compare actual to oracle retrieval, and evaluate correct answers, abstention and citations. Replay identical records through optional RAGAS and DeepEval mappings from Tests 10–11 | Retrieval ranking can stand alone using pre-ranked passages. Learner localizes a RAG failure, explains metric disagreements, and verifies a fix against a held-out slice. |
| Advanced 6 / Agent and workflow evaluation | Structured messages, rubrics and state, with retrieval assumed for document tools | Reuse Tests 12–13. Replay good and bad traces, verify outputs and final state, distinguish valid paths, inject a scripted tool outage, and compare judged reasons to explicit state outcomes. Add case, step and attempt timing | Standalone trace replay with schema guide. Learner evaluates observable tool use, recovers failed runs, and explains relationships among path, policy, output and cost. |
| Advanced 7 / Safety and defensive evaluation | Labeling, metrics and the relevant system module | Construct a harm, fairness, privacy and refusal test matrix using fictional data. Use fixed safe inputs and mock tools to check trust boundaries. | Production 8 / Lifecycle and capstone | Core statistics, regression, safety and one system track | Reuse Test 14 to follow a trace, run a replayable CI gate, triage a synthetic drift incident, and convert reviewed failures into regression cases. Learner identifies which metric claims transfer and substantiates where a new rubric or data slice is needed. |

The capstone should ask each learner to submit a versioned mini-suite, evaluation contract, a reproducible score report with disagreements and uncertainty, one failure diagnosis backed by evidence, and a release recommendation. Instructors should be able to replay the submitted evaluation and verify how errors, refusals and incomplete evidence were handled.
