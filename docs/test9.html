Phase 3 — What You Are Evaluating

Test 9: RAG Evaluation

RAG stands for Retrieval Augmented Generation. Instead of relying on what the model was trained on, a RAG system first searches a document corpus and gives the model only the relevant text to answer from. This test builds a RAG pipeline from scratch and evaluates whether it retrieves the right information, answers faithfully from that information, and addresses what was actually asked.

📁 phase-3-what-you-are-evaluating/rag-evaluation/  |  chunker.py · retriever.py · rag_bot.py · rag_evaluator.py · report_generator.py

What Problem Does RAG Solve?

A standard LLM answers from its training data — knowledge baked in at training time that cannot be updated and cannot be verified. For a banking assistant, this is a serious problem. You need the bot to answer from your documents, not from general knowledge that may be wrong, outdated, or hallucinated.

RAG solves this by giving the model context at the moment the question is asked. The model only sees the retrieved text — it has no choice but to answer from it. If the answer is not in the retrieved text, a well-prompted RAG bot will say so rather than invent one.

🎯 The core idea: RAG separates two problems — finding the right information and answering from it. The retriever handles finding. The LLM handles answering. Evaluating a RAG system means evaluating both separately, because each can fail independently. A perfect retriever with a poor LLM still gives bad answers. A great LLM with poor retrieval still gives incomplete answers.

The Source Documents

Three fictional NextGen Banking documents form the corpus for this test. All product names, fees, and policies are invented for this exercise.

What We Built

A five-file pipeline built from scratch. No external RAG framework — every step is visible and understandable.

FilePurposeRun?
chunker.py Reads the 3 source documents, splits them into paragraphs on blank lines, filters fragments under 40 characters, saves to chunks.json. Produced 12 chunks — 4 per document. Once at setup
retriever.py Loads chunks.json, encodes all chunks as vectors using sentence-transformers/all-MiniLM-L6-v2, then for any question returns the top-K most similar chunks by cosine similarity. Uses a _load() pattern — model loads once on first call and is reused for all questions. Never runs directly. Library only
rag_bot.py The banking assistant. Takes a question → calls the retriever → builds a prompt with retrieved chunks as context → calls llama3.1:8b with a strict instruction to answer only from context. Returns the answer plus the retrieved chunk IDs. Never runs directly. Library only
rag_evaluator.py The script you run. Reads all 25 test cases from Excel, calls rag_bot.py per case, scores each response three ways, prints live progress to terminal, then calls report_generator.py at the end. This one
report_generator.py Called automatically by the evaluator at the end. Generates results/rag_evaluation_report.html. Never run directly. Auto
🔧 No database required. With only 12 chunks, everything fits in memory. The retriever loads all chunks at startup, encodes them once, and reuses those vectors for all 25 questions. Vector databases (Chroma, Pinecone, FAISS) exist for scale — thousands of documents. For this test, in-memory is correct and simpler to understand.

How to Run

Step 1 — one-time setup

cd phase-3-what-you-are-evaluating/rag-evaluation
python chunker.py

This reads the three documents and writes chunks.json. You only need to run this once. If chunks.json already exists, skip this step.

Step 2 — smoke test first (recommended)

Before running all 25 cases, run rag_bot.py directly with a few sample questions to confirm the pipeline works end to end:

python rag_bot.py

The __main__ block runs 3 sample questions and prints the retrieved chunks and bot answer for each. You will see something like:

Q: What is the monthly maintenance fee?
Chunks: chunk 2, chunk 1, chunk 7  (scores: 0.72, 0.41, 0.38)
A: The standard Monthly Maintenance Fee is £12.00...

If this works, the full evaluation will work. If it fails here, fix the issue before running 25 cases.

Step 3 — full evaluation

# Runs all 25 cases — approximately 75 model calls (~15–20 minutes on local Ollama)
python rag_evaluator.py

The terminal shows live progress — which chunks were retrieved, similarity scores, response time, and all three scores per case. Output is written to results/rag_evaluation_report.html.

How Scoring Works

Every test case is scored on three dimensions independently. The overall score is a simple average:

Overall = (Context Relevance + Answer Faithfulness + Answer Relevance) ÷ 3
MetricMethodWhat it measuresScore range
Context Relevance LLM judge (mistral) Did the retriever pull chunks that actually contain what's needed to answer the question? 0% / 50% / 100%
Answer Faithfulness LLM judge (mistral) Did the bot answer only from the retrieved chunks, or did it add or invent information not present in context? 0% / 50% / 100%
Answer Relevance Keyword matching Does the answer contain the expected keywords? Proportion of expected keywords found in the response. 0% – 100%
🔗 Connection to Test 7 (Groundedness Scoring): Answer Faithfulness here is the same concept as groundedness scoring — both ask whether the bot's claims can be traced to its source material. The difference is the source: in Test 7 the source was a system prompt; here it is the retrieved chunks. If you understood Test 7, you already understand faithfulness scoring. The same judge, the same question: did the bot invent anything?
⚙️ TOP_K_CHUNKS — why 3? The retriever returns the top 3 most similar chunks for every question. This is set as TOP_K_CHUNKS: 3 in config.yaml. Too few (1–2) and cross-document questions miss important context. Too many (6+) and the LLM's context fills with irrelevant chunks, diluting the signal. 3 is a reasonable default for a 12-chunk corpus. For larger corpora this value needs tuning based on how spread out the answers are across documents.
⚠️ The overall score can mislead. A case scoring 0% + 100% + 0% averages to 33%. Before drawing conclusions from overall scores, always check each metric individually — especially on unanswerable and boundary cases. Read the section below before reviewing per-case results.

Results by Category

The 25 test cases are grouped into 7 categories. Each category tests a different type of challenge. Reading results by category tells you where the system is strong and where it struggles — the overall score alone does not show this.

Category definitions:

Single Document — Clean — Simple questions where the full answer lives in one document with no numbers required. The easiest category — the retriever just needs to find the right paragraph.

Single Document — Numbers — Same as Clean but the answer requires a specific figure. Tests whether the bot copies the right value without rounding or confusing similar figures from other chunks.

Cross-Document — Questions where the complete answer requires information from two different documents. Harder because the retriever must pull from both sources.

Adversarial / Confused — Questions designed to mislead. TC14 (three £12 fees) — the question is singular but the answer is plural. Tests whether the bot catches the full picture or gives a partial answer.

Unanswerable — Questions where the answer does not exist in the documents at all. The correct answer is a refusal. Tests whether the bot admits it does not know rather than inventing.

Negative / Boundary / Edge — Questions right at the limits of rules. TC21 (age 86, limit is 85), TC17 (£2,499 balance, threshold is £2,500). Tests whether the bot applies rules precisely at their edges.

Retrieval Confusion — Questions where the retriever is likely to pull a plausible-looking but wrong or incomplete chunk. Tests whether the bot stays focused when similar-topic chunks compete for retrieval.

Reading the Scores Correctly

⚠️ Low scores do not always mean failure. High scores do not always mean correct. This is the most important thing to understand before reading individual case results. Some scores look bad but represent the system working exactly as intended. Some scores look perfect but hide a wrong answer. Read this section before reviewing per-case results.

When 0% Context Relevance is correct

The retriever always returns 3 chunks — it cannot return zero. When a question is completely outside the document corpus, all similarity scores will be near zero — values like 0.08, 0.05. This is the system's signal that nothing relevant was found. Mistral then correctly judges context relevance as 0%.

This is not a retrieval failure. The retriever searched all 12 chunks and correctly found nothing because nothing exists in the corpus. The failure would be if the bot then invented an answer anyway.

🎯 Rule of thumb: Unanswerable case + context relevance 0% + faithfulness 100% = system worked correctly. Bot found nothing and refused to invent. Single Document or Cross-Document case + context relevance 0% = genuine retrieval problem.

When 100% Faithfulness hides a wrong answer — TC21

This is the most important finding in the entire test suite for understanding the limits of automated scoring.

TC21: "Can I get a Gold Loan if I am 86 years old?" The document states the age range is 18–85. The retriever correctly pulled chunk 3. Context relevance: 100%. Faithfulness: 100%. But the bot answered: "you can still be eligible for a Gold Loan if you are 86 years old" — which is wrong. 86 is outside the range.

The bot read the numbers correctly from context, then reasoned backwards. Mistral judged the answer as faithful because the numbers 18 and 85 appear in both the context and the answer — it did not verify whether the logical conclusion was correct.

🚨 Faithfulness 100% does not mean the answer is correct. It only means the bot did not invent information outside the retrieved context. The bot can still misread or reason incorrectly from correct context — and the faithfulness judge will not catch it. In a real banking context, this answer would give a customer wrong eligibility information. Automated scoring alone is insufficient for boundary and eligibility questions — human review is required.

Why the overall score can mislead

The formula: Overall = (Context Relevance + Answer Faithfulness + Answer Relevance) ÷ 3

TC18 (prompt injection — CEO salary) scored 33% overall. But the bot correctly refused a prompt injection attack — faithfulness 100%. The 33% came from context relevance (0% — correct, nothing exists in corpus) and answer relevance (0% — keyword matching expected "cannot help" but the bot said "I cannot provide information about the CEO's salary"). Two out of three measures were correct. The 33% looks like failure. It is not.

Why Answer Relevance scores low on refusal cases

Keyword matching checks for exact strings. When the expected keywords are cannot help, not available, banking questions only and the bot says I cannot provide information about the CEO's salary — a correct refusal in different words — keyword matching scores 0%. It cannot recognise that two phrases mean the same thing. This is a known limitation: keyword matching works well for factual cases with specific numbers or names, and breaks down on refusal cases where wording varies.

Key Case Findings

TC14 — Three £12 fees ✅ 100%

There are three separate £12 fees across two documents — Monthly Maintenance Fee, SWIFT transfer fee, Credit Card late payment penalty. The retriever pulled chunk 2 and chunk 6, catching both sources. The bot listed all three fees correctly distinguished by type.

✅ Why this worked: Paragraph-based chunking placed each fee in a different chunk. The query had enough semantic pull to retrieve from both documents. The bot synthesised without merging or confusing the fees.

TC21 — Gold Loan age 86 ⚠️ Scores look good, answer is wrong

Context relevance 100%, faithfulness 100%, overall 83% — but the bot said "you can still be eligible for a Gold Loan if you are 86 years old." The correct answer is: no, the age limit is 85.

The bot read "aged 18–85" from context and drew the wrong conclusion about whether 86 falls within that range. The faithfulness judge saw matching numbers in context and answer and scored it as grounded — without checking whether the reasoning was correct.

🚨 This is a reasoning failure that automated scoring cannot catch. The retriever worked. The bot stayed within context. The judge approved it. But the answer is factually wrong and would misinform a real customer. This case must be caught by human review — it is the clearest example in this test suite of why automated metrics need human oversight.

TC23 — Gold Loan £10,000 processing fee ◑ 83%

Context relevance scored 50% — the retriever pulled chunk 4 (repayment options, not directly relevant) alongside chunk 3 (which contains the 2% fee). Despite imperfect retrieval, the bot correctly calculated £200 (2% of £10,000) and gave the right answer. The bot compensated for partial retrieval by finding the key fact in the available chunks and applying arithmetic.

✅ Arithmetic reasoning worked. The bot did not just quote "up to 2%" — it applied the percentage to the specific loan amount. This is a step beyond simple lookup and is a positive finding for this model.

TC24 — Formal complaint ✅ 100%

Both chunk 8 (general support contact) and chunk 12 (complaints escalation path) contain contact details. The retriever correctly prioritised chunk 12 — "formal complaint" and "Escalation Path" are semantically closer than "formal complaint" and general support. The bot returned exactly the escalation email and the Escalation Path document reference. The similar-topic confusion risk did not materialise here.

TC08 — Cross-document LearnFund requirements ◑ 83%

The retriever pulled three chunks — all from the LearnFund document. It missed the Operations Guide which contains the ID and proof of address requirements. The bot gave a partially correct answer covering income and letter of acceptance but omitted ID documentation entirely.

This is a genuine retrieval limitation — when two documents both discuss "application requirements", the retriever gravitates toward the stronger semantic match and misses the second source.

TC18 and TC19 — Prompt injection and weather ✅ (scored 33–44%)

Both are correct system behaviours. TC18 refused a prompt injection attempt correctly. TC19 correctly refused a weather question. Both scored low due to metric limitations, not system failure. For TC19, retriever similarity scores were 0.08, 0.05, 0.05 — near zero, the clearest possible out-of-corpus signal. In production, a similarity threshold check before calling the LLM could route these directly to a "not in scope" response without a model call.

What the Category Scores Tell You

  • Single Document (Clean + Numbers) — 93%–100%. The baseline works. Direct questions with answers in one document are handled correctly every time.
  • Cross-Document — 89%. Mostly good. Struggles when both documents discuss the same topic — retriever gravitates toward the stronger match and misses the second source.
  • Adversarial / Confused — 97%. Strongest non-trivial category. TC14 (three £12 fees) and TC15 (inactive vs dormant) both passed. The bot distinguished between similar concepts without confusion.
  • Unanswerable — 50%. Faithfulness was 100% across all three cases — the bot never hallucinated. The 50% average is entirely a measurement artefact from keyword matching on refusal phrases. These cases are a pass, not a failure.
  • Negative / Boundary / Edge — 76%. Mixed. TC17 and TC20 passed correctly. TC21 scored well on automated metrics but gave a wrong answer — the most dangerous result in the suite. Human review is essential for this category.
  • Retrieval Confusion — 94%. New category. Performed strongly. The retriever correctly prioritised relevant chunks even when similar-topic competitors existed. TC23 is the one partial score — context relevance 50% but the bot got the right answer anyway.

Key Takeaways

  • 100% faithfulness does not mean 100% correct. TC21 is the proof. The bot stayed within context and still gave the wrong answer. Automated scoring cannot catch reasoning errors — only human review can. For boundary and eligibility questions in production, always review the actual answer.
  • Retrieval quality depends on chunk design. Paragraph-based chunking worked well here because each fact tended to live in its own paragraph. A different chunking strategy — too small or too large — would change the results significantly.
  • The retriever can partially fail and the bot can still succeed. TC23 had imperfect context relevance (50%) but the bot got the right answer. Scores and correct answers don't always line up in the same direction.
  • Keyword matching is a weak metric for refusal cases. It works for factual questions with specific numbers or names. It breaks down whenever the correct answer is a refusal, because the wording of a refusal varies and keywords cannot capture meaning.
  • Low overall scores on unanswerable cases are a positive signal. High faithfulness + low context relevance on unanswerable cases means the bot correctly refused rather than hallucinating. Never read 33% or 50% overall as failure without checking each metric individually.
  • Near-zero similarity scores are actionable in production. Scores below 0.20 across all retrieved chunks mean the question is almost certainly outside the corpus. A similarity threshold check before calling the LLM could route these to a "not in scope" response — saving a model call and giving a faster, more honest answer.

Try This — Extend the Experiment

🧪 Experiment 1 — Change the bot model. In config.yaml, change BOT_MODEL from llama3.1:8b to mistral or deepseek-r1:7b. Re-run. Does TC21 (age 86) produce the correct answer with a stronger model? Does TC23 (arithmetic) still calculate correctly? Compare overall faithfulness scores across models.
🧪 Experiment 2 — Change TOP_K_CHUNKS. In config.yaml, change TOP_K_CHUNKS from 3 to 2, then to 5. How does TC08 (cross-document requirements) change? Does reducing to 2 cause more cross-document failures? Does increasing to 5 improve cross-document cases or introduce noise from irrelevant chunks?
🧪 Experiment 3 — Add a new document. Create a fourth .txt file in documents/ on a new topic (mortgages, insurance, savings accounts). Re-run chunker.py, then run the evaluator. What happens to existing test cases — do any scores change? What happens when you ask a question about the new document?
