Phase 4 — Frameworks & Tools

Test 11: DeepEval

DeepEval is a pytest-style LLM testing framework. Instead of writing your own scoring logic, you declare what you want to test and DeepEval runs the assertions. Every metric produces a PASS or FAIL verdict — not just a score. This test runs the same 25 RAG cases from Test 9 through DeepEval to compare framework-based evaluation against hand-rolled evaluation.

📁 phase-4-frameworks-and-tools/deepeval-evaluation/  |  test11_deepeval_evaluator.py · report_generator.py · rag_bot.py · retriever.py · chunker.py

What Is DeepEval?

Every evaluator you have built so far — Test 5 LLM-as-a-Judge, Test 6 Semantic Similarity, Test 7 Groundedness, Test 9 RAG — required you to write the scoring logic yourself. You decided what a good answer looks like, how to prompt the judge, and how to interpret the score.

DeepEval wraps all of that. You pass it a test case and a metric, and it handles the judge prompt, the scoring, the threshold check, and the pass/fail verdict. The output is closer to a test runner than a measurement tool — which is exactly the mental model a QA engineer already has.

🧪 The unit test analogy. In software testing, a test either passes or fails. You don't get a "72% correct" result from a unit test — you get green or red. DeepEval applies the same model to LLM evaluation. Each metric has a threshold (default 0.5 in this test). Score at or above threshold = PASS. Below = FAIL. This is a deliberate design choice — it forces you to define what "good enough" means before you run, not after you see the numbers.

How DeepEval Works — The Key Concepts

LLMTestCase — the unit of evaluation

Everything in DeepEval is built around a LLMTestCase object. You provide three things:

Field What it is In this test
input The question asked The Question column from Excel
actual_output What the bot said llama3.1:8b response via Ollama
retrieval_context The chunks the RAG bot used Top-3 chunks from retriever.py — as a list of strings

Once a LLMTestCase is built, you pass it to any metric. The metric sends it to the judge model and returns a score, a reason, and a pass/fail verdict.

OllamaModel — running without a paid API

DeepEval was designed with OpenAI as the default judge. To use a local Ollama model instead, you register it once via the CLI:

deepeval set-ollama --model=mistral --base-url="http://localhost:11434"

This writes a config file on your machine. After that, DeepEval uses mistral for all judge calls — no OpenAI key needed. In code, you instantiate OllamaModel and pass it to each metric.

⚠️ async_mode=False is required for local models. DeepEval defaults to async_mode=True — it fires multiple concurrent requests to the judge. Ollama cannot handle concurrent requests locally. It queues them, the async calls time out waiting, and scores default to 0.0 — appearing as FAILs. Always set async_mode=False when using Ollama. This is a one-line fix per metric: ContextualRelevancyMetric(threshold=0.5, model=judge, async_mode=False).

The three metrics

Metric DeepEval class What it judges Equivalent in Test 9
Contextual Relevancy ContextualRelevancyMetric Do the retrieved chunks contain what's needed to answer the question? Context Relevance (LLM judge)
Faithfulness FaithfulnessMetric Is every claim in the answer supported by the retrieved context, or was something invented? Answer Faithfulness (LLM judge)
Answer Relevancy AnswerRelevancyMetric Does the answer directly address what was asked? Answer Relevance (keyword matching in Test 9 — LLM judge here)
🔗 Key difference from Test 9: In Test 9, Answer Relevance used keyword matching — it checked whether expected keywords appeared in the bot's response. In DeepEval, AnswerRelevancyMetric uses the LLM judge — it asks whether the answer semantically addresses the question. This is a stronger, more flexible measure. It can recognise that "I cannot provide information about the CEO's salary" is a correct refusal even if none of the expected keywords appear.

The Timeout Problem — What Happened and Why

This is the most important finding from Test 11 — not the scores, but what caused the scores to break down.

What happened

TC01–TC15 ran correctly — mistral judged all three metrics per case and returned real scores. From TC16 onward, the terminal began printing RetryError[TimeoutError] warnings. When a metric times out, DeepEval catches the exception and defaults the score to 0.0, marking it as FAIL. By TC20–TC25, all three metrics were timing out on almost every case.

Why it happened

DeepEval's ContextualRelevancyMetric and FaithfulnessMetric are internally decomposed — they send multiple sub-prompts to the judge to build their score. Each case makes significantly more than 3 judge calls. After 15 cases (roughly 2–3 hours of sustained Ollama load), the machine's available RAM was exhausted, Ollama was swapping memory, and response times grew beyond DeepEval's internal timeout window — even with async_mode=False.

🚨 This is not a DeepEval bug — it is a local resource constraint. DeepEval is designed to run against a paid API (OpenAI, Anthropic) where response times are fast and consistent. Running it against a local Ollama model on a 16GB laptop for 5 hours is outside its intended use case. The framework works — the infrastructure does not scale to this volume locally.

The Context Relevance Calibration Problem

The single most striking pattern in TC01–TC15 is how harshly DeepEval's ContextualRelevancyMetric scored context relevance compared to Test 9.

Test 9 — Context Relevance (hand-rolled)
84%
Average across 25 cases. Most clean single-document cases scored 100%.
Test 11 — Context Relevance (DeepEval)
24%
Average across all 24 scored cases. TC01–TC15 had real judgements; TC16–TC25 had timeouts defaulting to 0.00 on most.

TC01 is a clean example: "How long does it take to open a NextGen account?" The retriever pulled the correct chunks. The bot gave the correct answer. Test 9 scored this context relevance at 100%. DeepEval scored it at 0.41 — a FAIL.

This is a calibration difference, not a system failure. DeepEval's ContextualRelevancyMetric internally asks whether each retrieved chunk is directly relevant to the question — it penalises any chunk that is topically related but not specifically needed. With TOP_K=3, the third chunk is often a supporting or nearby paragraph that adds background but is not the primary source of the answer. DeepEval's judge penalises this. Test 9's hand-rolled judge was more lenient — it asked "is there enough context here to answer?" rather than "is every chunk directly relevant?"

🎯 This is the key learning from Test 11. Two different judges, same metric name, meaningfully different scores. The label "context relevance" does not guarantee identical evaluation — it depends entirely on how the judge prompt is written. When you compare scores across evaluation frameworks, always check whether the underlying prompt is asking the same question. A score of 84% in Test 9 and 27% in Test 11 does not mean one system is wrong — it means the two judges have different calibration.

TC11 — Faithfulness 0.0 on a Correct Refusal

TC11: "What is the interest rate on a NextGen personal loan?" The bot answered: "The information provided in the context does not mention the interest rate on a NextGen personal loan." This is a correct answer — the documentation does not contain this information.

DeepEval scored faithfulness at 0.0. Why? FaithfulnessMetric decomposes the answer into claims and checks each claim against the context. A refusal statement like "the information is not available" is not a claim supported by a chunk — it is an absence of information. DeepEval's faithfulness judge does not have a category for "correct absence of claim" — it treats uncorroborated statements as unfaithful.

⚠️ Faithfulness metrics struggle with correct refusals. This is a known limitation across all faithfulness evaluators — not just DeepEval. When the correct answer is "I don't know", there is no chunk to support that statement. The judge marks it as a faithfulness failure. Human review is required for unanswerable cases — automated faithfulness scoring alone will systematically penalise correct refusals.

TC15 — The One PASS

TC15: "What is the difference between an inactive and a dormant account?" This is the only case that passed all three metrics.

Context relevance 0.58, faithfulness 1.00, answer relevance 1.00. The question has a clear factual answer that maps directly to the retrieved chunks. The distinction between inactive (12 months, no transactions) and dormant (24 months, no transactions) is precisely described in one chunk. No boundary reasoning is required. No multi-document synthesis. The retriever pulled the right chunk and the bot quoted it accurately.

✅ TC15 is the clearest signal that the pipeline works. When retrieval is clean and the answer is a direct lookup, DeepEval correctly issues a PASS. The 1/25 pass rate is not evidence that the RAG system is broken — it is evidence that the context relevance threshold (0.5) is strict relative to DeepEval's judge calibration, and that the timeout problem corrupted TC16–TC25.

When to Use DeepEval vs Hand-Rolled

Test 11 surfaces a genuine trade-off that you will face in production evaluation work:

  • Use DeepEval when you want fast setup, pytest integration, pass/fail verdicts for CI/CD, and you are running against a paid API with consistent response times. It reduces the amount of evaluation code you write and maintain.
  • Use hand-rolled evaluation when you need full control over the judge prompt, when you need to understand exactly why a case scored the way it did, or when you are running locally and need predictable performance. You also need hand-rolled evaluation when the framework's metric calibration does not match your definition of quality.
  • Use both when validating a new evaluation setup. If DeepEval and your hand-rolled scorer agree on a verdict, you can trust the verdict. If they disagree, investigate — the disagreement itself is a finding.
🎯 The calibration lesson. Before adopting any evaluation framework in production, run it on a set of cases where you already know the correct verdict — either from human review or from a trusted hand-rolled evaluator. Check how well the framework agrees. If it systematically disagrees on a category (e.g. all refusal cases), understand why before deploying it as your primary quality gate.

The Local vs Paid API Problem

The 5-hour runtime and timeout cascade from TC16 onward is a concrete demonstration of a trade-off you will face on every evaluation project:

Local Ollama
Free
Zero cost. Full privacy. But slow, memory-constrained, and not suitable for sustained multi-metric evaluation runs with frameworks like DeepEval.
Paid API (OpenAI / Anthropic)
~$0.50
25 cases × 3 metrics at gpt-4o-mini pricing. Fast, consistent, no timeouts. DeepEval was designed for this environment.

For learning and prototyping, Ollama is the right choice — it allowed you to run hundreds of iterations through Tests 1–10 without any cost. For production evaluation pipelines that need to run reliably, on schedule, and at scale, a paid API is the practical choice. The cost is lower than it appears — 25 evaluation cases costs less than a cup of coffee.

Key Takeaways

  • DeepEval works — the infrastructure is the constraint. TC01–TC15 scored correctly. The framework produced valid judgements. The failure was not in DeepEval but in running a sustained multi-metric evaluation against a local model on limited RAM.
  • Same metric name ≠ same score. Context relevance scored 84% in Test 9 and ~27% in Test 11. Both are valid — they measure the same concept with different judge prompts and different thresholds. Always validate a new framework against known results before trusting its scores.
  • Pass/fail verdicts force explicit quality standards. In Test 9 you observed scores and drew conclusions. In DeepEval you set a threshold before running. This is a better engineering practice — it prevents post-hoc rationalisation of results.
  • Faithfulness 0.0 on correct refusals is a known framework limitation. TC11 was a correct refusal scored as a faithfulness failure. This is not a bug — it is a calibration gap. Any production faithfulness evaluator needs a separate handling path for unanswerable cases.
  • LLM-judge answer relevance outperforms keyword matching. DeepEval's AnswerRelevancyMetric correctly handled refusal cases that Test 9's keyword matching scored at 0%. For real evaluation work, LLM-judge answer relevance is worth the extra judge call cost.
  • For production evaluation pipelines: paid API, not local Ollama. $0.50 for 25 cases at gpt-4o-mini. Reliable. Fast. No timeouts. The local model is for learning — the paid API is for production.
