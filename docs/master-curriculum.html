Using the dependency roadmap

Open Learning Roadmap and select a module or topic by name or ID. The required route includes the target and every transitive mandatory topic, each counted once, in suggested study order. Selecting a module uses every topic in that module as a target. Recommended preparation adds context and may be skipped. A conditional link applies only to the exercise named beside it. Implementation readiness describes skills or tool setup you can demonstrate independently, so those notes and preparation hours sit outside the academic dependency graph. A dash means that category has no prerequisite.

Tokens, messages and context windows, Objectives, dimensions and failure taxonomy and Structured output and schema validation have no mandatory course prerequisites. Start with M01-T01 for a first look at model behavior, M02-T01 for evaluation design, or M03-T02 if you already know basic Python and JSON and want to validate structured outputs.

  • I want to learn RAG evaluation. Select RAG system evaluation or Path D. Check the reference-answer prerequisites first. For an interpretation-only refresher, select Context sufficiency, answer correctness and citations. Use the conditional notes before changing a dense encoder or adding a judge.
  • I already know Python and deterministic evaluation. Verify the preparation checkpoints and use Path B's fixture as a diagnostic. Mark familiar topics completed only when you can demonstrate their stated result. For structured data and provenance, enter at Golden schemas, provenance and versioning once its prerequisites are met.
  • I only want to learn LLM-as-a-Judge. Select Pointwise LLM-as-a-Judge for pointwise scoring, or Path C to add calibration and pairwise ranking. Use optional extensions as needed.
  • I want to become a complete evaluation engineer. Use Path A through the production capstone, then choose specialization topics or Path G. A short route establishes the advertised skills for its target. Course-wide competency requires the broader assessments and capstone.

Why This Lesson Matters

Imagine calling your bank and asking about a fee. The person on the phone says, “I can’t confirm that from the information I have.” The answer may be in the bank’s handbook. Did anyone give them the right page?

The same thing can happen in a chat. A customer asks Harbor Leaf Bank for the Standard Savings minimum. The bank’s policy says ₹5,000, but the assistant can’t confirm it. Before rewriting the assistant’s answer, check what it received. Did the app leave out the page the assistant needed?

The chat assistant uses an LLM, short for large language model. It can write a reply based on the information it receives. In this lesson, you’ll follow that information into a request and see what happens when some of it is left out.

Harbor Leaf is fictional. Its policy sets a ₹5,000 minimum and a ₹100 monthly fee when the balance is below ₹5,000. These are teaching examples, not financial advice. The lab’s counts, limits, and prices are made up so you can check the arithmetic yourself.

Beginner Explanation

1. What a token represents

Say you want to count the words in “balance ₹5,000.” You might point to two groups separated by a space. A model works with smaller pieces of text called tokens. A piece might be a word, part of a word, a punctuation mark, or a piece that includes a space.

The program that splits text and gives each piece a number from its vocabulary is a tokenizer. The model works with those numbers. When it writes a reply, the numbers it generates can be turned back into text.

Try splitting “balance ₹5,000” into “balance”, “ ₹”, “5”, “,”, and “000”. That’s five pieces for two space-separated groups. This is a made-up split. A real tokenizer may split it another way. Try picturing a name you’ve never seen or the same phrase with extra spaces. Spelling, language, and formatting can all change where the pieces fall. Different tokenizers may also count the same text differently.

Why care about the split? Counting the pieces tells you how much information will fit and can help you estimate what a request costs. The splitting and numbering process is called tokenization.

A word count is only a rough guide. For a real request, use the model’s tokenizer or the service’s measured usage if you have it. Write down how you got the count. In the lab, you’ll use counts we supplied. Neither Python’s character count nor splitting on spaces can reproduce a model’s tokenizer by itself.

Think of the request and reply as two entries on a bill. Input tokens count the pieces sent to the model. Output tokens count the pieces it generates.

Suppose input costs 2 paise per token and output costs 6. Sending 42 input tokens costs 84 paise. Generating a six-token reply costs another 36. That’s 120 paise, or ₹1.20. The arithmetic is 42 × 2 plus 6 × 6. Room you leave unused for a longer reply is capacity. Our pretend bill charges for tokens processed or generated. Real billing depends on the service and features in use.

If you want to spend less, start by looking for text the assistant doesn’t need. Removing the policy might save a few tokens and leave the assistant without the answer.

2. Conversations are ordered records

Imagine reading a chat transcript where every line starts with the speaker’s name. You need to know who said what. In an app, each entry is a message. Its role tells you where it came from, and its content holds the text or other data.

When the customer asks a question, the app gathers the information it will send. That package is the request. What comes back is the reply. We’ll call one exchange a turn. The chat on your screen may show more history than the app sends on that turn.

Here are five role names you may see in an application. APIs differ in the roles they expose and how they represent instructions and tool calls. These descriptions explain the purpose of each role in the examples.

  • System. Model-facing instructions for how the assistant should act. In this lesson the system message says it is Harbor Leaf Bank's support assistant.
  • Developer. Instructions from the application builder. Here the developer says to use approved policy evidence and to say when an answer cannot be confirmed.
  • User. What the customer asks or supplies. “What is the Standard Savings minimum?” is a user message. If the user guesses ₹10,000, their guess is still user input. It has no policy authority.
  • Assistant. Text or a structured request produced by the assistant. A prior reply can appear as an assistant message in later requests. Its claim is evidence of what was said in the past. You still need a policy to establish whether the claim is accurate.
  • Tool. Data returned by a program the assistant or application used. In the example a lookup tool returns an approved policy excerpt. A lookup result can also contain a draft, an error, or text from an untrusted source. Review what it contains and where it came from.

Suppose the assistant asks a lookup program for the savings policy. That request to a program is a tool call. The excerpt the program sends back is a tool result. A real service interface, or API, may use an ID to match the result with the right call. The lab uses short records you can read by eye. Nothing runs a lookup.

Could you file a receipt against the right order if the order number were missing? A program needs the same kind of link between a lookup and its result.

Look at the message order, the sequence in which the records appear. In our example, you’ll see the instructions, the customer’s question, the assistant asking for a lookup, then the tool result. The assistant can use that result to answer. On the next turn, the app may include the earlier exchange with the new question.

If the result comes first, belongs to a different call, or is missing, the request can be rejected or the wrong evidence can be used. When you investigate, keep the request or a trace, a record that shows what happened.

3. Context windows and token budgets

Imagine packing one bag for an outbound trip and leaving space to bring something home. The things you pack and the things you bring back have to fit in the same bag.

In this lesson the shared space is the context window, the capacity for information the model can work with in a request and its generation. Instructions, messages, tool results, and the current question take up input space. So can extra pieces used to mark roles or organize a message. We call those extra tokens overhead. The reply takes up output space.

Some model interfaces impose a separate input limit or output limit. An output limit is the largest reply the interface allows. The lab also uses an output reserve, the room the application decides to leave for the upcoming reply. Choose a reserve inside the output limit. Actual interfaces differ in how they enforce limits or reserve space. Use their documented rules for real requests.

Let’s check a request before sending it. The model in our example has a 60-token window. Its separate limits are 54 input tokens and 16 output tokens. You leave 12 for the reply.

First subtract the 12 reserved tokens from the 60-token window. That leaves 48. The input has to fit under both 48 and 54, so you have an input budget of 48. The unused part of that budget is the headroom. With 52 tokens of input, the headroom is 48 − 52 = −4. You need at least four more tokens of room.

You could remove some input, leave a smaller reserve if the answer can still fit, or stop before sending the request. A smaller reserve makes room for input. It can also leave the assistant with too little room for a useful reply.

What can an app do when a conversation is too long? It can drop part of the history to make the request fit. This is called truncation. Our example keeps the instructions and the latest question and removes the oldest history it’s allowed to drop first. Other apps might summarize, pick the most useful evidence, or stop. The rule you see here belongs to this fictional app. Check what a real app actually keeps or removes.

Try the budget with three piles of input. The protected pile takes 28 tokens. An older exchange contains the policy and takes 14. Recent small talk takes 10. That’s 52, with room for only 48.

If you remove the oldest pile, you’ll have 38 tokens left and no policy. What if you remove the small talk instead? You’ll have 42 tokens left and still have the answer. Check the order of the kept conversation too. When a lookup call and its result belong together, keep or drop them as a group.

4. Diagnose a failure at the stage where it happened

Put yourself in the reviewer’s chair. First ask, “What could the assistant see?” If it had the approved excerpt and said ₹10,000, you can point to a contradiction. If it never received the excerpt and said it couldn’t confirm the amount, the reply followed the instruction to abstain, or decline to make a factual claim without enough evidence.

In that second run, the customer still didn’t get the answer. Look at how the app gathered or trimmed the policy before changing the assistant’s wording.

Keep three pieces of information together. Save the intended request and its token budget. Save the messages actually sent or the list of groups dropped before sending. Save the reply and whether it met the expected behavior for that input. This distinguishes a request construction problem from a problem in the reply. It also prevents an old assistant answer or a customer's guess from becoming the policy you grade against.

Step 1 — Store and inspect the messages

Let’s print the saved chat in order so you can spot a missing or misplaced record before judging the reply. Start with messages = .... The name messages is a variable, and = gives that name the value on its right. The square brackets hold a list, a collection that keeps its items in order.

Inside the list, each pair of braces holds a dictionary, a record with named fields. Text in quotation marks is a string. The names "role" and "content" are keys. A colon joins each key to its value, and commas separate fields and records.

Now read for message in messages: as “take each saved message in order and call the current one message.” The colon starts the loop’s body. The spaces on the left, called indentation, keep the print line inside that body.

On each pass, message["role"] and message["content"] look up the two fields. print() displays the values inside its parentheses. You give it three items separated by commas, so it places a space around the dash.

Step 3 — Calculate remaining context capacity

Will this request fit? Start with the four numbers at the top of the program. In context_window - reserve, - subtracts the room you want for the reply. min() picks the smaller of that allowance and the separate input limit, because you have to meet both.

Next, subtract input_tokens from that budget to find headroom. Read the two print lines as “what fits?” and “how much room is left?” A negative result means you need to free space.

input_limit = 54
reserve = 12
input_tokens = 52

headroom = input_budget - input_tokens

Step 4 — Simulate dropping old history

Suppose you have to make the request smaller. First, add up the protected 28 tokens and the two history groups. The old lookup and its result are one group, so removing them won’t leave an unmatched tool record.

Read while input_tokens > input_budget and history: as “keep doing this while the input is too large and there are still groups to try.” A while loop repeats while its condition is true. > means “greater than,” and requires both checks to hold, and a list used this way counts as true when it has items.

The dot in history.pop(0) gives you an operation on the list. pop(0) takes the first item out, at position zero, and hands it back. Save it as removed so you can subtract its tokens and print its name. At the end, read the new total and the names in the list that remains. This lets you see what you gave up to fit the budget.

protected = 28

Step 5 — See how missing evidence changes evaluation

What if you keep the reply the same and change only what the assistant could read? The first row has the policy. The second lost it. True and False mean yes and no here.

cases = [
    {
        "name": "Full request",
        "policy_present": True,

Step 7 — Build an offline context-budget diagnostic

Let’s put the budget checks in one place so you can try new values without rewriting the checks. A function is a named block you can run whenever you need it. def defines it. The names between the parentheses are parameters, the names it uses for the values you give it. The lines indented after the colon belong to the function.

Python saves those instructions when it reads them. The diagnose(...) line at the bottom actually runs them with this example’s numbers and history. A plain return ends the current run of the function early, which is useful when the request can’t fit.

Read the function from the top. reserve < 1 checks for fewer than one reserved token. or means either check can trigger the stop. A reserve above the output limit also stops the run. The next stop protects the required input. If that much won’t fit, trimming history can’t fix it.

If both checks pass, history.copy() makes a separate list. Removing entries from it leaves the original list alone. We don’t edit the dictionaries inside either list. As the loop trims, dropped.append(...) adds each removed name to the end of the report list. The last loop checks each kept group’s approved_policy flag. The function reports whether the request still has the evidence, as well as whether it fits.

def diagnose(window, input_limit, output_limit, reserve, protected, history):
    if reserve < 1 or reserve > output_limit:
        print("STOP: output reserve is outside the allowed range.")
        return

    budget = min(input_limit, window - reserve)
    print("Input budget:", budget)
    if protected > budget:
        print("STOP: protected input cannot fit.")
        return

    kept = history.copy()
    input_tokens = protected
    for group in kept:
        input_tokens = input_tokens + group["tokens"]

    dropped = []
    while input_tokens > budget and kept:
        group = kept.pop(0)
        dropped.append(group["name"])
        input_tokens = input_tokens - group["tokens"]

    policy_kept = False
    for group in kept:
        if group["approved_policy"]:
            policy_kept = True

    print("Dropped groups:", dropped)
    print("Input sent:", input_tokens)
    print("Input headroom:", budget - input_tokens)
    if policy_kept:
        print("Evidence: approved policy retained")
    else:
        print("Evidence: missing approved policy; expect abstention")

Beginner Explanation

1. Watch a reply take shape

Think of the suggestions that appear as you type on a phone. After “The minimum,” you might see “is” or “balance.” Once you add “is,” the next suggestions change. That gives you a way to picture how a model writes a reply.

A large language model, or LLM, takes the information you send and can generate text from it. Using an already-trained model to produce an answer is called inference. Training is the earlier work of adjusting the model using examples. In this lesson, we use the model as it is. The written instructions, question, and any attached policy together make up the prompt in our examples.

As you saw in the previous chapter, a token is a piece of text that the model can represent as a number. For each step of a reply, the model can give possible next tokens different chances based on the request and the tokens already chosen. A chance expressed as a number is a probability. Once the model picks a token, it uses the longer text to work out the next set of chances. Repeat and you get a reply.

Suppose the reply so far is “The minimum is”. In a classroom sketch, the next piece might start the amount or be a word such as “usually”. The possible pieces change after that choice. Try finishing both versions aloud. This is why a difference early in a reply can change what comes later. Our Python examples use prewritten pieces and invented chances. Real text can split into tokens differently, and a real model computes fresh chances at each step.

2. Choose the most likely piece or draw from several

Imagine a bag with 60 blue counters, 30 green ones, and 10 white ones. If you’re allowed to pick whichever color appears most often, you’ll choose blue every time while the bag stays the same. If you reach in without looking, blue is more likely than either other color, and you can still draw green or white.

Picking the highest-scoring next token is called greedy selection. Drawing a token according to its chance is called sampling. You can think of the chances as the proportions of colored counters. The model makes a decision for each next token. Greedy selection chooses the locally highest score. It doesn’t check every possible finished reply or verify the bank’s policy.

In the lab, we’ll draw from possible next words after “The minimum”: “is”, “balance”, and “required”. The invented chances are 60%, 30%, and 10%. Try drawing several counters from the bag and putting each one back. Some sets of four draws may all be blue. Others may include every color. Four attempts tell you what you saw. They give you only a rough picture of the long-run chances.

3. Change how much the choices differ

Suppose you run a quiz and give three choices different chances of being picked. You want your most likely choice to show up more often. You can widen its lead, while still allowing a less likely choice to be picked sometimes.

Temperature controls how strongly the model favors higher-scoring choices before a sampled draw. A lower positive temperature pushes more of the chance toward the strongest choices. A higher temperature spreads the chances more evenly across choices. At temperature 1, this adjustment leaves the original chances unchanged. Some interfaces use 0 to request greedy behavior. The supported values and behavior depend on the interface.

In the lab, we start with probabilities and raise them to the power of one divided by temperature, then scale them back to sum to 1. At temperature 0.5, this squares the probabilities. For 0.60, 0.30, and 0.10, the squared values are 0.36, 0.09, and 0.01. Divide each by their total, 0.46, to get a new set of probabilities. The first choice rises from 60% to about 78.3%. At temperature 1, the first choice stays at 60%. This arithmetic illustrates the usual score adjustment using an already normalized set of probabilities.

Would the higher chance make a bank answer more accurate? Ask which choice got the extra chance. If the preferred amount is wrong, making it more likely can repeat the error. Review the claims against the policy before choosing settings for a customer-facing use.

4. Decide how many likely choices to keep

Think of putting the most-used tools in a small toolbox. Start with the most useful one. Add the next until you’ve covered enough of the jobs you expect to do. A tool just beyond that line stays outside the box.

Top-p, also called nucleus sampling, sets a cutoff for the combined probability of choices to keep. Put the choices in order from highest probability to lowest. Keep adding them until their probabilities reach or exceed the cutoff. Include the choice that crossed the line, then scale the remaining chances so they sum to 1 before drawing. Implementations can have details such as tie handling. This example has no ties.

Using 60%, 30%, and 10%, try a cutoff of 80%. The first choice only covers 60%, so keep the next one too. You now cover 90% and leave out the third. Divide the two kept chances by 90% to get about 66.7% and 33.3%. Now try 95% on paper. You’ll need all three, so each retains its original chance. A lower cutoff can remove choices entirely. Temperature adjusts their chances. Change one setting at a time in an experiment so you know which change you’re examining.

5. Repeat a draw and record what was held fixed

Imagine a friend following a numbered list of draws that looks random. Start them at the same place, follow the same directions, and they can repeat the list. Start in a different place and you may see a different order.

A pseudorandom number generator is a program that makes a sequence of numbers that behave like random draws for tasks like this. A seed is a starting value for that program. In our Python lab, each time you create a fresh generator with the same seed and perform the same operations, you get the same sequence. Reusing a generator for more draws continues its sequence. It doesn’t go back to the beginning.

Repeatability asks how consistently you get the same result under stated conditions. A real model interface may accept a seed or offer another way to request more repeatable replies. The same seed can help under matching conditions. It cannot fix changes in the input, settings, model version, or the system running the model. Tiny differences in the calculations, or differences in how a service processes requests, can also affect which piece wins. Even a greedy request can vary across environments or versions.

A model snapshot is a specific published version of a model, where the provider makes one available. A general name may point to a different version later. If you compare March’s results with today’s and you saved only the general name, you may have changed the model without realizing it. Record the snapshot or other version information you actually have, and flag what’s unknown. A version ID makes a comparison easier to explain. Other parts of the request may still have changed.

6. See why a reply ended

You ask a colleague to give a short announcement. They might finish the sentence, stop at an agreed cue, or get cut off when time runs out. In every case you stop hearing words, but the reason tells you what to do next.

Maximum output tokens cap how many tokens the model may generate for a request. If it uses the entire allowance and could have continued, you may see a length-related ending. Suppose “The minimum is” is all that fits. You received words, but the customer still needs the amount.

A stop condition is any rule that ends generation. It might be the output limit, a special end marker generated by the model, or a configured text sequence. Different interfaces may report stop reasons or hide markers differently. This lab uses the classroom marker “<END>” to signal an intended end. The program doesn’t show that marker in the reply.

A timeout means part of the system waited longer than allowed and ended the attempt. A timeout with no reply gives you no amount to check. If an answer arrives and claims ₹10,000, that’s a different result. Save what ended the attempt, then check any usable answer against the policy. If the result doesn’t tell you why it ended, record that the reason is unknown.

7. Use the evidence a fair comparison gives you

If you bake one tray at a different oven temperature and it turns out better, how much did you learn? Perhaps the dough was colder, or that tray was on a different shelf. Bake more than one tray and keep track of what stayed the same.

In a model comparison, keep the actual questions, instructions, policy, and scoring rules the same. Save the model snapshot, temperature, top-p, seed or seed schedule if available, output cap, and stop settings. A seed schedule is the list of starting values you plan to use across attempts. Save the returned text, version and settings information you received, and the reason each attempt ended. When a service only provides some of those details, keep that limitation visible.

First repeat the same setting to see what variation you observe. Then compare two settings across the same cases and planned repeat counts. If you can match starting settings and seeds for each case, record those pairs. In a live experiment, mix the order of the two settings rather than running all of one first. A service could get busier or run differently later, affecting failures or timing. Keep incomplete answers and attempts with no reply visible alongside policy scores.

Two answers may read differently and both satisfy the policy. Check meaning as well as exact wording. Report what changed in *these* attempts. A couple of replies can suggest where to investigate. They don’t establish how every model will behave or whether one setting is ready for release.

Step 3 — Adjust the chances with temperature

You’ll now change the chances before drawing. Start from the 60%, 30%, and 10% you already know. At temperature 0.5, see how much of the chance moves to “is.”

In Python, / divides and ** raises a number to a power. Read chance ** (1 / temperature) as “divide 1 by the temperature, then raise this chance to that power.” append() adds an item to the list named before the dot. The first loop makes a list with the new weights. sum() adds those weights. Dividing each by the total turns the weights back into probabilities you can draw from.

In the print line, an f before a quoted string lets you put values into it using braces. In {chance:.1%}, .1% tells Python to show a fraction as a percentage with one digit after the decimal point. It rounds each line for display. The full numbers can sum to 100% even if the individually rounded lines don’t.

Copy and run. Paste this program and run it. Compare the first printed chance with its original 60%.

temperature = 0.5
original = [0.60, 0.30, 0.10]
weights = []

for chance in original:
    weights.append(chance ** (1 / temperature))

total = sum(weights)
print("Temperature:", temperature)
for weight in weights:
    chance = weight / total
    print(f"Chance: {chance:.1%}")

Step 4 — Keep enough choices to reach a cutoff

Try setting aside the least likely choices before you draw. We’ll use whole percentage points so you can add them on paper. This is top-p with a cutoff written as 80 out of 100 rather than 0.8 out of 1.

Each pair inside parentheses is a tuple, two values kept together in order here. The list is already sorted from most likely to least likely. for word, points in choices: takes the two values from one pair and gives them their own names. This is called unpacking. The loop keeps the pair, then adds its points. When >= (“at least”) becomes true, break ends the loop. The pair that reached the cutoff has already been kept.

The final loop divides each kept entry’s points by the total kept. This is what gives you chances that sum to 100% across the smaller set.

Copy and run. Paste the block and run it. Predict how many choices you’ll keep before the 80-point cutoff is reached.

cutoff = 80
choices = [("is", 60), ("balance", 30), ("required", 10)]
kept = []
covered = 0

for word, points in choices:
    kept.append((word, points))
    covered = covered + points
    if covered >= cutoff:
        break

print("Covered points:", covered)
for word, points in kept:
    chance = points / covered
    print(f"{word}: {chance:.1%}")

Step 5 — Repeat a set of draws with a seed

Now let Python supply the draw positions. To see what a seed can control, start two fresh number generators with the same seed and use each for four draws. Think of these as four separate attempts at picking the next piece after “The minimum.” The starting text and chances reset for each attempt. The generator keeps moving through its number sequence.

The import random line makes Python’s standard tools for simulated draws available. random.Random(seed) creates a fresh generator. Each generator.random() gets the next number from 0 up to but excluding 1. The * sign multiplies that number by 100. int() drops the decimal part so you get a position from 0 to 99. The tests then use the same ranges as Step 2.

A function is a named block you can run again. def show_draws(seed): names the work and gives it a name, seed, for its input. The indented lines run each time you call the function. range(4) supplies four positions, starting at zero. The name turn marks which repetition you’re on. The print line adds one so the report starts at 1. Calling show_draws() with a value starts the function and creates the generator inside it again.

import random


def show_draws(seed):

            piece = "is"
        elif draw < 90:
            piece = "balance"
        else:
            piece = "required"
        print(turn + 1, draw, piece)

You’re helping the bank decide what to test next. We’ll use the eight saved attempts from Example 3. Each setting has four starting seeds. Save the shared settings and count the outcomes separately, so a timeout or cutoff stays visible in the report.

Read each row as a tuple with five entries. In order, they are temperature, seed, stop reason, reply, and policy review. None means a value is absent. On a timeout there is no reply or policy review. The cut-off reply is saved, but it’s missing the amount, so it has no policy review label in this exercise. The other policy labels were assigned by a human who checked the savings policy.

Common Mistakes

  • Calling every wording change a mistake. Compare what each answer says. “Five thousand rupees” and “₹5,000” can express the same requirement.
  • Expecting one draw to reveal the effect of a setting. Repeat both settings. Read the individual answers before interpreting the counts.
  • Assuming lower temperature fixes incorrect answers. It can give a wrong but favored choice even more weight. Check the policy claims directly.
  • Reading top-p as a fixed number of choices. Start at the strongest and add their chances. The total you need to reach determines how many you keep.
  • Saving the seed and forgetting the rest of the request. Save the full input, snapshot if available, other settings, and outcomes. Look for changes when two runs disagree.
  • Dropping short or missing replies from the report. Record what ended the attempt. Report all attempts as well as the subset you could assess.

Beginner Explanation

1. Start with what the customer sees

Think of a calculator on a phone. You tap keys, and a program follows a rule to show the result. A program or group of programs that helps someone do a task is an application, often called an app.

A banking chatbot still has a screen and rules. It also uses a large language model, or LLM, to write replies. The model takes in information and produces text. As you saw in the previous lessons, it works with pieces of text called tokens and can produce different wording across attempts. Some apps without an LLM also vary. The distinction here is which work the bank’s app gives to a language model and which rules the app follows itself.

The chat box, send button, and reply make up the user interface. These are the parts the customer interacts with. If you press Send and a reply appears, you’ve seen the screen handle that interaction. You still need to read the answer. Imagine a correct answer hidden behind a blank screen, then a wrong answer shown beautifully. Those problems happen in different places.

2. Give each part of the app a job

Think back to the café. Someone takes the order, someone checks what ingredients are available, and someone prepares the food. The arrangement of the parts and how they work together is called architecture. An app can split these jobs across programs or do several of them in one program. Here’s how they work at Harbor Leaf Bank.

The screen sends the customer’s question to a part that decides what happens next. That decision-making code is the application logic. It checks that there’s a question to answer and decides what information to look for. The part that asks another program to do something is called a client. The program that receives that request and performs the work is a server. The chat screen can be a client of the bank’s app. The bank’s app can in turn be a client of the model server.

The app searches the bank’s approved material for the Standard Savings policy. That collection is the knowledge source. The search and selection step is called retrieval. If the app asks a separate lookup program to do the search, that program is a tool. Open the right page in a handbook and you have what you need to answer. Open an old page or come back without one and the same question can be much harder.

Now collect the question, the policy excerpt, and an instruction such as “Use the approved information. Say when you can’t confirm an answer.” The material the app sends to the model makes up the prompt here. Putting it together is prompt assembly. The model is the part asked to write the response. You can change the prompt while keeping the same model, just as you can give a person different instructions for the next order.

Using the trained model to generate a reply is inference. A program that receives the request and runs the model is an inference server. It may return the reply along with details such as which model ran or why it stopped. The bank’s app can then extract the text, check that it is usable, and hand it to the screen. Work done after receiving the model’s result is called post-processing. Formatting an answer and verifying its amount are separate checks.

3. See what crosses from one program to another

Imagine two people who agree to exchange orders using a form. A clear form tells them which details to send and where to find the answer. An application programming interface, or API, is an agreed way for programs to use each other’s features. Here it tells the bank’s app what to send to the model server and what to expect back.

One common way to send the request is HTTP, a set of rules programs use to exchange requests and responses. Think of the request as “Please do this work” and the response as “Here is what happened.” An HTTP status such as 200 can mean the server handled the request successfully. The policy claim in the body still needs checking. If the app waits too long and gets no response, it may report a timeout. That’s a kind of transport error, a problem getting a request or response across the connection in this example. A timeout by itself leaves you unsure whether the server ever started or finished the work.

JSON is a way of writing structured information as text. Think of a little form with named boxes. The JSON text {"reply": "The minimum is ₹5,000."} has a field named “reply” and a value containing the answer. Braces surround the form. The colon joins the field name to the value. Quotes mark where text starts and ends. A program can read that text into data it can use. Reading a format this way is called parsing.

Suppose the app receives the text {"reply": and nothing follows. Some data arrived, but the form is unfinished. That’s malformed JSON, text that breaks the format rules. Start by checking what the app received and how it tried to read it. You have different evidence from a timeout with no response or a readable reply with the wrong amount.

4. Walk the question to the model and back

Trace the arrows. The engineer at the end looks back at the evidence saved during the journey.

Request → Chat screen → App receives the question → App selects the approved policy → App packages the instructions, question, and policy → Inference server

5. Keep a small record of what happened

If a delivery goes missing, a list of times and stops can help you see how far it got. A log is a saved record of events. 6. Check the basics before doing a full evaluation

After a mechanic works on a car, they may start it before taking it on a road test. Starting the engine answers a useful first question. It doesn’t tell you how well the brakes work on a wet road. A smoke test is that quick first check for an app. Pick one or a few important paths and see if they work well enough to continue testing.

At Harbor Leaf Bank, ask a known question and check whether the app returns a readable reply with the approved amount. A smoke test can catch a broken connection, an unreadable reply, or a known answer that suddenly gives the wrong amount. It covers the particular path you tried. A more detailed evaluation checks behavior across many situations against clear rules. Later you’ll try alternate wording, different policies, and questions the bank cannot answer.

Before pressing Send, write a test case. It says what you’ll give the app, which conditions apply, and what should happen. For example, give the app one Standard Savings question with the approved ₹5,000 policy. The expected result is a readable answer with that amount. The actual result is what you observed when you ran the case. A status records how those two compare.

  • PASS. The check met its stated expectation. If you ask about an ATM limit absent from the supplied policy and expect a clear “I can’t confirm,” that reply can pass.
  • FAIL. You know the expectation was missed. A reply of ₹10,000 fails the policy check. A timeout fails the basic delivery check if the test expected a reply. Record which check failed. The timeout left no answer to judge for correctness.
  • NEEDS REVIEW. You lack enough information to judge the observation. Perhaps there’s a readable reply but no approved expectation for that case. Ask for the missing evidence or for a person to review the meaning. Keep this outcome visible when you count results.

Write a two-part checklist before you look at an answer. First ask “Did I get a readable reply?” Then ask “Does it meet the expectation?” If the first answer is no, record the delivery or format failure. Leave factual correctness unscored.

import json

minimum_question = "What is the minimum balance for a Standard Savings account?"
atm_question = "What is the daily ATM withdrawal limit?"
waiver_question = "Does the student fee waiver apply?"
topics = {minimum_question: "minimum"}
policy = {"minimum": "The minimum is ₹5,000."}
expected_minimum = "The minimum is ₹5,000."
fallback = "I can't confirm that from the approved policy."


def simulate_reply(approved, mode):
    if mode == "timeout":
        return None
    if mode == "malformed":
        return '{"reply":'
    if approved is None:
        reply = fallback
    elif mode == "wrong":
        reply = "The minimum is ₹10,000."
    else:
        reply = approved
    return json.dumps({"reply": reply})


def smoke_check(question, mode, expected):
    topic = topics.get(question)
    approved = policy.get(topic)
    raw_result = simulate_reply(approved, mode)
    if raw_result is None:
        return "FAIL", "transport: no reply before timeout"
    try:
        result = json.loads(raw_result)
    except json.JSONDecodeError:
        return "FAIL", "response handling: unreadable JSON"

    reply = result["reply"]
    if expected is None:
        return "NEEDS REVIEW", reply
    if reply != expected:
        return "FAIL", "unexpected text: " + reply
    return "PASS", reply

  4. Check each layer. A success status indicates success at the HTTP request level. A readable JSON reply gives you structured information you can inspect. You still have to check for the reply field and judge the answer against the policy.

  6. Decide using the expectation. PASS if the case explicitly requires a fallback and receives it. NEEDS REVIEW if you got readable text but don’t yet know what the assistant should say for that case. Record why.
  7. Scope the result. A smoke test shows the checked path met its expectation on that attempt. Try more questions and repeat runs to learn how behavior varies, using the same evaluation rule where it applies.
  8. Compare both sides of the handoff. Keep the selected policy and the actual request, the raw model result, and the text the user saw. If the returned amount is right and the displayed amount differs, investigate reply handling.

Common Mistakes

  • Treating the screen as the entire application. If the server saved ₹5,000 and the chat shows ₹10,000, check what happened after the response. If the server saved ₹10,000, follow the question further back.
  • Treating the prompt as the model. You can attach a different sentence about the fee while sending both requests to the same model. Keep a record of the instructions and the model version separately so you can see what changed.
  • Calling an app reliable after one correct reply. One correct ₹5,000 reply leaves open how the app handles another wording, a fee question, or a long conversation. Try those paths and repeat a few cases.
  • Calling a smoke test a full evaluation. A successful lookup gets you to the next round of tests. A full evaluation plan needs explicit goals and varied cases. Include questions where the app should say it can’t confirm the answer.
  • Expecting a simulator to behave like a model. If you replace one word in the question, the exact lookup may fail. A real model can respond to new wording. The simulator gives you predictable ways to practice checking what the app received and returned.
  • Marking a technical error as a wrong policy answer. A timeout gives you no claim to check. Malformed JSON can stop the app before it has readable text. A readable answer of ₹10,000 gives you a policy mistake to investigate directly.

Beginner Explanation

1. Evaluation starts with something you can check

You’ve already checked one answer. The response is the text the assistant returned. The system writing that text is an LLM, short for large language model. It generates text from the information it receives.

A deliberate check of how that response or the system behaves is an evaluation. In the opening example, your purpose was to check a policy amount. You had one answer, one policy line, and a clear reason to say the answer was wrong.

What should settle the answer? Use the policy the bank has authorized for this question. We call it the approved reference.

Try “You need ₹5,000 for that account.” That still agrees with the policy. Now imagine a reply that repeats “Standard Savings Account” but gives ₹10,000. The words sound official, yet the amount is wrong. Read for what the reply claims.

A single example can tell you what to look at next. It can’t tell you how the assistant will handle the next customer. Save the question, the evidence, and what a good reply should do. Together, those make a case you can check again. Build a few different cases so the team can see what to fix or whether to let users try the feature.

2. Define the decision, the evaluation unit, and success

Imagine two teammates agree to “make the bot better.” One checks that answers are friendly. The other checks whether the fee is right. They can come away with different verdicts because they were looking for different things.

Write down the decision first. “Before releasing the Standard Savings FAQ assistant, check that it answers balance and fee questions from the approved policy and safely handles requests it cannot answer or should not handle.” This is your evaluation objective. It tells both reviewers what to look for and why. The style of the answer can still matter. For this release decision, getting fees and balances right comes first.

Say you asked three questions and saved three replies. To check the answers, take one question and its reply at a time. The thing you judge together is your evaluation unit. Here it’s one response to one question under one policy version.

Why decide this before counting? If one reply has three mistakes, it’s still one failed reply in a response-level pass rate. If a question gets no reply because the request takes too long, that attempt can still count when you check whether the service responds. And if your goal is to judge several turns together, you can make the whole conversation the unit. Choose the unit that answers your question, then use it consistently.

Look at “answer the balance question well.” How would you tell two reviewers to check it? Try “State that the Standard Savings minimum is ₹5,000 without giving a conflicting amount for that account.” That’s a success criterion, a rule you can apply to one unit and point to evidence for.

For a customer who also asks about the fee, add “State the monthly fee and when it applies.” For safety, add “Never ask for a PIN.” A counterexample shows where a rule would be broken. Try “₹5,000 or ₹10,000, whichever you prefer.” Seeing the right number once doesn’t make that reply pass the rule against conflicting amounts.

Try writing your own criterion for an unanswered question. “Respond politely” is too broad for this purpose. A checkable version is “If the supplied reference cannot answer the policy question, the assistant says it cannot confirm the answer and does not invent an amount.” You will use a case like this in Practice 4.

3. Know what each evaluation dimension asks

Think about giving a friend directions. The directions can take them to the right street and still leave them unsure which door to use. You can ask different questions about one answer.

Each property you check is a dimension. Before reading the reply, use the customer’s question and the policy to decide which dimensions matter. Here we’ll start with two that are easy to mix up.

Correctness and completeness

Start with the amount. The assistant says ₹10,000. The policy says ₹5,000 for the same account. The two facts conflict. You’re checking correctness, whether the reply’s claims are accurate. A confident number still needs to match what you can verify.

Now ask for the minimum *and* what happens below it. “The balance is ₹5,000” gets the amount right, but what happened to the fee? You’re checking completeness, whether the reply covers everything the question or rule requires.

Try writing down the two requested parts first. Extra sentences about online banking won’t fill the blank next to “fee.” In Practice 2 you’ll make a separate judgment about each dimension.

Relevance and groundedness

Say you ask for directions to the entrance and someone tells you the building has a nice café. That could be true without helping you find the door. Relevance asks whether the reply addresses what the person asked.

“Harbor Leaf Bank offers paperless statements” can be an approved fact and still miss the balance question. Look for what each substantial part of the reply does for this customer. Mentioning the right bank isn’t enough.

Now suppose the balance policy is all the assistant received. It says, “The minimum is ₹5,000, and the bank will waive every fee if you ask.” Can you point to the line about waivers? You can’t. Groundedness asks whether the evidence supplied to the assistant supports what it says.

For each claim, try pointing to the sentence that supports it. If there isn’t one, record the claim as unsupported under this reference. Your judgment is about what the assistant had for this case.

Often, the same policy settles both questions. What if you find a separate, trustworthy policy later and it confirms a fee the assistant stated? The number may be correct, and the original reply can still fail groundedness if the assistant only had the balance excerpt.

The reverse is possible too. An answer can accurately follow an old policy it received and be wrong for today’s customer. Check which version was sent before deciding that the assistant made the amount up. If you can’t establish the facts, record “needs review” for correctness.

Usability and safety

Imagine reading the reply on your phone while deciding whether to open the account. “The applicable threshold is INR 5e3, subject to the aforementioned product schema” gives the figure ₹5,000 in a form you may have to decode. “Keep at least ₹5,000 in the Standard Savings Account” tells you what to do.

You’re judging usability, how easily the intended reader can understand and act on the answer. Both answers can name the same amount. Ask which one lets the customer act without guessing.

Now imagine the reply says, “The minimum is ₹5,000. Send your PIN to confirm.” A PIN is a secret number that protects access. The customer doesn’t need to share it to ask about public account terms, and the bank’s chat rules prohibit asking for it.

That’s a safety problem, something in the reply that could cause avoidable harm. Check for unsafe requests even when the amount is right. Friendly wording or a disclaimer doesn’t clear the request for a secret. You’ll give it a separate label in Practice 3.

Cost and latency

Suppose two versions give the same correct, safe answer. One takes 0.9 seconds and costs ₹0.04 per request. The other takes 3.4 seconds and costs ₹0.18. The money spent processing a request is its cost. The time from sending the question to getting the full reply is its latency in this exercise.

Say the team set limits of 2 seconds and ₹0.10 per request for a small trial. Which version meets both on this attempt? The first one. Check the timing and spending recorded beside the reply. The word “instant” in the reply can’t tell you either number.

Cost and latency are separate from the quality of the wording. A cheap, fast answer still fails a safety rule if it asks for a PIN. A slow answer can be factually right and fail a speed target. Before drawing a release conclusion, repeat measurements under comparable conditions and include slow or failed attempts in the availability discussion. One observed request does not establish typical performance. Knowledge Check 7 asks you to make a scoped decision using both limits.

4. Describe what failed before deciding why it happened

Suppose the assistant gives ₹10,000. That specific mistake is an error. Because it broke the balance rule, the check records a failure. If you scored the answer against a retired policy or your scoring program misread ₹5,000, the error was in the evaluation. Fix the check and rerun it before asking the assistant team to change anything.

What if the request took too long and no reply arrived? The system failed to deliver an answer. There’s no wording to score for correctness.

Imagine a repair list where every item just says “broken.” You’d still have to open each one to know what to fix. A failure taxonomy is a shared set of labels for the kinds of problems you saw. Start with labels that send reviewers to different next steps.

  • Incorrect fact. A claim conflicts with a known fact, such as ₹10,000 instead of ₹5,000. Check the approved policy, then trace where the incorrect number entered the answer.
  • Missing required information. The reply leaves out a requested part, such as when the fee applies. Improve the instructions and test more two-part questions.
  • Irrelevant content. The reply supplies material unrelated to the customer's request. Check whether it followed the question and selected appropriate context.
  • Unsupported claim. A claim cannot be backed by the available reference. Ask the assistant to stick to the supplied evidence or say it cannot confirm the claim.
  • Hard to use. The reply obscures a needed next action or uses wording the expected reader cannot readily understand. Rewrite and compare with a customer-readable answer.
  • Unsafe request. The reply asks for a secret or gives an unsafe instruction. Block release for the affected flow and test variations after a fix.
  • Operational failure. There is no usable reply due to a timeout, or a measured operational target was missed. Inspect timing, spending, or request failures independently of factual judgments.

Label what you can observe. For one conflicting amount, use “Incorrect fact” as the main classification for that claim. A separate unsupported waiver claim earns “Unsupported claim.” This convention gives you more useful counts than treating every contradictory amount as a second, independent unsupported defect. Keep both dimension judgments in your notes if they matter. If no answer exists, mark response dimensions N/A, meaning not applicable for that attempt. A missing or untrusted reference when a response does exist calls for “needs review” on claims you cannot assess.

After assigning a failure label, investigate the root cause, the underlying reason the problem occurred. A wrong amount could have come from old policy, wrong evidence selection, or an answer generated despite the right excerpt. Inspect what the system received before prescribing a fix. Teams can use the categories to prioritize a severe safety issue, decide what evidence to collect next, and retest the same cases after an update. A small teaching set is a starting point for that work. It cannot establish production readiness on its own.

What you are learning. Separate review signals so a teammate knows which part of a reply to inspect. Step 6 — Introduce functions

What you are learning. Put one rule under a name so you can use it repeatedly. Keeping the rule in one place helps every case receive the same check.

You don’t need to copy the whole rule for each reply. Give it a name and reuse it. A function is a named block of work. def sets it up, and the names in parentheses are parameters, the names it uses for the values you send it. The colon and spaces mark which lines belong to it, just as they do for if and for.

Follow the first print(minimum_signal(...)) from the inside out. The inner call runs the rule on the supplied reply and amount. The return line ends that call and hands back the message. The outer print() shows the message.

Copy the whole block, paste it in place of Step 5, and run it.

def minimum_signal(response, expected_amount):
    if expected_amount in response:
        return "Minimum text found"
    else:
        return "Review: minimum text missing"

Step 7 — Complete mini evaluation program

What you are learning. Turn the previous checks into a repeatable report. Every saved reply answers the same question here. “What is the minimum balance, and what happens if I fall below it?” The approved policy requires a ₹5,000 minimum, a ₹100 monthly fee below the minimum, and safe handling of PINs.

Read the three parts before running.

  1. The rules. The function starts with an empty list, []. The dot in flags.append(...) uses the list’s append operation, which adds one label to the end. The fee rule uses or. It raises a flag if either the fee amount or the word below is missing. The function returns the complete list for this reply.
  2. The saved cases. Each item in responses is a fictional reply to the same question. The list includes a correct baseline, a correct paraphrase, a contradictory answer, and a reply that needs several reviews.
  3. The report. The outer loop processes one reply at a time. print() with empty parentheses adds a blank line. if flags means “does the list contain anything?” When it does, the inner loop prints each flag on a separate line. Its extra indentation keeps it inside the if block. An empty list gives “No rule flags.”

Worked Solutions to Practice

Solution 1

Reply B fails correctness. “₹10,000” contradicts the approved ₹5,000 minimum, so label it Incorrect fact. It is still relevant because it directly addresses the minimum. Reply A meets both checks. You do not need an exact word-for-word match with the reference to accept A.

Solution 2

The stated ₹5,000 is correct. Saying a fee may apply does not conflict with the policy, but the reply is incomplete because it never gives ₹100 or the condition “below ₹5,000.” A better reply is “Keep at least ₹5,000 in Standard Savings. A ₹100 monthly fee applies if your balance falls below ₹5,000.” The fix adds the missing parts without changing the true amount.

Solution 3

The ₹200 claim is an Incorrect fact because ₹4,000 is below the threshold and the policy charges ₹100 monthly in that situation. “Unlimited fee waivers for students” is an Unsupported claim because the approved text says nothing about waivers. The PIN instruction is an Unsafe request because the chat policy forbids it. The travel insurance sentence is Irrelevant content for a fee question, even if it were accurate. Hold the release for the PIN-collection path first. Then investigate the fee source and ensure unsupported waivers are never promised. Count this as one failed response with four labels.

Solution 4

A usable objective is “Before releasing this FAQ flow, check that supported policy answers are correct and complete, unsupported questions disclose the gap, and account-specific help never asks for a PIN.” One evaluation unit is one response to one question under the supplied policy. These are four valid dataset rows.

  1. Balance. Ask “What minimum do I need?” Supply the Standard Savings reference with ₹5,000. Expect that amount for this account with no conflict. Flag a wrong amount.
  2. Two parts. Ask “What is the minimum and when do I pay a fee?” Supply ₹5,000 and the ₹100 monthly fee below it. Expect both amounts and the condition. Flag an omitted fee trigger.
  3. Unsupported question. Ask “What is my ATM withdrawal limit?” Supply only the balance-and-fee reference. Expect the assistant to say it cannot confirm the limit from this policy and direct the customer to approved support if needed. Flag an invented limit.
  4. Sensitive request. Ask “Can I send my PIN so you can check my own balance?” Supply the chat policy forbidding PIN requests and allowing referral to approved support. Expect the assistant to tell the customer not to share the PIN and point them to approved support. Flag any request to submit it.

An unsafe request in row 4 should stop the release. A wrong published amount should also block this narrow FAQ flow until corrected. Passing all four rows gives evidence about those four situations. Broaden the questions and phrasings before claiming the feature is ready for real traffic.

Knowledge Check

  1. The assistant writes a natural sentence with ₹10,000 while the reference says ₹5,000. Which check exposes the defect, and why does fluency not save it?
  2. A reply gives the correct balance but omits the fee in a two-part question. How do you rate correctness and completeness?
  3. The reference covers only balance. A reply mentions a fee waiver. Can you mark that claim grounded, and what would change your answer?
  4. The same reply misstates the amount, requests a PIN, and digresses about insurance. How many responses and how many categories do you record?
  5. The request times out. Which category applies, and what do you record for correctness?
  6. The exact-token check flags “five thousand rupees” as missing ₹5,000. Is this enough to reject the answer?
  7. A correct, safe response takes 3 seconds and costs ₹0.07. The fictional test limits are 2 seconds and ₹0.10. What can you conclude about this request?
  8. Two reviewers disagree because one uses an older approved balance amount. What should they verify before calling the assistant wrong?

Knowledge Check Answers

  1. Correctness. The numerical claim contradicts the approved evidence. Fluency only tells you the sentence reads naturally.
  2. Correct for what it says, incomplete for what was asked. The balance can pass while the required fee information is absent. Record the omission separately.
  3. Flag it as unsupported under the supplied reference. You need evidence available for the case that actually authorizes that waiver. A vague mention of fees is insufficient.
  4. One response with three failure categories. Record Incorrect fact, Unsafe request, and Irrelevant content. Counting three failed responses would misstate how many times users saw a bad reply.
  5. Operational failure. Record the attempt and timeout. Mark factual correctness N/A because there is no wording to evaluate.
  6. No. The literal rule found different wording. Both expressions can represent the same amount. Compare the amount to the reference before assigning a factual label.
  7. This request passes the cost limit and misses the latency limit. Nothing in that comparison overturns the quality result. Repeat timing measurements before making a general performance claim.
  8. Verify the policy version that governs the case and the excerpt actually supplied. A stale reference is a problem with the evaluation inputs. Rescore using the approved version for the stated objective.

Common Mistakes

  • Assuming a fluent answer is correct. Underline the factual claim and compare it with the approved reference. Tone alone cannot tell you which balance is right.
  • Treating correctness and groundedness as identical. Ask whether a claim is accurate and whether the supplied evidence supports it. If you lack enough evidence for the first question, record uncertainty rather than guessing.
  • Reporting one overall score. Keep the dimension labels and examples alongside an overall verdict. This exposes severe failures, even when most other checks pass.
  • Confusing an individual error with a broader failure. A wrong number is the observed mistake. The failed criterion is the consequence. Check whether stale evidence, the assistant, or the evaluator caused the mismatch before selecting a fix.
  • Choosing dimensions without a clear objective. Decide which decision the evaluation serves first. A public FAQ pilot may focus on policy accuracy and safe handling. Chat speed still matters, but it should not replace those checks.
  • Treating a deterministic flag as a final verdict. Inspect paraphrases, negations, and missing replies. A word search can find evidence for review, but it can miss a contradiction in a sentence containing the expected amount.
  • Dropping missing replies from the report. Keep attempted cases visible. Mark their content dimensions N/A, and count their operational failures separately.

Beginner Explanation

1. Ground truth starts with the question and the evidence

Suppose the question is about July 15, 2026. The approved policy says the minimum for Standard Savings was ₹5,000 that day. That’s what you can verify before you look at any reply. We call the best-supported fact or expected behavior for a case its ground truth.

Now suppose the customer asks about the ATM limit and the supplied policy says nothing about it. You can still expect the assistant to say it can’t confirm the limit. The missing evidence tells you how to handle the question. It doesn’t establish that the bank has no limit.

Keep three things separate as you work. The fact is the requirement you can verify. For July 15, it’s the ₹5,000 minimum. A reference answer is one acceptable way to say it. Try “The Standard Savings minimum is ₹5,000.”

An evaluation label is your judgment of a reply you actually read. “Keep five thousand rupees in the account” can earn PASS if it’s clear which account you’re discussing. A reply that asserts ₹10,000 earns FAIL. The policy fact stays the same when the label changes.

What if one reviewer likes “maintain” and another likes “keep”? Ask them to point to the same policy line and say what the reply needs to mean. A word preference doesn’t decide a bank requirement.

Teams sometimes call reviewed evidence gold evidence or a reviewed answer a gold reference. This means someone checked it for that case. If you later find an error, you can correct it and record why.

Some questions have an answer you can’t verify yet. A policy can change with time, omit an ATM limit, or disagree with another approved document. If an excerpt simply omits the limit, you can test whether the assistant admits the gap.

If two equally authoritative policies disagree and neither takes priority, you can’t verify either policy claim. Mark the case NEEDS REVIEW and ask the person responsible for the policy to resolve it.

2. Read the Harbor Leaf policy records

Think of the bank publishing a new fee sheet. A draft in someone’s folder might look just as official as the version the Savings Policy team signed off. An approved source is one the bank authorizes for the subject at hand.

Leave a trail another reviewer can follow. Write down the document ID, version, section, approving owner, and dates. This record of where the evidence came from is called provenance. Here the policy register, the bank’s record of approved documents, gives the Savings Policy team authority over Standard Savings balances and fees. It also requires the assistant to keep PINs private. Use the excerpts below as the full evidence for the examples that cite them.

  • SV-1, Savings Policy version 1, §2, approved. Effective January 1 through June 30, 2026, inclusive. Standard Savings requires a minimum of ₹4,000. A ₹80 monthly fee applies when the balance is below ₹4,000.
  • SV-2, Savings Policy version 2, §2, approved. Effective July 1, 2026. Standard Savings requires a minimum of ₹5,000. A ₹100 monthly fee applies when the balance is below ₹5,000. At the minimum, the below-minimum fee does not apply. This excerpt is silent about ATM limits and special student waivers.
  • HELP-DRAFT, help-center draft, unapproved. Edited July 10, 2026. It suggests that Standard Savings requires ₹3,000. Its editing date establishes when someone saved the draft. Approval and effective dates determine which policy governs.
  • FEE-A and FEE-B, fee addenda, both approved. Both list the same Savings Policy owner and become effective August 1, 2026. A says students are eligible for a below-minimum fee waiver. B says students are ineligible. The register gives no precedence or supersession between them. The baseline minimum and fee in SV-2 still apply to questions that do not depend on these addenda.

Which day is the customer asking about? That’s the as-of date. If they ask about “today,” write down the date the case uses.

  1. Check that the policy covers the account and subject.
  2. Check who approved it and whether that owner can set the rule.
  3. Check that the policy was in force on the date asked about.
  4. Look for another document with the same authority that gives a different rule. If the register says which one replaces the other, record that. If it doesn’t settle the disagreement, mark NEEDS REVIEW.

A file’s edit or download date shows when someone worked with it. Use the approval and effective dates to decide which policy applies.

Notice how the two approved savings versions can both be accurate for their dates. A reply about June 15 can correctly say ₹4,000 even if the evaluator opens the July policy today. By contrast, the two August addenda overlap in date, scope, and authority. Escalate that conflict because neither of those filters breaks the tie.

3. Build a reference answer from the evidence

Imagine handing another reviewer a short example of what you’d accept. Write the fact or action the reply needs to convey, then write one way to say it. Attach the source, section, version, and date to that reference answer so the next reviewer can check it.

You may also want the assistant to point the customer to the source. That pointer is a citation. A source number next to a wrong claim doesn’t make the claim right.

For “What is the Standard Savings minimum on July 15, 2026?”, all three replies meet the same fact requirement under SV-2 §2.

  1. “The Standard Savings minimum is ₹5,000.” This names the right account and requirement directly.
  2. “Keep at least ₹5,000 in Standard Savings.” “At least” correctly includes the threshold and amounts above it.
  3. “Maintain a minimum of five thousand rupees in Standard Savings.” This spells out the amount and preserves its meaning and scope.

Keep those three reviewed wordings together and you have a reference answer set. It gives a reviewer examples of the same meaning. If the assistant phrases it a fourth way, read what it says before deciding.

When would you really need an exact match? One case is a software connection that expects a fixed status value. Another is an extractive task, where you ask for text copied from the source. If you ask for the amount exactly as printed in “Standard Savings requires a minimum of ₹5,000,” expect the text “₹5,000.” In a generative task, the assistant writes an answer in its own words. “Five thousand rupees” can be fine for a customer explanation. Pick the rule that fits the job.

Now try writing an acceptable reply for the ATM limit. “I can’t confirm the daily ATM withdrawal limit from the supplied policy” tells the customer where the answer stops. Holding back a claim you can’t support is abstention. If the task allows it, the assistant can suggest checking an approved ATM policy. A guessed number should fail. Save the exact excerpt so another reviewer can check what it leaves out.

The August waiver case is different. The documents give opposite answers. A cautious reply can acknowledge that conflict, but the policy owner still needs to settle it. If you want to score the assistant’s handling of the conflict, write a separate expected behavior for that.

4. Build a benchmark that can teach you something

Suppose you want to repeat the July question tomorrow. Save the question, what the assistant had to go on, and what a good reply should do. That saved scenario is a test case. Put several cases together and you have a dataset.

To compare answers fairly across runs, agree on the questions you cover, rules for scoring, and which version of the dataset to use. Together these form a benchmark. When you apply that benchmark to a set of replies, you’re doing an evaluation run. One case can show how a rule works. A benchmark lets you check how that rule and the assistant behave across different situations.

Begin with two cases. B01 checks a straightforward supported answer. B02 checks a correct paraphrase. They cover one question in two forms, which is enough to show why exact matching can fail. Use this compact benchmark sheet as you expand the set. Each row has a stable case ID, question, as-of date, source, saved reply, expected label, and reason. For every row, SV-1 and SV-2 refer to §2 and the policy register given above.

  • B01, supported. Ask “What is the Standard Savings minimum?” as of July 15, 2026, using SV-2. Reply “The minimum is ₹5,000.” PASS. The minimum matches the current approved policy.
  • B02, accepted paraphrase. Ask the same question using the same date and source. Reply “Keep five thousand rupees in Standard Savings.” PASS. The amount and account are unchanged.
  • B03, incorrect reply. Ask the same question using SV-2 on July 15. Reply “The minimum is ₹10,000.” FAIL. The reply conflicts with the approved amount.
  • B04, historical policy. Ask “What minimum applied on June 15, 2026?” using SV-1. Reply “The minimum was ₹4,000.” PASS. The as-of date is inside version 1’s effective interval.
  • B05, boundary. Ask “Is the below-minimum fee due at exactly ₹5,000?” on July 15 using SV-2. Reply “No below-minimum fee applies.” PASS. The fee applies below the threshold.
  • B06, tempting wrong fee. Ask “What fee applies at a balance of ₹4,999?” on July 15 using SV-2. Reply “A ₹100 fee applies every day.” FAIL. The amount happens to match, but the fee is monthly.
  • B07, unsupported question. Ask “What is the daily ATM withdrawal limit?” on July 15. The evidence packet contains only SV-2. Reply “I can’t confirm that from the supplied policy.” PASS. Abstaining is the approved behavior for this packet.
  • B08, unresolved evidence. Ask “Does the student waiver apply on August 3, 2026?” using both approved addenda, FEE-A and FEE-B. Reply “The student fee waiver applies.” NEEDS REVIEW. The register leaves the conflict unresolved.

B01, B02, and B04 are positive cases for a correct response. B03 and B06 are negative cases for an evaluator that detects known wrong replies. B05 is a boundary case, an input at the edge of a rule where “below” and “at or below” produce different results. B07 checks an unsupported question. B08 checks that you can keep uncertainty visible. Production questions also vary in form, context, topic, and difficulty. This sheet is a teaching set. It contains eight saved cases that test selected distinctions, so it cannot establish production readiness.

Give each real benchmark row a stable ID and include the question, date or account context, source authority and excerpt, expected behavior, acceptable variants, and a short reason reviewers can apply. Keep the saved model reply and your actual run label with the run. A test can have a known expectation before any assistant reply exists. Separate a wrong policy answer from a response that never arrived, as in M02-T01.

5. Check the benchmark itself

Imagine checking whether a new employee can handle the savings help desk by asking only “What is the minimum?” A good answer still leaves you wondering what they’ll do with conflicting documents or an unsupported request. Benchmark validity asks whether your cases and rules measure the behavior you set out to check.

Write a short scoring guide, called a rubric. In B06, tell the reviewer to check both the fee amount and how often it applies. Otherwise one reviewer may accept any answer with ₹100 while another notices that “every day” changes the claim.

Watch for errors in the reference data. If a July row mistakenly cites SV-1, a correct ₹5,000 reply might fail. If a fee reference says “₹100 when low,” reviewers may disagree about what low means and when it is charged. Fix the source or make the cutoff and frequency explicit. If two reviewers disagree, give them the same evidence and ask for their reasons. Use a policy owner for disagreements about authority. Retest with the revised rubric and record who approved the change.

The automated pitfalls from M02-T01 still apply. A strict phrase comparison can produce a false failure on a correct paraphrase. A weak keyword check can produce a false pass on “₹100 every day” because it sees the right amount. Read the entire claim against the evidence. For an unfamiliar reply, route it to review rather than assuming that absence from a list is a failure. Review can mean the source is unresolved or the reply is new to a simple checker. Give the two reasons separate labels when you report them.

Imagine giving a student the answer key to the quiz, then using their score to decide how they’ll do on new questions. If reserved questions, answers, or near-copies reach the assistant or its tuning process and make the test unrealistically easy, that’s data leakage.

Giving the assistant an approved policy is part of its job here. Giving it the reserved cases and their answer key changes the test. Use some cases to improve the assistant and save other realistic questions for the release check. Look for copied and lightly reworded questions across the two groups. Try fresh wording before you claim an improvement.

Version the benchmark, for example HLB-SAV-1, and record the exact policy excerpts and rubric version used. To repair a label, explain the defect, record the old and new labels and reasons, have another reviewer check the change, and publish a new version. Preserve the original results with their benchmark IDs. Comparing a score from eight easy cases with one from a larger, tougher sheet may reflect the change in cases rather than a model change. To compare two assistant versions, rerun both on the same frozen benchmark and report counts, including NEEDS REVIEW. If you publish an aggregate, state which cases are included in its denominator.

Worked Demonstration

Example 1. Accept a paraphrase and repair the check

User question. “What minimum balance do I need for Standard Savings on July 15, 2026?”

Approved reference. SV-2 §2 requires ₹5,000 from July 1, 2026.

Actual LLM response. “Keep five thousand rupees in Standard Savings.”

Assessment. Ask three small questions. Does the reply name the right account? Yes. Is “five thousand rupees” ₹5,000? Yes. Does “keep” convey the requirement? Here it does. Mark PASS. A literal comparison with “The minimum is ₹5,000” would wrongly reject the reply. Keep the paraphrase as a reviewed example and leave room in the scoring guide for other wording with the same meaning.

Example 2. Resolve two conflicting amounts by date and authority

User question. “What minimum balance applied on June 15, 2026?”

Approved reference. SV-1 §2 says ₹4,000 through June 30. SV-2 §2 says ₹5,000 starting July 1. HELP-DRAFT is unapproved.

Actual LLM response. “The Standard Savings minimum was ₹4,000.”

Assessment. Put your finger on June 15 in the calendar. SV-1 covers that date and gives ₹4,000. SV-2 starts after it, and the draft was never approved. Mark PASS. Move the question to July 15 and try the same ₹4,000 reply again. It now fails. Save the question date and policy version so another reviewer knows why.

Example 3. Separate a missing answer from a policy conflict

User question. “What is the ATM limit?” The second customer asks, “Did the student waiver apply on August 3?”

Approved reference. The ATM case supplies only SV-2 §2, which does not cover withdrawals. The waiver case supplies FEE-A and FEE-B, with equally authoritative conflicting claims.

Actual LLM response. For the ATM question, “I can’t confirm the limit from the supplied policy.” For the waiver question, “The student fee waiver applies.”

Assessment. Ask what you can check in each case. For the ATM question, you can verify that the excerpt omits the limit and the assistant says so. Mark PASS for that behavior. A guessed amount would fail. For the waiver question, you can verify that the documents disagree, but you can’t verify the claim that the waiver applies. Mark NEEDS REVIEW, keep both addenda, and ask the policy owner to settle the conflict. To check whether the assistant explains the disagreement to the customer, write that expectation as a separate test.

Step 7 — Produce a readable evaluation report

Use the eight reviewed cases above. This miniature checker looks up known good and known bad saved replies. It does not judge an unfamiliar reply for factual accuracy. The cases show the expected behavior within the supplied evidence packets, including a reviewed abstention for B07.

You need the same order of checks for all eight cases. Put the checks in a function, a reusable block of instructions. def assess(case): names the block and says it works with one case at a time. The indented instructions run whenever you call it.

Read the checks from top to bottom. If the source is unresolved, end the check there. Otherwise test the list of accepted replies, then the list of rejected replies. If you can’t find the wording in either list, ask for review. Each return stops that call and hands back a label and a reason, an ordered pair called a tuple. The line outcome, reason = assess(case) puts those two results into two names in that order.

The cards keep the dates, sources, and reviewed replies. Empty brackets [] mean there are no items in that list yet. The report loop calls assess for each card. After the dot in outcomes.append(outcome), append means “add this label to the end of the list.” Once the loop finishes, outcomes.count("PASS") counts the entries equal to PASS. The last two lines do the same for FAIL and NEEDS REVIEW, so you can see every kind of outcome.

def assess(case):
    if case["evidence"] != "resolved":
        return "NEEDS REVIEW", "evidence is unresolved"
    if case["reply"] in case["accepted"]:
        return "PASS", "reviewed acceptable reply"
    if case["reply"] in case["rejected"]:
        return "FAIL", "reviewed incorrect reply"
    return "NEEDS REVIEW", "reply has no reviewed label"

Knowledge Check Answers

  1. Fact. The Standard Savings minimum was ₹5,000 on July 15 under SV-2. “The minimum is ₹5,000” is a reference answer. A ₹10,000 claim receives FAIL.
  2. Equivalent meaning. Both require at least ₹5,000 for the same account. The reference is a reviewed way to say it. An exact match can miss equally valid wording.
  3. SV-2. It is approved and effective for that date. The draft's later edit time carries no policy authority.
  4. It separates below from at or below. A program that accidentally includes equality can pass easier cases above and below the threshold and still fail this boundary.
  5. PASS for the reviewed abstention, NEEDS REVIEW for the conflict. The bounded ATM case has known expected behavior. The waiver claim lacks a resolved source of truth.
  6. A keyword test can find the amount without checking its frequency. The reply’s policy claim converts a monthly charge to a daily charge. Review the relationship between the amount and the frequency.
  7. The score could exaggerate performance on fresh questions. The assistant may have seen the evaluation answers during tuning. Use held-out, independently reviewed cases and check for near-duplicates.
  8. Rerun both assistant versions on the same corrected benchmark. Preserve the older reports with their version IDs. A change in labels and case coverage can change a score even when the assistant's behavior stays the same.

Common Mistakes

  • Selecting the newest file automatically. Select by approval, scope, and the case's as-of date. Use the register to check supersession.
  • Treating every unfamiliar reply as a failure. Separate reviewed errors from replies you have yet to judge. A paraphrase can be correct.
  • Guessing at a policy conflict. Keep the source IDs and ask the policy owner for a documented decision.
  • Using a keyword as the entire rubric. Check what the reply claims, especially thresholds, units, frequency, and negation.
  • Editing a previous result in place. Keep the original report, issue a documented benchmark revision, and run comparisons on aligned versions.

Beginner Explanation

1. Offline evaluation uses a saved set of cases

Before giving customers a new version, try it on questions you can save and repeat. You can stop after each one, compare the reply with the policy, and try again. That’s offline evaluation. It happens outside live customer requests.

Save the question, the date or account, the approved evidence, and what the reply should do. A reference answer shows one reply you’d accept. A rubric tells the reviewer what to look for. In a fee case, “A monthly fee of ₹100 applies” and “The charge is ₹100 per month” express the same amount and timing. Your rubric can accept both.

Harbor Leaf's examples reuse these approved policy excerpts.

  • SV-1 §2. From January 1 through June 30, 2026, inclusive, the Standard Savings minimum was ₹4,000. A ₹80 monthly fee applied below ₹4,000.
  • SV-2 §2. From July 1, 2026, the minimum is ₹5,000. A ₹100 monthly fee applies below ₹5,000. The below-minimum fee does not apply at exactly ₹5,000. The excerpt gives no ATM limit.

Ask what applies on June 15. Open SV-1 even if the customer happens to ask in July. Now ask the bank for an ATM limit using only SV-2. Can you find a number in that excerpt? No. An acceptable reply says it can’t confirm the limit. Holding back a claim you can’t support is called abstention.

Suppose you want to check the same wrong fee reply again. You can score the saved text or send the same question to a new version in a test environment. Reusing saved inputs or outputs this way is replay. In the lab, you’ll score saved text and make no model calls.

The same saved text and fixed rule let you reproduce a result. If you ask a model to generate the reply again, the words or answer may change. Save the version, settings, and replies so you know what was actually checked. Run comparable trials more than once if that variation could affect your decision.

Offline evaluation can catch mistakes before customers see them and help you reproduce a failure while you change one component. It works without customer traffic and lets you include rare but severe failures deliberately. Its coverage ends where its cases end. Passing six saved examples says what happened on those six examples. It gives little evidence about the frequency of errors across live traffic.

2. Online evaluation observes a deployed assistant

Imagine the new help desk is open. Customers arrive at different times with questions you didn’t plan, and some wait longer than others. Now you can watch how the service actually runs. The live setting is called production, and checking activity from a deployed service is online evaluation.

Monitoring means keeping track of what happens over time. Are replies arriving? How much does a request cost? Do reviewers find wrong claims about fees? You can also measure latency, the time a request takes. Decide when to start and stop the clock, such as from the request to the complete reply, and use the same measure when comparing versions.

If there are too many replies to read, choose some to review. That smaller group is a sample. You might select replies at random throughout the day and separately pull extra historical-policy questions because they’re rare and important.

Keep those groups separate in your report or account for how you chose them when estimating a rate. Reading a pile of complaints can help you find a problem. Those complaints alone tell you little about how often the whole customer base sees it.

A customer taps thumbs-up. Did they check the fee against the policy, or were they pleased to get a quick response? That rating is user feedback. Someone can like a wrong answer or dislike an honest “I can’t confirm that.”

When you report a fraction, say what you divided by. That’s the denominator. For example, “4 of 12 submitted ratings were negative” and “2 of 30 reviewed replies failed the policy check” answer different questions. People who didn’t rate their reply may have had a different experience.

Suppose you’re checking slow replies. Do you need the customer’s message? Time taken, the assistant version, the question category, and the source version may already help you check slow responses and old evidence. For a policy error, use a narrowly chosen example with identifiers removed, or build a fictional example that produces the same error. Follow the bank’s rules for approval, who can see the records, and how long to keep them. Keep real messages, PINs, and account numbers out of the lab.

If unsupported advice reaches a customer and could cause harm, the team can treat it as a safety incident. Follow the bank’s incident process and keep only what’s needed to investigate.

3. Match the evidence to the decision
  • Inputs. Offline evaluation uses saved cases, expectations, and approved evidence. Online evaluation uses deployed behavior such as sampled replies, timing, spend, and feedback.
  • Strengths. Offline evaluation checks the same known cases before release and helps isolate changes. Online evaluation reveals unexpected questions and live traffic or system conditions.
  • Limits. Offline results can be misleading when coverage is narrow or the team has tuned on the test cases. Online results can be misleading when samples are unrepresentative, labels are missing, or traffic differs between versions.
  • Decisions. An offline gate can stop a candidate that guesses an ATM limit on a known case. Online evidence about a new policy error can justify pausing a rollout already in progress.

The new version you’re deciding whether to release is the candidate. You can try it behind the scenes first. With shadow evaluation, it gets an approved copy of a live request, while the customer still sees the regular reply. The team can read the candidate’s answer separately. It can still cost money and process sensitive information, so approve and isolate it first.

When you want to see how customers fare with the new version, serve it to a small, controlled share of eligible requests. That’s a canary. You can stop early if you see harm. A higher canary error rate than last week’s rate could come from the new version or from a different mix of questions.

Say you want to know whether the new version actually changes how many customers get correct answers. Set up a comparison before looking at the results. In an online experiment, you decide what to change and compare groups that experience different versions.

An A/B test uses a planned rule, usually random assignment, to put eligible users in version A or B. When the groups and measurements are comparable, this can help you estimate what the version changed. Decide who can take part, how long to measure, and when to stop if you see harm.

Replaying saved live requests offline can reproduce a problem. To estimate what caused a change in live user behavior, you need evidence suited to that question.

4. Follow the evaluation lifecycle

How does one wrong fee answer change what you do next week? Start with the reason you’re checking it. Then use the results of the test and the rollout to improve the next round. Those connected steps are the evaluation lifecycle. Follow the fee question through them.

  1. Define objectives and success criteria. Ask what decision the evaluation supports. The bank wants July fee answers to give the correct amount and frequency and unsupported financial questions to receive a safe abstention. Decide in advance what evidence would be enough for the release decision.
  2. Prepare representative cases. Include common questions, wording variants, boundaries, older policy dates, and unsupported questions. Give each case an ID, evidence, and expected behavior. Separate a development set from cases reserved to assess the release so that tuning on known answers does not inflate confidence.
  3. Establish a baseline. Record the starting version and its results. For Harbor Leaf, use the currently deployed prompt with its model and approved sources. A prompt is the instructions and other input supplied to the model. The version being considered is the candidate.
  4. Run offline evaluations. Score each version on the same saved cases with the same evidence and rubric. Record the replies and judgments beside their case IDs. Keep a separate outcome for unresolved evidence or an execution error. A request that never produced a reply supplies no answer to score.
  5. Analyze failures. Group results by what went wrong, such as “wrong fee frequency” or “unsupported limit.” Then investigate why. Read the question, source excerpts, instructions, and reply. The same wrong charge can come from the wrong policy being supplied or from the assistant misreading a correct one.
  6. Improve one part of the system deliberately. You might clarify the prompt, fix retrieval (the step that finds and supplies documents), or change the model's configuration. Log the change and the reason for it. A better retrieval result will not help if the assistant ignores the effective date in that result.
  7. Re-evaluate for regressions. A regression is behavior that gets worse after a change. Pair baseline and candidate results for each case, including ones the baseline already passed. Keep known failure cases in a regression suite, a reusable set of tests that guards against mistakes returning.
  8. Make a release decision. Check the release criteria, list remaining risks, and record whether you would approve a monitored release, block it, or gather more evidence. Name the owner and the condition that would pause or reverse the rollout.
  9. Monitor online behavior. Review results from the approved rollout. Track correctness where you have evidence, response latency and cost, safety events, and feedback. Define when a team member should look more closely and when the rollout must pause.
  10. Investigate incidents and update the dataset. Contain any harmful behavior, then reproduce it safely. Add an evidence-backed case that would have caught it. Save the old benchmark and run. Start a new benchmark version and score both versions on it before claiming a comparative improvement.

A useful decision worksheet records the question being decided, version IDs, benchmark version, reviewed and unresolved counts, paired changes, safety findings, recommendation, and next owner action. For a live signal, add the measurement window, population, selection method, denominator, and any limits on collection. You will fill parts of this worksheet in the lab and assignment.

5. Apply release gates without losing individual failures

Suppose you checked seven replies. Five pass, one fails, and one still needs a decision. If you report “five out of six,” say that you counted only the replies you could decide. That fraction is the pass rate among decided cases. Also report that you reached a decision on six out of seven. Otherwise the missing judgment disappears from the report.

Next ask what went wrong. “Wrong fee frequency” is a failure category, a name for the kind of mistake you saw. Some mistakes have consequences the team regards as unacceptable. We call those failures safety-critical. In this lesson that includes making up an ATM limit when the approved evidence doesn’t give one.

Before looking at a new score, agree on what would be enough to proceed. The rules you agree to use are your release gate. Here are the invented rules for the lab.

  1. BLOCK if any confirmed candidate safety failure exists.
  2. INVESTIGATE if a required candidate case remains under review after checking for confirmed safety failures.
  3. BLOCK if less than 80% of all required candidate cases pass.
  4. Otherwise, APPROVE LIMITED ROLLOUT with monitoring. The examples assume a required, nonempty suite.

The order matters. An unresolved row cannot hide a confirmed safety failure. Approval here means the team can proceed to a limited rollout under the exercise's assumptions. Real teams choose gates based on harm, coverage, evidence quality, and who owns the decision. Zero observed safety failures in six cases is a starting condition for this exercise, not a guarantee. If an assistant moves from four passes to five by fixing two ordinary cases and breaking one safety case, the overall pass rate rises while the release becomes unacceptable.

Fix the decision rules before you see the score. Python first counts passing cases, cases awaiting review, and confirmed safety failures. A flag is a yes-or-no value. Knowledge Check Answers

  1. Offline scoring of live observations. The replies came from production. The team is applying rules to a saved batch separately from live serving.
  2. Source selection. A July answer about June 15 may require SV-1. A date and policy version let another reviewer find the same evidence and reproduce the judgment.
  3. Paired changes and harm. Name both improvements and the regression by case. A single total hides the loss, and the broken behavior may be more serious than both improvements.
  4. Block. The 5 of 6 score clears 80%, but the confirmed unsupported limit is safety-critical in this exercise and takes priority.
  5. Who sees the answer. Shadow traffic exercises the candidate without showing its reply to the customer. A canary serves the candidate's reply to a limited share of traffic and monitors what happens.
  6. Different measures. The rating may reflect convenience, politeness, or whether the response sounds plausible. Check the fee claim against the applicable evidence.
  7. A comparable comparison. Check case categories and relevant conditions, and compare like with like. A well-designed randomized online comparison with agreed measurement can help attribute effects to the version. Offline replay can show whether both versions handle the same historical cases differently.
  8. Versioned evidence. Save a minimized reproduction, the date and approved source, expected behavior, and the reason for the change. Keep the original run. Score baseline and candidate under the same new suite and rubric, then record the results as a new comparison.

Common Mistakes

  • Relying on a single average. The overall pass rate rose in Example 2 while an important safety behavior got worse. Report the paired outcomes. In Example 3's sample, mean latency was 600 ms and one reply took 900 ms. If slow replies matter, inspect the distribution and report counts beyond a defined latency limit.
  • Putting too much weight on small samples. Six known cases can catch specific mistakes. To estimate broader performance, you need coverage of representative traffic and enough evidence in important categories.
  • Changing test conditions mid-comparison. A July policy and a June policy can both be valid in different cases. Freeze the applicable evidence version, prompts, model settings, and scoring guide for a comparison. Record deliberate changes and rerun both versions when those changes affect comparability.
  • Assuming a live issue must be in the saved suite. Example 3 exposed a combination the suite did not test. Reproduce it with a minimal record and add a versioned regression case.
  • Using ratings as fact checks. Investigate feedback for user experience and sample replies with approved evidence for factual review. Keep their denominators separate.
  • Trusting every automated result. A literal match rejected a valid paraphrase in Step 2. Inspect a disagreement directly. If evidence is incomplete, report a pending judgment while a reviewer resolves it.

Lesson Summary and Next Step

Use offline evaluation to check and reproduce known cases. Use online evaluation to learn what happens on deployed traffic. Compare versions on the same saved cases, review serious failures individually, and make the release decision explicit. When production exposes a new failure, investigate the cause, preserve the original evidence, and extend the suite so you can test the fix before the next release.

    About the Course

    Vision and audience

    A long-term reference for learners entering LLM evaluation, engineers owning evaluation decisions, and instructors teaching or adapting practical labs. By the end of the core path, a learner should be able to design a versioned evaluation, build and calibrate scorers, quantify uncertainty, diagnose RAG and agent failures, and defend a production release decision. Expertise includes knowing when the evidence warrants another experiment or human review.

    Start with concepts and explicit decision criteria, then build a small Python scorer. Use frameworks once learners can explain the metric and verify a result by hand. Study RAG and agents through observable inputs, outputs and states. Finish by connecting offline evaluations to release decisions, traces and monitored outcomes. The plan describes target competencies and future labs. The coverage statuses describe the current repository.

    Sequence and time estimates

    Core progression spans Beginner, Intermediate, Advanced and Production. Specialized / Expert modules are electives that can be studied independently after their listed prerequisites. Topic records give the minimum preparation for focused study. The recommended module order provides a complete beginner route. Required study for an individual module is computed from the prerequisites of its topics. Each stage ends with a reviewable artifact, and the capstone brings those artifacts together.

    Times are planning estimates in hours. Each topic lists theory, guided hands-on implementation, independent experiments and interpretation, exercises and assessment, total learner time, and instructor-led classroom time. Instructor-led hours are a separate delivery estimate for explanation, demonstration and supervised practice. Preparation, breaks, and optional provider work are outside that estimate. Plan extra preparation for a first teaching run.

    Estimates assume a learner who can use a terminal and read simple Python, coaching available for the first lab, and prepared fixtures with expected outputs. Guided times include routine setup and troubleshooting for the activity. Learners new to Python should practice reading a JSON file, looping over records, and running a test before starting guided implementation. Large downloads, hardware delays, provider wait times, deep remediation and elective live extensions vary by environment. Pilot time estimates with both a beginner and an experienced engineer.

    One evolving application

    • Beginner — Evaluate a fictional bank support chatbot from six saved responses. Build exact/semantic boundary examples, a deterministic scorer and a blind human review sheet. Explain failure, uncertainty and execution error.
    • Intermediate — Publish a versioned gold dataset, calibrate a judge on frozen examples and compare prompt versions with paired Python analysis. Verify labels, denominators and uncertainty before drawing a conclusion.
    • Advanced RAG — Give the chatbot a fictional policy corpus. Evaluate ranked passages, context sufficiency, claims and citations, then compare retrieval changes against an oracle reference.
    • Advanced agents and safety — Add a mock account lookup and a simulated workflow. Verify actions, arguments, state, recovery and safe refusals. Assess defensive controls from fixed fictional traces and inert records.
    • Production — Add fixture-driven gates, trace metrics and a simulated incident. Convert a reviewed failure into a regression fixture and defend a release, hold or rollback decision.
    • Electives — Change the task when the method needs different evidence. Use synthetic fee charts for multimodal evaluation, public-style and private fictional benchmarks for contamination lessons, and benign generated functions for test-driven code evaluation. Use the healthcare examples for transfer lessons on score validity and source grounding.

    Execution modes and tool choices

    Every essential lesson starts with a fixture or simulated run that needs no model, network or credentials. Live Ollama inference and locally cached embeddings are optional hands-on extensions. The existing Test 5 configuration points to OpenAI and the existing Test 10 RAGAS integration requires OpenAI calls. These examples are references until local or fixture alternatives and effective settings are verified. Hosted graders and paid comparisons are optional, explicitly budgeted extensions.

    Choose DeepEval for Python-oriented assertions and thresholds when its chosen metric fits the construct. Choose RAGAS for a RAG metric suite when the record carries its required references or evidence. Both may call judges or embeddings and need versioned adapters, explicit failure states and checked denominator behavior. Choose promptfoo for a declarative prompt and provider matrix, and OpenAI Evals for an OpenAI-centered managed grading workflow when supported graders, data handling and cost fit. Compare both on saved cases before adding a managed run.

    Choose Langfuse for linked LLM traces, observations and scores. It depends on the quality of instrumented events and attached scores. OpenTelemetry is useful when correlation across services is the objective, with separate application quality measures. In defensive evaluation, Garak illustrates scanner-style coverage and PyRIT illustrates organized assessment records. Use prepared offline reports to compare their evidence formats and coverage. Tool output depends on scope, fixtures and labels, and requires review before it informs a decision.

    Teaching Plan

    Mandatory lesson standard

    1. State observable learning objectives.
    2. Give prerequisites, setup, input artifacts and an entry checkpoint.
    3. Explain the concept in plain language.
    4. Explain why it exists.
    5. State the problem it solves and constraints on use.
    6. Give realistic engineering use cases.
    7. Work a small example by hand with a known answer.
    8. Increase complexity gradually, including a conflicting or ambiguous case.
    9. Give a step-by-step Python implementation or reproducible Python replay when the topic concerns a managed workflow.
    10. Explain code sections that change behavior, scores or denominators.
    11. Show expected artifacts and key execution results.
    12. Interpret results and what decisions they can support.
    13. Demonstrate common mistakes.
    14. Explain limitations and failure cases, including evaluator failure where relevant.
    15. Include a guided experiment with one controlled variable.
    16. Assign independent exercises with measurable outputs.
    17. Provide solutions or verification criteria, including accepted alternative solutions.
    18. Include instructor notes with timing, prediction prompts, common learner errors and offline fallback.
    19. Document troubleshooting and how to identify failure stage.
    20. Include knowledge checks and observable completion criteria.
    21. Connect the current topic to earlier and later evaluation decisions.

    Classroom preparation and assessment

    Each session should use the topic's prerequisite check and demonstrations, then ask learners to predict a result before running it. Prepare a small known-answer fixture, one common misconception and a harder case. Grade claims against evidence and review inclusion, decision policy and exceptions. Where output is stochastic, grade expected invariants and justified decisions. For the capstone, require an annotated dataset, manifest, replayable report, failure diagnosis and release recommendation. Ask a peer to reproduce the result.

    At least one teaching variant for core labs should use standard-library Python and prepared data. Where a framework is the objective, provide a fixture containing its inputs and results and prepare a pinned optional environment. Instructors should try the first run on target classroom hardware and define bounds for compute, data handling and spend before optional live sessions.

    Implementation sequence

    1. First milestone — Deliver the M01–M03 fixture-first slice, the starter M04-T01 schema and the first M06-T01 judge replay. Use exactly shared response IDs across the human, rule and judge evidence. Supply a handout, annotated answer key, instructor demonstration and local fixture verification before updating requirements for optional runs.
    2. Build the dataset and measurement spine in M04–M07. Establish reliable denominators, anchors, held-out cases, paired comparisons and uncertainty exercises before publishing example baselines.
    3. Add M08–M12 around the same contract. Reuse the banking corpus and traces. Verify gold passage and final-state controls before framework demos. Prepare safety and defensive-review fixtures for bounded, fictional labs.
    4. Add M13–M15 after the offline gates are stable. Introduce sampled synthetic traffic, redacted tracing and incident-to-regression review.
    5. Build electives once the relevant core artifacts are stable. Add tracks based on learner need and verify each against a separate domain-specific rubric.
