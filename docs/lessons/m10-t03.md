## Beginner Explanation

### Decide what succeeded before counting a recovery

A reliable agent repeatedly completes the intended task safely under stated conditions. A fluent refund answer may match a reference while its ticket is missing or duplicated. Check the tool’s availability, the correctness of the agent’s decision, the actual state, the goal and authorization separately.

Read the first observable failure. A model may choose ticket creation for a status question or send an invalid order argument. A service may return a timeout, an execution error, or a malformed reply despite receiving a valid call. A missing result leaves the outcome unknown. A successful eligibility decision with no required ticket is partial completion. A success receipt without a matching independent state record fails verification. Each finding points to different engineering work.

### Decide whether another attempt is justified

A transient failure may clear, such as a read timeout, temporary unavailability or rate limiting. A persistent permission denial, invalid input or unsupported operation needs a change in authority, arguments or plan before another attempt. When a provider returns a documented retry delay, consider it within the same remaining deadline. A retry repeats work and can add cost even when the original request already ran.

A maximum of three **attempts** includes the original call and allows two **retries**. The retry budget limits attempts, time or spend. **Backoff** is a wait before retrying. For a base of 20 ms, waits might be 20 ms, 40 ms and 80 ms before the first, second and third retries. They add 140 ms before counting the calls. **Jitter** varies the waits slightly across clients so they are less likely to retry at the same time. For a replay, freeze the realized delays, such as 22, 37 and 84 ms.

Suppose Northstar stops waiting for the order service at 80 ms. That is the per-call timeout. If the customer-facing journey must finish within 320 ms, the agent also has to budget for earlier model work, the policy lookup, any retry waits and the final answer. That larger limit is the end-to-end deadline. If 60 ms remains and the next retry needs 20 ms waiting, up to 50 ms tool time and 15 ms to finalize, its 85 ms reservation does not fit. Stop or use a permitted alternative. Cancellation requests that work stop, but a service may have committed work before it receives the request. Reconcile state when that matters.

### Handle a missing write acknowledgment

Say the ticket service stores T-1042 at 35 ms and the acknowledgment never arrives. Draw two timelines that look identical from the caller’s screen. In the first, the write never committed. In the second, T-1042 is already in the ledger and only the reply was lost. An immediate retry is harmless only if the service can ensure the same operation has one effect. Inspect the authoritative ledger to distinguish the timelines. Use a separate authorized ledger read or a service that durably enforces an **idempotency key**, a stable identifier for the same logical operation.

The server needs to bind the key to the caller, operation and arguments, enforce uniqueness across concurrent requests, and preserve or recover the original result with the side effect. Reusing a client-generated string without server enforcement still permits duplicates. If verification is unavailable and enforcement is unproven, stop and report the ambiguity. Avoid claiming a ticket number until it is verified.

### Replan using evidence

After a failed read you may retry within budget, use an approved versioned source, request human review, or stop safely. A random note claiming a 90-day window is an unapproved fallback. Treat it as untrusted data. The approved 30-day limit still governs. A successful fallback can complete the goal. A safe handoff can preserve safety without completing it. If a write might exist and its ID is still unknown, report an unresolved outcome. If eligibility was established but the required ticket failed, record partial recovery. A guessed answer or blind write is unsafe continuation.

### Count runs and timing with explicit denominators

Imagine five planned runs. Four encounter a fault. Two of those four recover, one safely stops and one is unresolved. Failure exposure is 4/5, recovery is 2/4, safe termination is 1/4 and unresolved is 1/4. If three fault-exposed runs retried the same operation and two then verified success, retry success is 2/3. If one of two write-attempted runs created duplicates, duplicate-action rate is 1/2. Record critical findings separately. A failure can remain in other categories, such as unsafe continuation. Keep missing traces visible in coverage. Use N/A for a zero denominator.

Run both agent versions on the same cases, tools, fault schedules, and starting states. For an evaluation with nondeterminism, repeat trials under disclosed settings and keep each run. One success after several trials can conceal variability. See [Confidence intervals, significance and sample size](#m07-t02) for uncertainty. A small fictional replay demonstrates evaluator behavior and arithmetic. It provides no estimate of production reliability.

Measure local tool time, retry waiting, other work, and end-to-end response time in the same units. In a sequential fixture, 80 ms timeout plus 20 ms wait plus 40 ms read is 140 ms of retry flow. Add steps before and after it for total latency. For parallel work use the elapsed wall-clock span. Summing overlapping calls overstates elapsed time. One second is 1,000 ms.

Sort elapsed times to find the median, the middle value or average of the middle pair. For nearest-rank percentiles, multiply the sample size by the fraction, round up, then count from one. For five times `100, 120, 130, 160, 370` ms, the median is 130 ms. The p90, p95 and p99 ranks are all 5, so all equal 370 ms. The 370 ms journey can miss a 340 ms latency target even while the 130 ms median looks comfortable. In this tiny batch p90, p95 and p99 all name the same observation. Report the sample size so readers can interpret that tail result.

Add model, tool and retry costs across all evaluated runs, including failures. If the batch costs 60 illustrative cents and verifies five successes, cost per verified success is 12 cents. Track unnecessary tool calls and repeated model work. A cheap fast agent that leaves goals incomplete may be worse than a slower recovered one. An expensive agent that repeats already successful reads buys no new evidence. An agent with a critical unauthorized effect cannot qualify for release even if success or latency improves.

### Keep enough evidence to reconstruct the recovery

Save run and step IDs, tool name, attempt index, start and end time, error class, retry decision, key reference, durable-state check and final outcome. Separate measured latency from an estimate or an unavailable value. Use model-request IDs and tool-call IDs for correlation. Keep provider or transport failures separate from model-choice and argument failures. Compare versions against predeclared coverage, recovery, deadline and cost thresholds. HOLD for critical safety findings. REVIEW for missing evidence or a missed operational target. RELEASE only when the entire gate is satisfied.

## Worked Demonstration

### Example 1. Recover a read-only timeout

**User question.** Check ORD-1042 and escalate only if it is ineligible.

**Approved reference.** The authorized read can retry once after a temporary timeout. The entire scripted run must finish in 320 ms. The actual purchase is 25 days old.

**Actual LLM response.** Attempt 1 records an 80 ms timeout. The application waits 20 ms and attempt 2 succeeds in 40 ms. The scoped policy then takes 40 ms. The opening and closing model steps take 30 ms each. The reply says the purchase is eligible and no ticket is created.

**Assessment.** The read recovery takes `80 + 20 + 40 = 140` ms. The whole run takes `30 + 140 + 40 + 30 = 240` ms. Check that the verified ledger stayed unchanged and the answer cites the 30-day rule.

**Failure classification.** Transient read failure followed by a successful bounded retry. Permission denial would stop the same read immediately.

### Example 2. Reconcile a lost ticket acknowledgment

**User question.** The same request is replayed with a verified purchase age of 45 days.

**Approved reference.** The conditional authorization permits one review ticket after the 30-day policy establishes ineligibility. The starting ledger has only the unrelated T-1000.

**Actual LLM response.** The first write commits T-1042 and loses its acknowledgment. An unsafe second write creates another ticket despite sending the same operation key. The final reply names T-1042, which is real.

**Assessment.** Compare the final ledger with the starting ledger. Two new tickets violate the one-ticket goal. In a safe replay, a successful independent state check recovers T-1042 directly. If the check is inconclusive, only a verified, server-enforced same-key retry is permitted within budget, followed by reconciliation.

**Failure classification.** Ambiguous first response, then confirmed duplicate effect. HOLD. A successful-looking answer cannot clear the ledger finding.

### Example 3. Trade latency for recovery within the gate

**User question.** Evaluate both agent versions on the same eight fault fixtures.

**Approved reference.** Compare verified goals, recovery over exposed runs, duplicate effects, p95 and cost. Count all attempts. A confirmed duplicate blocks release.

**Actual LLM response.** Agent-V1 verifies 2/8 goals. Agent-V2 initially verifies 4/8 but duplicates a ticket. The repaired V2 verifies 5/8, removes duplicates, and leaves a 370 ms tail run.

**Assessment.** In the lab, the repaired candidate recovers 4/7 exposed cases and costs 61 illustrative cents, or 12.20 cents per verified goal. Its p95 is 370 ms. The threshold is 340 ms and no deadline miss is allowed. Predict what happens if a known-futile last attempt is skipped.

**Failure classification.** Baseline HOLD for a duplicate, then REVIEW for excessive latency and a deadline miss. A tighter simulated admission threshold removes that last attempt and improves operational metrics without increasing verified goals.

### Step 2 — Evaluate a bounded retry

Replay two transient errors followed by success. Decide what the attempt limit permits.

A slice `outcomes[:limit]` keeps only the allowed prefix. `enumerate` labels each attempt, and `break` ends the loop after success.

[Open Python Editor](https://www.online-python.com/)


```text
Attempt 2 unavailable

```

**Predict and modify.** Reduce `limit` to 2, which includes the first attempt.

```text

Recovered: False
```

### Step 3 — Compare backoff with a deadline

Reserve the known attempt duration and future delay before starting another read.

`zip` pairs the waits and durations. The loop adds them to elapsed time only if the attempt fits. The first delay is zero because it precedes the first attempt.

[Open Python Editor](https://www.online-python.com/)

```python
deadline = 280
elapsed = 0
for attempt, (wait, duration) in enumerate(zip([0, 20, 40], [80, 60, 50]), 1):
    finish = elapsed + wait + duration
    if finish > deadline:
        print("Attempt", attempt, "blocked; would finish at", finish, "ms")
        break
    elapsed = finish
    print("Attempt", attempt, "finished at", elapsed, "ms")
```


**Predict and modify.** Tighten the deadline to 220 ms.

```text

Attempt 2 finished at 160 ms
Attempt 3 blocked; would finish at 250 ms
```

The third attempt would end at 250 ms. The evaluator can verify that the scheduler stopped before spending the extra wait.

## Optional Real Reliability Instrumentation Walkthrough

### Instrument a bounded read with OpenAI Responses REST v1

**Verification status.** API-checked, live execution unverified. The application and reporting logic ran with a deterministic fixture. This example uses Python’s standard library and `POST /v1/responses` directly, so there is no SDK dependency. Its local tool reads an invented order. [Function-calling guide](https://developers.openai.com/api/docs/guides/function-calling) · [Responses REST reference](https://developers.openai.com/api/reference/resources/responses/methods/create)

The official references are available at `developers.openai.com/api/docs/guides/function-calling` and `developers.openai.com/api/reference/resources/responses/methods/create`.

Record an application run ID and a unique request ID for each provider attempt. The example sends `X-Client-Request-Id` and logs the returned `x-request-id` when available. Keep the provider’s response `id` separate from both. The provider proposes a `function_call`. The application validates the JSON arguments and session scope, then owns execution, retries and timing. An HTTP or transport failure can leave a provider event without a usable proposal. Report that as infrastructure evidence. Do not silently assign a model-choice error to the case. [Official request-ID documentation](https://developers.openai.com/api/reference/overview) · [Function-call output contract](https://developers.openai.com/api/reference/resources/responses/methods/create)

The app records each tool attempt against the same `call_id`. It reserves the backoff and per-attempt wait before retrying. The application refuses to use a result after its deadline. Its socket timeout limits waiting but cannot promise remote cancellation or prevent a late commit. After the successful read, it returns a `function_call_output` with the matching `call_id` and chains to the prior response through `previous_response_id`. It resends instructions and uses stored responses. Record provider and tool timing with a monotonic clock, which advances independently of wall-clock corrections. [Responses request and result schema](https://developers.openai.com/api/reference/resources/responses/methods/create)

The walkthrough verifies that an independent demo ledger stays unchanged because only a read is authorized. In a write-capable flow, the application would record a redacted operation-key reference, the server’s reconciliation result, and a separate ledger snapshot before reporting the ticket. Every retry may repeat work. A model-request correlation ID cannot deduplicate a side effect. The ticket boundary must enforce idempotency, as in the offline lab.

```bash
import sys

        "strict": True, "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}},
                                     "required": ["order_id"], "additionalProperties": False}}
ARGS = {"order_id": "ORD-1042"}
INSTRUCTIONS = "Read order ORD-1042 using the available tool, then answer exactly 'Delivered.' when confirmed."
QUESTION = "Was ORD-1042 delivered?"

def instrument(send, read, clock, pause, model, run_id, events, deadline_ms=3000, rates=None, tool_cents=None):
    start = clock()
    def elapsed():
        return round((clock() - start) * 1000)

    def remaining():
        seconds = deadline_ms / 1000 - (clock() - start)
        if seconds <= 0:
            raise TimeoutError("application deadline")
        return seconds

    def record(kind, **fields):
        events.append({"run_id": run_id, "step": len(events) + 1, "kind": kind, **fields})

    def request(payload):
        client_id = f"{run_id}-{len(events) + 1}"
        began = elapsed()
        try:
            response, request_id = send(payload, min(remaining(), 2), client_id)
        except (TimeoutError, URLError) as error:
            record("provider error", client_id=client_id, start_ms=began, end_ms=elapsed(),
                   request_id=error.headers.get("x-request-id") if isinstance(error, HTTPError) else None,
                   error=type(error).__name__)
            raise
        usage = response.get("usage")
        priced = (usage["input_tokens"] * rates[0] + usage["output_tokens"] * rates[1]
                  if usage and rates is not None else None)
        record("provider response", client_id=client_id, request_id=request_id,
               response_id=response["id"], start_ms=began, end_ms=elapsed(),
               status=response["status"], usage=usage, estimated_cents=priced)
        remaining()
        if response["status"] != "completed":
            raise ValueError("incomplete provider response")
        return response

    common = {"model": model, "instructions": INSTRUCTIONS, "tools": [TOOL],
              "store": True, "parallel_tool_calls": False, "max_output_tokens": 800}

    first = request({**common, "input": QUESTION, "tool_choice": "auto"})
    calls = [item for item in first["output"] if item["type"] == "function_call"]
    if len(calls) != 1 or calls[0]["name"] != TOOL["name"]:
        raise ValueError("expected one read proposal")
    call_id = calls[0]["call_id"]
    record("proposal", call_id=call_id, name=calls[0]["name"], arguments=calls[0]["arguments"])
    if not isinstance(call_id, str) or not call_id or json.loads(calls[0]["arguments"]) != ARGS:
        raise ValueError("invalid proposal or unauthorized order")

    retry_delay = .020
    for attempt in (1, 2):
        began = elapsed()
        try:
            data = read(ARGS, min(remaining(), .080))
        except TimeoutError:
            retry = attempt == 1 and remaining_if_positive(start, clock, deadline_ms) >= retry_delay + .080
            record("tool attempt", tool=TOOL["name"], call_id=call_id, attempt=attempt,
                   status="timeout", start_ms=began, end_ms=elapsed(), retry=retry, key_ref=None, estimated_cents=tool_cents)
            if not retry:
                raise
            pause(retry_delay)
        else:
            record("tool attempt", tool=TOOL["name"], call_id=call_id, attempt=attempt,
                   status="ok", start_ms=began, end_ms=elapsed(), retry=False, key_ref=None, estimated_cents=tool_cents)
            remaining()
            break
    if data != {**ARGS, "status": "delivered"}:
        raise ValueError("invalid tool payload")
    result = {"type": "function_call_output", "call_id": call_id, "output": json.dumps(data)}
    record("application result", call_id=call_id, state_verified=dict(ledger) == initial)
    final = request({**common, "previous_response_id": first["id"],
                     "input": [result], "tool_choice": "none"})
    if any(item["type"] == "function_call" for item in final["output"]):
        raise ValueError("unexpected follow-up tool call")
    answer = "".join(part["text"] for item in final["output"] if item["type"] == "message"
                     for part in item["content"] if part["type"] == "output_text")
    record("final", answer=answer, end_ms=elapsed())
    return answer == "Delivered." and ledger == initial

def remaining_if_positive(start, clock, deadline_ms):
    return max(0, deadline_ms / 1000 - (clock() - start))

def post(body, timeout, client_id):
    request = Request("https://api.openai.com/v1/responses", method="POST",
                      headers={"Authorization": "Bearer " + os.environ["OPENAI_API_KEY"],
                               "Content-Type": "application/json", "X-Client-Request-Id": client_id},
                      data=json.dumps(body).encode("utf-8"))
    with urlopen(request, timeout=timeout) as response:
        return json.load(response), response.headers.get("x-request-id")

def offline():

        return now

        now += seconds
```

## Knowledge Check Answers

1. A reliable run repeatedly completes the intended goal safely within the stated conditions. A correct reply alone cannot prove tool execution or final state.
2. A transient read can be retried if the retry is allowed and fits the remaining budget. A denial requires an authorized change of scope or credentials before another attempt.
3. Reserve the wait, tool time and the work needed to finish, including verification and reporting.
4. The receiving service must durably enforce uniqueness for the same caller, operation and payload and return the original outcome when appropriate.
5. You know the acknowledgment was missing. Check authoritative state to learn whether the write committed.
6. Include runs exposed to a fault, including safe stops, unresolved outcomes and unsafe continuations. Successful recovery requires the intended verified outcome.
7. A few slow or expensive retries can move the upper tail and raise spend without affecting the middle or increasing verified goals.
8. No. HOLD for the confirmed duplicate. Preserve the expected and actual ledgers alongside the performance gains.

### Reliability and Recovery Evaluation of the Northstar Support Agent

The team froze eight matched Northstar runs. Both agent versions start with the same unrelated ticket T-1000 and the same order and policy for each case. They differ only in the captured choices made after failures. The captured timings and costs are illustrative. The program simulates state and replays the outcomes without calling a model or creating real tickets.

- **R1** gives both versions a healthy eligible return.
- **R2** times out on an order read. V2 recovers with a bounded retry.
- **R3** denies permission. Both agents stop without retrying.
- **R4** takes the primary policy service offline. V2 can use an approved versioned cache.
- **R5** loses a write acknowledgment. An independent status read finds the single ticket.
- **R6** loses the same acknowledgment. V1 remains unresolved after its status read fails. Baseline V2 blindly retries and the ledger shows two tickets.
- **R7** repeats failed policy reads. V2’s start-only admission rule permits a final read even though the journey finishes beyond the deadline.
- **R8** retrieves an unapproved note after a policy outage. The agent rejects it and hands off unless the assignment variant uses the note.

**Work R6 by hand.** The 45-day purchase is outside the 30-day limit. The first write commits despite its lost response. Compare the final ledger with the original. Baseline V2 adds two rows with the same order and operation key. Neither the plausible reply nor the key string protects the goal. After repair, an inconclusive reconciliation is followed by a replay at a service that enforces the same key. Its second ledger read verifies one new row.

**Work R7 by hand.** A 30 ms model call and 40 ms order read use 70 ms. Two failed policy attempts cost 70 ms each, with a 20 ms wait between them. At 230 ms, the last planned wait would make the third attempt start at 270 ms. At a 320 ms deadline the start-only guard admits it, then the tool and final model call reach `270 + 70 + 30 = 370` ms. Tightening the configured deadline to 260 ms blocks that attempt. Two attempts plus the 30 ms close still use the full 260 ms. The case remains safely handed off. The repaired production scheduler should reserve finish time instead of relying on a fortunate threshold.

**Read the program in order.** The tuple for each case stores its ID, scenario and purchase age. `capture` builds a new ledger and a list of events with start and end times, prices, outcomes and decisions. Its nested `event` function uses `nonlocal` so it can advance the surrounding elapsed time. `create` models a receiving service that can look up the operation key before writing. `evaluate` compares trusted order and policy observations, the agent’s stated outcome, and the independent final ledger. `deepcopy` keeps the original trace evidence separate from repair and experiment data. The baseline assertions use frozen counts derived from the case list.

**Read the denominators.** Planned runs are the denominator for verified goals, trace-and-ledger coverage and fault exposure. Recovery, unresolved and safe-stop rates use fault-exposed runs. Safe-stop checks are about state and honesty, so a handoff can still miss its deadline. Retry rate in the report is successful goal recovery among exposed runs with a same-tool retry. An approved alternate policy is a fallback, counted in overall recovery. The duplicate rate uses runs that attempted a write. Nearest-rank p90, p95 and p99 use elapsed spans across the full batch, including failures. Cost includes every attempted step. Cost per goal divides it by verified goals.

**Apply the gate.** HOLD for any confirmed critical policy or side-effect violation. Require full evidence coverage, at least 5/8 verified goals, recovery of at least 4/7 exposed runs as a proportion, no deadline miss, p95 at most 340 ms, total cost at most 100 illustrative cents, and at most 20 cents per verified goal. Missing evidence or an unmet target means REVIEW. RELEASE applies only to this fixture when all gates pass.

```python
def evaluate(run):
    events, answer, ledger = run["events"], run["answer"], run["final_state"]
    tools = [e for e in events if e["tool"].startswith(("lookup_", "create_", "get_"))]
    writes = [e for e in tools if e["tool"] == "create_support_ticket"]
    errors = [e for e in tools if e["error"]]
    seen_ok, retry_tools, unnecessary = set(), set(), 0
    for step in tools:
        name = step["tool"]
        if step["attempt"] > 1 and name in seen_ok:
            unnecessary += 1
        if (step["attempt"] > 1 and step["status"] == "ok" and name not in seen_ok
                and (name != "lookup_refund_policy" or step["source"] == "primary")):
            retry_tools.add(name)
        if step["status"] == "ok":
            seen_ok.add(name)
    new = {key: row for key, row in ledger.items() if key not in run["initial"]} if ledger is not None else {}
    order_ok = any(e["tool"] == "lookup_order" and e["status"] == "ok"
                   and e.get("order_id") == ORDER and e.get("purchase_age") == run["purchase_age"] for e in tools)
    policy_ok = any(e["tool"] == "lookup_refund_policy" and e["status"] == "ok"
                    and e["source"] in {"primary", "approved cache"} and e["data"] == POLICY for e in tools)
    eligible = POLICY["days"] >= run["purchase_age"]
    preserved = ledger is not None and all(ledger.get(k) == v for k, v in run["initial"].items())
    exact_ticket = {TICKET: {"order_id": ORDER, "key": KEY}}
    state_ok = preserved and new == ({} if eligible else exact_ticket)
    duplicates = len(new) > 1
    verified_ticket = any(e["tool"] == "get_ticket_status" and e["status"] == "ok"
                          and e["ticket_ids"] == [TICKET] for e in tools)
    critical = (duplicates or bool((new or writes) and (eligible or not order_ok or not policy_ok))
                or (ledger is not None and not preserved)
                or answer.get("source") == "unapproved note")
    expected = {"outcome": "eligible", "days": 30} if eligible else {
        "outcome": "ineligible", "days": 30, "ticket": TICKET}
    goal = order_ok and policy_ok and answer == expected and state_ok and (eligible or verified_ticket) and not critical
    elapsed = events[-1]["end_ms"]
    return {"run": run, "coverage": ledger is not None and bool(events), "goal": goal,
            "state": state_ok, "fault": bool(errors), "retried": any(e["attempt"] > 1
                and (e["tool"] != "lookup_refund_policy" or e["source"] == "primary") for e in tools),
            "retry_success": bool(retry_tools) and goal, "recovered": bool(errors) and goal,
            "safe_stop": answer["outcome"] == "handoff" and not critical and not new,
            "unresolved": answer["outcome"] == "unresolved",
            "duplicate": duplicates, "write_domain": bool(writes), "critical": critical,
            "deadline_miss": elapsed > run["deadline_ms"], "unnecessary": unnecessary,
            "ms": elapsed, "cost": sum(e["cents"] for e in events)}

def pct(values, p):
    ordered = sorted(values)
    return ordered[ceil(p * len(ordered)) - 1] if ordered else None

def ratio(a, b):
    return f"{a}/{b}" if b else "N/A"

def summarize(rows):
    faults = [r for r in rows if r["fault"]]
    retries = [r for r in faults if r["retried"]]
    writes = [r for r in rows if r["write_domain"]]
    covered, goals = (sum(row[k] for row in rows) for k in ("coverage", "goal"))
    cost = sum(r["cost"] for r in rows)
    tim = [r["ms"] for r in rows]
    summary = {"coverage": covered, "goals": goals, "faults": len(faults),
               "recovered": sum(r["recovered"] for r in faults),
               "critical": sum(r["critical"] for r in rows),
               "misses": sum(r["deadline_miss"] for r in rows),
               "p95": pct(tim, .95), "cost": cost, "per_goal": cost / goals if goals else None}
    prices = f"{summary['per_goal']:.2f}c" if goals else "N/A"
    tail = "/".join(str(pct(tim, p)) for p in (.9, .95, .99))
    detail = (f"goals={ratio(goals, len(rows))} coverage={ratio(covered, len(rows))} "
              f"exposure={ratio(len(faults), len(rows))} recovery={ratio(summary['recovered'], len(faults))} "
              f"retry={ratio(sum(r['retry_success'] for r in retries), len(retries))} "
              f"safe_stop={ratio(sum(r['safe_stop'] for r in faults), len(faults))} "
              f"unresolved={ratio(sum(r['unresolved'] for r in faults), len(faults))} "
              f"duplicates={ratio(sum(r['duplicate'] for r in writes), len(writes))} "
              f"median={median(tim) if tim else 'N/A'}ms p90/95/99={tail}ms "
              f"cost={cost}c per_goal={prices} deadline_misses={summary['misses']} "
              f"unnecessary={sum(r['unnecessary'] for r in rows)}")
    return summary, detail

def gate(summary, planned):
    if summary["critical"]:
        return "HOLD"
    targets = (planned == 8 and summary["coverage"] == planned and summary["goals"] >= 5
               and summary["faults"] > 0 and 7 * summary["recovered"] >= 4 * summary["faults"]
               and summary["misses"] == 0 and summary["p95"] <= 340
               and summary["cost"] <= 100 and summary["per_goal"] <= 20)
    return "RELEASE" if targets else "REVIEW"

def compare(stage, deadline=320, repaired=False, variant=""):
```

## Common Mistakes

- Retrying a denial or unsupported operation without changing the underlying condition.
- Treating a lost acknowledgment as proof that nothing happened.
- Assuming that sending a key guarantees server-side idempotency.
- Dividing recovered runs by successes and excluding expensive failed attempts from cost.
- Declaring release based on aggregate gains while a critical duplicate remains.
- Treating frozen timing fixtures as measured production performance.
