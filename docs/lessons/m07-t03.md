## Beginner Explanation

### Start with the exact comparison

| Case | Current | Proposed |
| --- | --- | --- |
| C01 | PASS | PASS |
| C02 | FAIL | PASS |

In two matched cases the proposed version gained one pass and lost none. That is evidence about these two questions. Now imagine it wrongly tells someone on day 45 that they still have time. The next question in the test could change the launch decision.

The current configuration is the **baseline**. Freeze its resolved model version, prompt text and version, generation settings, tools or policy source, and response-handling rules. The proposed configuration is the **candidate**. Give both a stable configuration ID. Save the dataset, rubric, judge settings, run ID, and the captured responses so a colleague can replay the comparison. This is a **locked baseline** because a later re-run can identify the exact version used.

| Question you want to answer | Change on purpose | Keep fixed |
| --- | --- | --- |
| Does a different model help? | Model A to Model B | Prompt, policy input, cases, rubric, and comparable generation and retry settings |
| Does the prompt help? | V1 to V2 | Model, policy input, cases, generation settings, and evaluation |
| Is the complete package better? | A documented bundle | Cases and evaluation rules. Record every intentional change. |
| What happens to real users? | Randomly assigned complete variants | Eligibility, outcome definitions, collection rules, and the comparison window |

Check the effective settings rather than just the settings you requested. One model can obey a format instruction that another ignores, take longer at the same workload, or fail in a different way. Decide what to do if a setting has no equivalent. If you customize the prompt or retry policy for one model, the result measures a bundle. Treat invalid or missing results consistently. Keep them out of binary accuracy, report them in coverage, and inspect whether they cluster in a hard segment.

### Pair the cases and count gains and losses

Join both replies on the same case ID, then place each complete pair in one of four groups. Both pass and both fail are agreements. A baseline-only pass is a regression. A candidate-only pass is an improvement. For example, 1 both-pass, 1 baseline-only, 2 candidate-only and 0 both-fail gives baseline 2/4 = 50% and candidate 3/4 = 75%. The difference is +25 percentage points. Relative to 50%, the increase is 25 ÷ 50 = 50%. When the baseline is zero, the relative increase is undefined.

The net paired gain is two improvements minus one regression, or one additional pass across four cases. A positive total can hide a real loss. Read the baseline-only rows. A comparison on four cases with both conditions fixed still describes those four held-out cases. Repeat it if generation varies, and group related cases before drawing statistical conclusions. If one side has an unreadable verdict, report both configurations’ valid coverage and restrict the paired effect to the same complete case IDs. A candidate with 6 valid passes out of 7 valid answers could look better partly because its toughest case was omitted.

### Change one factor and look at the interaction

Try four combinations on the same known-answer cases, using Model A or B and Prompt V1 or V2. Compare A/V1 with A/V2 to isolate the prompt on A. Compare A/V1 with B/V1 to isolate the model under V1. A two-by-two matrix also lets you check whether the effect of V2 is the same on B. If the prompt adds no passes on A and one on B, the observed prompt benefit depends on the model. That pattern is an **interaction** in this fixture.

Put C02 and C03 side by side. The reminder to mention both refund conditions helps on C02. On C03, the new reply asks for an order number before answering a question whose answer is already in the policy. Compare both replies using the same rubric. Then imagine that you also swapped the model. You could see whether the bundle improved, but the comparison would give you no way to tell which edit produced the change. That attribution problem is **confounding**.

### Check where the improvement happened

Group questions by the policy situation they test. These groups are **segments**, or slices. Look at routine, receipt, outside-window, and ambiguous questions separately. If the candidate gains two routine passes but loses one outside-window case, the overall rate can rise while the replies with the most serious consequences get worse.

Before testing, decide how much loss in a key segment would be acceptable for a given trade-off. Suppose faster delivery is worth at most a three-point drop in accurate routine guidance. That is a **noninferiority margin** of −3 points for candidate minus baseline. An appropriate confidence bound above −3 would support the claim that the drop is smaller than the allowance under the design. A bound at −8 leaves too much uncertainty even when the observed difference is −1. For example, for a 5% one-sided decision, use an appropriate one-sided 95% lower bound. A lower limit of −2 clears the −3 margin. The previous lesson shows how pairing changes uncertainty. Choose a method appropriate for that design before examining the result. An equality test with a large p-value cannot establish noninferiority. [CONSORT extension on noninferiority margins](https://jamanetwork.com/journals/jama/fullarticle/1487502)

The lab’s segment review uses an observed drop as a screening signal and gives no formal noninferiority conclusion. For eight prepared cases, report the effect and the exact paired test from M07-T02 as illustrative evidence. A nonsignificant result leaves the comparison open. A significant result would still need adequate coverage, practical benefit, and critical checks. Plan the primary comparison and a fresh confirmatory set before picking a winner from several alternatives.

### Use accuracy with the other release evidence

Choose a primary metric before looking at results. Offline, Harbor Leaf uses policy-correct pass rate. Record response time, cost per response, invalid-verdict rate, and coverage as separate measures. Report which attempts enter the latency and cost summaries. In a larger study inspect slow-tail latency as well as the mean. Online, you might also measure resolution without repeat contact and inspect satisfaction or escalation rate if you can measure them fairly. A user feeling reassured does not verify a 90-day promise.

A **critical gate** blocks on a verified wrong deadline or explicit receipt waiver. **Operational guardrails** limit mean latency and estimated cost in the toy lab. Set a practical floor for the observed gain so a tiny improvement does not justify an expensive change. Under the fictional rules, say HOLD when a blocking requirement fails, REVIEW when coverage, uncertainty or other evidence leaves the case open, and RELEASE only when the documented evidence clears the rules. In a real rollout, also plan monitoring and rollback.

Record `RELEASE` as the fixture's gate recommendation. Keep each case result and any run or exposure-log gaps in their own records. The accountable release owner decides whether to authorize the exact candidate and rollout scope and records the required sign-offs. A monitoring incident can pause a rollout while those earlier records remain valid. [Status crosswalk](#m02-t03) · [Release approvals and governance](#m13-t03)

### Randomize users when the question is about live effects

The offline comparison asks how both configurations answer the same prepared cases. A live A/B asks what happens when eligible users are assigned different variants. Lock eligibility before assignment. Randomly allocate users, keep each user on their assigned variant, and keep the same observation window and outcome definition. An **exposure** is a logged opportunity to see the assigned assistant. Record both assignment and exposure. A user who falls back to the old route still belongs to the group they were assigned when you estimate the effect of assigning the new variant.

For the teaching pilot, plan a 50/50 split and observe seven days with a fixed 24-hour resolution window per user. Estimate resolved requests per assigned user and prespecify deadline errors and latency as guardrails. Do not repeatedly peek at the primary outcome and stop as soon as it looks favorable. Stop or pause early for verified critical harm, missing exposure logs, or a broken assignment mechanism. Follow-up outside the planned window needs its own plan.

If the observed assignment proportions differ unexpectedly from the planned allocation, investigate **sample-ratio mismatch** before interpreting the outcome. Exposure can also differ while assignment is balanced. Check eligibility, assignment code, routing, and logging in order. A person seeing both variants is **contamination**. Inspect that case separately without silently dropping it from the assigned arm. [Fabijan et al., Diagnosing Sample Ratio Mismatch](https://www.microsoft.com/en-us/research/publication/diagnosing-sample-ratio-mismatch-in-online-controlled-experiments-a-taxonomy-and-rules-of-thumb-for-practitioners/)

The lab simulates assignment, exposure, and outcomes so you can debug an exposure gap. The output does not produce a live A/B effect or authorize a rollout.

### Step 7 — Report a decision without overwriting the failure

Replay five selected cases from the held-out table. The historical tuples store baseline and candidate verdicts plus the critical flag. The replay copies the dictionary and replaces only the affected tuple. The replacement stands for a new frozen reply that correctly tells the day-45 customer the deadline has passed. For uncertainty, `comb()` counts equally likely directions in the discordant-pair test from M07-T02.

[Open Python Editor](https://www.online-python.com/)

```python
from math import comb

experiment, dataset, rubric = "refund-subset-1", "refund-holdout-73", "refund-binary-v1"
baseline, candidate = "A/V1", "B/V2"
revision = "baseline"
history = {
    "C01": ("routine", "PASS", "PASS", False),
    "C02": ("routine", "FAIL", "PASS", False),
    "C03": ("receipt", "PASS", "PASS", False),
    "C05": ("outside", "PASS", "FAIL", True),
    "C07": ("ambiguous", "FAIL", "PASS", False),
}
rows = history.copy()
if revision == "deadline-repair":
    rows["C05"] = ("outside", "PASS", "PASS", False)
paired = [row for row in rows.values() if all(label in ("PASS", "FAIL") for label in row[1:3])]
n = len(paired)
a = sum(row[1] == "PASS" for row in paired)
b = sum(row[2] == "PASS" for row in paired)
wins = sum(row[1:3] == ("FAIL", "PASS") for row in paired)
losses = sum(row[1:3] == ("PASS", "FAIL") for row in paired)
m = wins + losses
p = min(1.0, 2 * sum(comb(m, k) for k in range(min(wins, losses) + 1)) / 2 ** m)
critical = [case for case, row in rows.items() if row[3]]
latency_ms, cost = 700, 0.023
gain = (b - a) / n
if critical or latency_ms > 900 or cost > 0.025:
    decision = "HOLD"
elif n < len(rows) or gain < 0.10 or p > 0.05:
    decision = "REVIEW"
else:
    decision = "RELEASE"

print(f"{experiment} | {dataset} | {rubric} | {revision}")
print(f"{baseline} {a}/{n} -> {candidate} {b}/{n} | coverage {n}/{len(rows)}")
print(f"Gain {100*gain:+.1f} pp | improvements {wins} | regressions {losses} | exact p {p:.5f}")
print(f"Outside slice: {history['C05'][1]} -> {rows['C05'][2]}")
print(f"Mean latency {latency_ms} ms | cost ${cost:.3f} | critical {','.join(critical) or 'none'}")
print(f"Audit C05 B: original {history['C05'][2:]} | replay {rows['C05'][2:]}")
print(f"Recommendation: {decision}")
```

```text
Gain +20.0 pp | improvements 2 | regressions 1 | exact p 1.00000

Audit C05 B: original ('FAIL', True) | replay ('FAIL', True)

```

```python
def index_records(expected, rows):
    indexed = {}
    for case, reply, label, latency, cost in rows:
        if case not in expected or case in indexed:
            raise ValueError(f"Unexpected or duplicate case ID: {case}")
        if reply not in replies or label not in (*valid_labels, "INVALID"):
            raise ValueError(f"Invalid capture or verdict for {case}")
        indexed[case] = (reply, label, latency, cost)
    return indexed

assert set(manifest) == set(captures)
assert all(prompt in prompts for _, prompt, _, _ in manifest.values())
assert all(len(keys) == len(cases) for keys in captures.values())

def paired(left, right, case_ids):
    ids = [case for case in case_ids if case in left and case in right
           and left[case][1] in valid_labels and right[case][1] in valid_labels]
    labels = [(left[case][1], right[case][1]) for case in ids]
    counts = tuple(labels.count(item) for item in
                   (("PASS", "PASS"), ("PASS", "FAIL"), ("FAIL", "PASS"), ("FAIL", "FAIL")))
    return ids, counts

def exact_p(losses, gains):
    discordant = losses + gains
    return min(1.0, 2 * sum(comb(discordant, k) for k in range(min(losses, gains) + 1)) / 2 ** discordant)

def guard_decision(critical, latency, cost, n, planned, gain, p, slice_alert):
    blockers = []
    if critical:
        blockers.append("critical")
    if latency is not None and latency > 900:
        blockers.append("latency")
    if cost is not None and cost > 25:
        blockers.append("cost")
    if blockers:
        return "HOLD (" + ", ".join(blockers) + ")"
    review = []
    if n < planned or not n or latency is None or cost is None:
        review.append("coverage")
    if slice_alert:
        review.append("slice")
    if gain is not None and gain < 0.10:
        review.append("practical gain")
    if p is None or p > 0.05:
        review.append("paired uncertainty")
    return "REVIEW (" + ", ".join(review) + ")" if review else "RELEASE"

    print(f"{name}: valid {len(valid)}/{len(cases)} | score {score} | missing {missing} | invalid {invalid} | {ops}")
    return latency, cost

    p = exact_p(losses, gains) if n else None
    change = f"{100*gain:+.1f} pp, rel {relative:+.1%}" if relative is not None else (
        f"{100*gain:+.1f} pp, rel unavailable" if n else "unavailable")

          + " | regressions " + (",".join(case for case in ids if left[case][1] == "PASS" and right[case][1] == "FAIL") or "none"))
```

## Common Mistakes

Compare the same case IDs before subtracting pass rates. Log missing and invalid results, including the hardest slice.

Use matched one-factor rows to attribute a change. For a bundle, name both changes and limit the conclusion to the bundle.

Check critical evidence and operational guardrails alongside uncertainty. For online tests inspect assignment, exposure, and outcomes before interpreting effects.
