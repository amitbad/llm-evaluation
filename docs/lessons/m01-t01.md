## Beginner Explanation

### 1. What a token represents

To work with text, a model first needs a way to represent it as numbers. A **tokenizer** is the code that splits the text into pieces and converts them into numeric IDs from a known set. Each piece is called a **token**. A model generates IDs for output tokens, which can then be turned back into text.

One token can cover a whole word, part of a word, punctuation, or a fragment that includes a space. Think about the two visible words in “balance ₹5,000.” A made-up splitter could represent the text as “balance”, “ ₹”, “5”, “,”, and “000”. That is five pieces for two space-separated units in this example. This split is just an illustration. A real tokenizer might group the pieces differently. Languages, unfamiliar names, spaces, and formatting can change the number of pieces. Two tokenizers may give different counts for the same text.

**Tokenization** is the splitting and numbering process. It matters when you ask how much text fits or what a request costs. Counting words with a document editor gives an approximation at best. In a real integration, use the tokenizer for the model you are calling or the service's measured usage when available. Record which method produced the count. The labs use numbers assigned by the author. Python’s ordinary string length and splitting operations alone do not reproduce a model tokenizer.

**Input tokens** represent the text sent into the model. **Output tokens** represent the text it generated. For a fictional price of 2 paise per input token and 6 paise per output token, 42 input tokens and 6 generated tokens would cost 120 paise, or ₹1.20. The arithmetic is 42 × 2 plus 6 × 6. The unused room you leave for a reply is capacity. This teaching bill uses only tokens processed or generated. Actual billing depends on the service and features in use. Reducing unnecessary text may lower cost, but dropping the essential policy can make the reply unreliable.

### 2. Conversations are ordered records

A **message** is one record in a conversation. It usually has a **role**, which identifies where it came from, and **content**, which carries its text or other data. The **request** is the information the application sends to the model for a particular turn. A turn is one exchange in the conversation. The **reply** is what comes back to the application. The model gets the request assembled for that turn, which may contain only part of the conversation you see in a chat interface.

Here are five role names you may see in an application. APIs differ in the roles they expose and how they represent instructions and tool calls. These descriptions explain the purpose of each role in the examples.

- **System.** Model-facing instructions for how the assistant should act. In this lesson the system message says it is Harbor Leaf Bank's support assistant.
- **Developer.** Instructions from the application builder. Here the developer says to use approved policy evidence and to say when an answer cannot be confirmed.
- **User.** What the customer asks or supplies. “What is the Standard Savings minimum?” is a user message. If the user guesses ₹10,000, their guess is still user input. It has no policy authority.
- **Assistant.** Text or a structured request produced by the assistant. A prior reply can appear as an assistant message in later requests. Its claim is evidence of what was said in the past. You still need a policy to establish whether the claim is accurate.
- **Tool.** Data returned by a program the assistant or application used. In the example a lookup tool returns an approved policy excerpt. A lookup result can also contain a draft, an error, or text from an untrusted source. Review what it contains and where it came from.

A **tool call** asks a program to do something, such as look up a policy. A **tool result** is its return value, such as the policy excerpt. An actual API may attach an identifier to a call and its result so the application can match them. The saved examples here use short readable records in place of those structured fields. They never run a lookup.

**Message order** is the sequence of records in the request. Start with the instructions, then the customer's question, the assistant's lookup request, and the corresponding tool result. An assistant reply can then use the result. On a subsequent turn the application might include that earlier exchange alongside a new question. If a result is attached to the wrong call, comes before its call, or is omitted, the request can become invalid or the evidence can be misinterpreted. Always keep the actual request or an equivalent trace before judging the answer. A **trace** is a saved record of what happened.

### 3. Context windows and token budgets

The **context window** is the capacity for information the model can handle in a request and its generation. Think of it as a shared budget in this lesson. Instructions, messages, tool outputs, source excerpts, and the customer's current question use input capacity. Encoding a message as part of a request can also add tokens for things like role markers. **Overhead** is the name we use for those extra tokens in the teaching examples. The reply uses output capacity.

Some model interfaces impose a separate **input limit** or **output limit**. An output limit is the largest reply the interface allows. The lab also uses an **output reserve**, the room the application decides to leave for the upcoming reply. Choose a reserve inside the output limit. Actual interfaces differ in how they enforce limits or reserve space. Use their documented rules for real requests.

Work through a small numerical example. Suppose the teaching window is 60 tokens, the input limit is 54, the output limit is 16, and you leave 12 tokens for the reply. The shared window gives you 60 − 12 = 48 tokens for input. The separate input cap is 54. Both limits must be respected, so 48 is the effective input budget. If your assembled input takes 52 tokens, its headroom is 48 − 52 = −4. A negative number is a shortfall. Trim at least four input tokens, adjust the reserve if the task can still be answered clearly, or reject the request before sending it. A shorter reply reserve leaves more input room but may also shorten what the model can say.

An application can **truncate** a conversation, which means dropping some of its content to fit the budget. One simple strategy removes the oldest eligible history first while keeping instructions and the latest question. Other applications summarize history, choose evidence by relevance, or stop when the request is too large. The lab’s rule belongs to our fictional application. A chat model is not guaranteed to keep, summarize, or drop any particular message for you.

Use a second version of the same teaching budget to see the risk. Reserve 12 tokens and hold the protected input at 28. An old policy exchange takes 14 and more recent small talk takes 10. The total input is 52. An oldest-first trim drops the policy group and leaves 38 tokens, well inside the 48-token budget. The system has made the request safe to send, but the evidence for the answer has gone. If you remove the small talk instead, input is 42 and the policy survives. Decide what matters for the task, then check that the kept conversation is still valid. If two tool messages need each other to make sense, trim or retain that exchange as a group.

### 4. Diagnose a failure at the stage where it happened

Evaluate the assistant's claim against the exact evidence it received. If the approved excerpt was present and the reply asserted ₹10,000, the reply contradicts evidence the model could see. If the excerpt was missing and it said it could not confirm the amount, the reply followed the instruction to abstain. **Abstain** means declining to make a factual claim when there is too little evidence. In that second run the application still needs attention if its goal was to deliver the approved answer. Both cases are worth recording, for different reasons.

Keep three pieces of information together. Save the intended request and its token budget. Save the messages actually sent or the list of groups dropped before sending. Save the reply and whether it met the expected behavior for that input. This distinguishes a request construction problem from a problem in the reply. It also prevents an old assistant answer or a customer's guess from becoming the policy you grade against.

### Step 1 — Store and inspect the messages

A **string** is text inside quotation marks. A **variable** is a name for a value. `messages = ...` assigns a value to that name. The value here is a **list**, an ordered collection inside square brackets. Each entry is a **dictionary**, a record inside braces. A dictionary's **key** names a field, and a colon separates that key from its value. Commas separate fields and records.

The `for` loop takes the list entries one at a time and names the current one `message`. The colon starts the loop body. Indentation, the spaces on the left, makes a line part of that body. Use square brackets after the dictionary name to retrieve a field by its key. `print()` displays the items you pass inside its parentheses, with spaces between comma-separated items. Inspecting the records in order can expose problems before you evaluate any reply.

### Step 3 — Calculate remaining context capacity

Subtract the output reserve from the context window to find the window’s allowance for input. `min()` returns the smaller of two numbers. Use it with the separate input limit to apply both restrictions. Once you have that budget, subtract the actual input size. The subtraction sign is `-`. The result, called **headroom** here, is how many input tokens are still available. A negative answer shows a shortfall.

Copy the block into a fresh editor or replace the previous file, then run it.

```python
context_window = 60
input_limit = 54
reserve = 12
input_tokens = 52

input_budget = min(input_limit, context_window - reserve)
headroom = input_budget - input_tokens

print("Input budget:", input_budget)
print("Input headroom:", headroom)
```

```text
Input budget: 48
Input headroom: -4
```

With a 12-token reserve, the shared budget allows only 48 input tokens. The saved input needs four more than that.

**Experiment.** Change only `reserve` from `12` to `8` and rerun. Assume the fictional model permits both output settings.

```text

Input headroom: 0
```

**Checkpoint.** What does zero headroom tell you? The input uses its entire allowance. The eight-token output reserve remains available. Any extra input would need to displace something or increase the budget.

### Step 4 — Simulate dropping old history

Keep the system message, developer message, current question, and overhead protected as 28 tokens. Treat the policy lookup and its related result as one history group so the simulated trim does not leave an orphaned tool record. A **while loop** repeats its block while its condition remains true. The greater-than sign, `>`, checks whether input exceeds the budget. `and` requires both conditions to hold. A list used as a condition is true when it has items.

The dot in `history.pop(0)` accesses a list operation. `pop(0)` takes out and returns the first item, at position zero. Each removed group's count is subtracted from the total. This version shows just enough of oldest-first trimming to inspect its consequences.

Copy the block into a fresh editor or replace the previous file, then run it.

```python
protected = 28
input_budget = 48
history = [
    {"name": "approved policy exchange", "tokens": 14},
    {"name": "recent chat", "tokens": 10},
]

input_tokens = protected
for group in history:
    input_tokens = input_tokens + group["tokens"]
print("Before trimming:", input_tokens)

while input_tokens > input_budget and history:
    removed = history.pop(0)
    input_tokens = input_tokens - removed["tokens"]
    print("Dropped:", removed["name"])

print("Input sent:", input_tokens)
for group in history:
    print("History kept:", group["name"])
```

```text
Before trimming: 52
Dropped: approved policy exchange
Input sent: 38
History kept: recent chat
```

The oldest group is removed as a unit. Removing all 14 tokens leaves more room than the four needed to make the request fit. It also removes the approved amount. “Input sent” describes what the simulated application would send. The program only prints the report.

### Step 7 — Build an offline context-budget diagnostic

A **function** is a named block you can run repeatedly. The keyword `def` defines it. Names inside its parentheses are **parameters**, the values the function uses when you call it. The colon and indentation mark the block to run. A plain `return` stops the function early. Use it when no safe request can be formed under these limits.

This diagnostic checks the maximum output setting first. The `<` symbol means less than, and `or` means either condition is enough. It then checks whether the protected input can fit. Finally it works through an independent list of history groups created with `history.copy()`. The list copy lets the simulation remove entries without changing the original list. It never edits the individual dictionaries. The `append()` operation adds each dropped name to a separate list for the report.

Copy the whole block into a fresh editor or replace the previous file, then run it.

```python
def diagnose(window, input_limit, output_limit, reserve, protected, history):
    if reserve < 1 or reserve > output_limit:
        print("STOP: output reserve is outside the allowed range.")
        return

    budget = min(input_limit, window - reserve)
    print("Input budget:", budget)
    if protected > budget:
        print("STOP: protected input cannot fit.")
        return

    kept = history.copy()
    input_tokens = protected
    for group in kept:
        input_tokens = input_tokens + group["tokens"]

    dropped = []
    while input_tokens > budget and kept:
        group = kept.pop(0)
        dropped.append(group["name"])
        input_tokens = input_tokens - group["tokens"]

    policy_kept = False
    for group in kept:
        if group["approved_policy"]:
            policy_kept = True

    print("Dropped groups:", dropped)
    print("Input sent:", input_tokens)
    print("Input headroom:", budget - input_tokens)
    if policy_kept:
        print("Evidence: approved policy retained")
    else:
        print("Evidence: missing approved policy; expect abstention")


window = 60
input_limit = 54
output_limit = 16
reserve = 12
protected = 28
history = [
    {"name": "approved policy exchange", "tokens": 14, "approved_policy": True},
    {"name": "recent chat", "tokens": 10, "approved_policy": False},
]

diagnose(window, input_limit, output_limit, reserve, protected, history)
```

```text
Input budget: 48
Dropped groups: ['approved policy exchange']
Input sent: 38
Input headroom: 10
Evidence: missing approved policy; expect abstention
```

The report prints a list of removed names, in square brackets, so you can inspect the trim. The request fits with ten tokens of input room after dropping the group. It has lost the evidence. The diagnostic tells you what to expect under the evidence rule. It does not generate a reply or certify that a real model would follow that rule.

**Experiment.** Change only `reserve` from `12` to `8`. Run again.

```text

Input sent: 52
Input headroom: 0
Evidence: approved policy retained
```

**Checkpoint.** Could you always shrink the output reserve to save an old policy? A reply still needs enough room for its intended job and must respect the model's output settings. Try retaining relevant evidence and dropping unrelated chat before sacrificing room for the answer.

## Worked Solutions to Practice

### Solution 1

The input costs 42 × 2 = 84 paise. The first reply costs 6 × 6 = 36, so its total is 120 paise. The second costs 10 × 6 = 60, so its total is 144 paise. The difference is 24 paise. The tokenizer decides how many pieces the model processes. Ordinary word counts do not establish measured token usage.

### Solution 2

The first record is system, the second developer, and the third user. The fourth is tool and the fifth is assistant. The assistant call should follow the user question and come before the tool result. An actual tool protocol might also require the result to match the call's identifier. Save the exact ordered request and the tool evidence, then capture the reply so the next reviewer can check which messages were available before the answer.

### Solution 3

The reserve of 12 is within the output limit of 16. The shared window leaves 60 − 12 = 48 tokens for input. The smaller of 54 and 48 is 48. Input of 52 is short by four. Dropping the ten-token small-talk group leaves 42, or six tokens of headroom. The approved policy is still present. Dropping the policy also frees space but would leave the model without the needed fact.

### Solution 4

Trace A contradicts evidence present in the request. Record an incorrect answer and verify that the policy actually reached the model in the correct order and role before attributing cause. Trace B abstains in agreement with the evidence rule, and the application lost required context during preparation. Replay the same question and instructions with the policy group preserved, then compare the held-out reply with the approved amount.

## Common Mistakes

- **Equating tokens with words.** Use model-specific counts for real requests. The numbers assigned in this lab are for teaching arithmetic.
- **Assuming the whole chat history reaches the model.** Inspect the actual request, including the tool result and any history that was dropped.
- **Keeping all old text at the expense of evidence.** Select history and excerpts for the current question and keep any required call and result pairs.
- **Treating a user guess or old assistant reply as policy.** Check role, source, and date before treating a value as approved evidence.
- **Using a fit calculation as a quality verdict.** Check token headroom and evidence retention separately. The model’s actual reply still requires evaluation.
