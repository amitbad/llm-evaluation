## Beginner Explanation

### 1. Give the assistant enough of the conversation

Look at the customer’s follow-up again. If you replace “What if I go below that?” with “What if my Standard Savings balance goes below ₹5,000?”, the question makes sense by itself. A chat app has another option. It can keep the question natural and send the earlier exchange along with it. The earlier lines are the conversation history.

A large language model, or LLM, is the part of the assistant that writes an answer using the information it receives. When you hit Send, an app like ChatGPT can assemble some earlier parts of the conversation, the new question, and other information. It sends that package to the model as a request. The answer comes back as the reply. In this lesson we call a question and its reply a turn. The chat screen and the package sent for any one turn can contain different amounts of history.

Each entry the app sends is a message. Look at “What’s the minimum balance for Standard Savings?” The words are its content. A separate label tells the model where those words came from. That label is the role. The customer’s two questions have the user role. The earlier “₹5,000” has the assistant role because the assistant wrote it.

Keep the follow-up word for word and try covering up both earlier lines. Here, “that” loses its meaning. In a test, hold the latest question fixed and run it with and without the earlier exchange. Save the messages actually sent. If the follow-up only fails when the app omits the history, check the history selection before trying to change the model.

### 2. Keep instructions and evidence separate

Suppose the customer adds, “I think the minimum is ₹10,000.” That’s useful information about what they believe. The bank still needs its own approved policy to settle the amount.

The bank sends instructions the customer may never see. In our saved example, the system message says, “You are Harbor Leaf Bank’s assistant.” A separate developer message from the people building the app says, “Use approved policy as evidence. If the policy doesn’t answer the question, say you can’t confirm it.” Read that second instruction as a rule about how to answer. The amount and the fee still have to come from somewhere else.

Try putting the same sentence, “Use approved policy as evidence,” in the customer’s message. The words are unchanged, but now the customer is the speaker. If an app accidentally labels the bank’s instruction as customer text, check that label first when the assistant ignores it. Different model services have different rules for their instruction roles. Check what the chosen service supports and what the app actually sent.

The assistant can ask a policy lookup program for help. A program the assistant can use this way is a tool. An assistant message asking the lookup to search for Standard Savings is a tool call. The excerpt that comes back is a tool result, sent with the tool role in this example. It says the minimum is ₹5,000 and a ₹100 monthly fee applies below it.

Put the follow-up, the lookup call, and its result in order. Try swapping just the call and the result. In our saved example the service rejects that sequence before writing an answer. A real service may also require a matching identifier so the app can tell which result belongs to which call. Keep the ordered messages, the selected policy, and either the reply or the error together. That record is called a trace. A trace helps a reviewer distinguish an answer that was wrong from an attempt that never produced an answer.

### 3. Count the pieces the model reads

Write “balance ₹5,000” on paper. If you use the space as a dividing line, you get two groups. Try using these five pieces instead. Put a line after “balance”, after “ ₹”, after “5”, after the comma, and at the end of “000”. Join them again and you still have the same text, including the space before ₹.

A language model uses numbers to represent text. Reusing parts of words lets it represent unfamiliar names and numbers without keeping a separate entry for every spelling. A piece can be a whole word, part of a word, a mark such as a comma, or a piece with a space attached. Each piece is a token. A tokenizer splits the text and looks up the number for each piece. When the model writes an answer, its output numbers can be turned back into text. Our split on paper illustrates the idea. The real model’s tokenizer decides the actual boundaries.

Try “balance ₹5000” with the comma removed. You changed one mark without changing the amount. A tokenizer might combine the digits differently. Try adding a second space before ₹ instead. A space can be its own piece or travel with a nearby piece, so that change can also affect the count.

Compare “minimum balance” with “न्यूनतम शेष राशि”, a way to say it in Hindi. A tokenizer’s set of familiar pieces can split those strings differently. You’d need the actual tokenizer to know either count. The language alone doesn’t tell you which string will use more tokens.

Why count these pieces? Imagine two ways of sending the same policy excerpt. One version of the full request uses 42 tokens. With a change in formatting, another uses 46 in this invented example. With room for only 44, the first fits and the second needs a change. At a fictional price of 2 paise per input token, the second also costs eight paise more to send, assuming the billing rule is otherwise the same. A reviewer can hold the policy meaning fixed, vary the formatting or language, then record actual token use, what survived, and whether the answer still works.

Check this before moving on. Would a Python program that counts spaces tell you whether the 46-token version fits? It could count space-separated groups, but you need the chosen model’s tokenizer or measured token usage to make that decision. The Python lab adds the practice counts provided in the examples.

### 4. Leave room for the answer

The bank wants to send the question, its instructions, some earlier chat, and the policy paragraph the lookup found. It also wants the model to write an answer. The space the model can work with for this request and its generated answer is called its context window. Use the following small limits for practice. They aren’t specifications for a real service.

The window holds 60 tokens. The app sets aside 12 for the reply, leaving 48 for what it sends. What goes in uses input tokens. Some are used to represent message roles and boundaries in this teaching example. We call those extra tokens overhead. The reply uses output tokens. The planned room for the reply is its output reserve. A separate output limit of 16 permits a reserve of 12 here.

The app also has a separate input limit of 54. Since it must satisfy both 54 and 48, the smaller number wins. The resulting input budget is 48. If the input would take 52, the request is four tokens over. We’ll write the difference, 48 − 52 = −4, as input headroom. The negative sign tells you it’s over budget.

Change only the reserve to eight. Now 60 − 8 leaves 52, and the separate limit still allows that much. Exactly 52 input tokens fit. The change also leaves the upcoming reply with less room. If an explanation needs more than eight tokens, look at what you could remove from the input before lowering the reserve. A real service may apply different input and output rules, so use its actual limits when testing.

### 5. Find what disappeared

Keep the original 12-token reserve. In the practice request, the required instructions, current question, and message overhead take 28 input tokens. The older policy lookup and result take 14, and recent small talk takes 10. That’s 52 tokens of input, four more than the budget allows.

First try a rule that always cuts the oldest optional group. Cross out the 14-token lookup exchange. You have 38 tokens left, and you lost the policy. Cutting part of a request to make it fit is one kind of truncation. Compare that with cutting ten tokens of small talk. The remaining 42 fit, and the policy can still answer the customer. Keep a lookup call and its result together when you cut, and keep retained messages in their original order.

Longer documents can expose the same problem even after small talk is gone. Keep the required 28 tokens, the question, and the output reserve fixed. With the short 14-token policy exchange, the input is 42. Replace it with a 26-token exchange containing a longer document. The input is now 54, six over budget. An app might reject it, send a focused approved excerpt, or leave out something important. Run the short and long cases with the same question. Check whether the fee sentence actually reaches the model before you grade the reply. This can explain why a short test passes while the longer one fails.

Other ways to make room include summarizing earlier chat and keeping the exact policy wording, or deliberately stopping when the required pieces alone won’t fit. A summary can also lose details, so test a question that depends on one of them. For this bank, check that the prepared input keeps both what “that” refers to and the approved fee rule. A request can fit while still losing either one.

### 6. Give the failure a useful name

Imagine two teammates send you the same note. “The assistant didn’t give the fee.” Open the records before treating these as the same failure.

In the first record, the model had the fee paragraph and said there was no fee. You can mark the answer wrong and point to the paragraph it contradicts. In the second record, the cutoff removed the fee paragraph. The assistant said it couldn’t confirm the fee. The answer followed the bank’s rule for missing information. Declining to make a claim you can’t support is called abstaining. The app still failed to bring the needed policy into that request.

Write two lines for each case. On one line, record what the app actually supplied. On the other, record what the assistant said. For the first case, investigate how the answer was produced given the evidence. For the second, test a change to the app that keeps the policy, then ask the same question again. If you change the question too, you lose the clean comparison.

### 7. Price the tokens actually used

Go back to the version that keeps the policy and sends 42 input tokens. The app sets aside 12 for the reply. This time the reply uses six.

At the invented prices of 2 paise per input token and 6 paise per output token, input costs 42 × 2 = 84 paise. Output costs 6 × 6 = 36 paise. The bill totals 120 paise, or ₹1.20. The practice bill charges for six generated tokens. The unused space is still part of the planning limit, and actual billing depends on the service.

Try a ten-token reply with everything else held fixed. Four extra output tokens cost another 24 paise. The request still had room for that reply. If the team wants to spend less, compare measured usage after a change and check that the assistant still gets the facts needed to answer.

### Step 3 — Calculate remaining context capacity

You know the request wants 52 input tokens. Before sending it, work out what the model will allow. In `context_window - reserve`, `-` subtracts the room held for the reply. That gives you 48.

`min()` picks the smaller of the two numbers inside its parentheses. Here it compares the input limit of 54 with the 48 tokens left in the window. Once you have the smaller number, the next line subtracts what the request uses. That leaves the room available, or the amount you’re over if the result is negative.

Copy this block into the editor and select **Run**. Compare the two lines with your calculation.

```python

input_limit = 54
reserve = 12
input_tokens = 52

input_budget = min(input_limit, context_window - reserve)
headroom = input_budget - input_tokens

print("Input budget:", input_budget)
print("Input headroom:", headroom)
```

```text
Input headroom: -4
```

With a 12-token reserve, the shared budget allows only 48 input tokens. The saved input needs four more than that.

### Step 4 — Simulate dropping old history

You’ll make the request smaller and see what the app gives up. First read one history row, `{"name": "recent chat", "tokens": 10}`. The braces hold named values, so this is a dictionary. A name such as `"tokens"` is a key. The colon connects it to its value. Commas separate pairs. `group["tokens"]` asks for the number under that key in the current row.

The two rows sit inside square brackets, which make an ordered list. Here the lookup and its result share one row, so the trim can remove them together. Read `for group in history:` as “take each row in turn and call the current one `group`.” This repeating pattern is a loop. The colon and spaces at the start of the next line show what to repeat. Those spaces are called indentation. Add each row’s count to the protected 28 tokens before deciding whether the request needs a trim.

Follow the `while` line only after reading the first total. It asks whether 52 is greater than 48 using `>`. It also checks that `history` still has items. The word `and` means both checks have to hold. This loop repeats until the input fits or there’s nothing left to remove.

`history.pop(0)` takes out the first item. Python numbers list positions from zero. The dot gives you an operation that belongs to the list, and `pop(0)` hands back the row it took out. Save it under `removed` so you can print its name and subtract its tokens. The next time through, the input fits, so there’s nothing more to remove.

Copy the block into the editor and select **Run**. Read what was dropped as well as the new count.

```python
protected = 28
input_budget = 48
history = [
    {"name": "approved policy exchange", "tokens": 14},
    {"name": "recent chat", "tokens": 10},
]

input_tokens = protected
for group in history:
    input_tokens = input_tokens + group["tokens"]
print("Before trimming:", input_tokens)

while input_tokens > input_budget and history:
    removed = history.pop(0)
    input_tokens = input_tokens - removed["tokens"]
    print("Dropped:", removed["name"])

print("Input sent:", input_tokens)
for group in history:
    print("History kept:", group["name"])
```

```text
Input sent: 38
History kept: recent chat
```

The oldest group is removed as a unit. Removing all 14 tokens leaves more room than the four needed to make the request fit. It also removes the approved amount. “Input sent” describes what the simulated application would send. The program only prints the report.

### Step 7 — Build an offline context-budget diagnostic

You can now count the pieces, make room, and check that the policy is still there. This program runs those checks together so you can try a different request without rewriting them. Start with the numbers at the bottom. `diagnose(...)` sends those values into the part of the program that does the work.

A named set of instructions like this is a **function**. At the top, `def` gives it the name `diagnose`. The names between the parentheses are **parameters**, the names it gives the values you pass in. The colon and indented lines show which instructions belong to it. Those lines run when you call `diagnose(...)` at the bottom. `return` ends the run early when there’s no useful trim to try.

Read the function from the top. `reserve < 1` checks for fewer than one reserved token. `or` means either check can trigger the stop. A reserve above the output limit also stops the run. The next stop protects the required input. If that much won’t fit, trimming history can’t fix it.

If both checks pass, `history.copy()` makes a separate list. Removing entries from it leaves the original list alone. We don’t edit the dictionaries inside either list. Start with `[]`, an empty list for the removed names. As the loop trims, `dropped.append(...)` adds each removed name to the end of that list.

Start `policy_kept` at `False`, meaning no policy has been found in the kept list yet. The last loop checks `approved_policy` on each remaining row and changes `policy_kept` to `True` if it finds the policy. This lets the final lines show both whether the request fits and whether it still has the evidence.

Copy the whole block into the editor and select **Run**. Read the dropped groups and the final evidence line together.

```python
def diagnose(window, input_limit, output_limit, reserve, protected, history):
    if reserve < 1 or reserve > output_limit:
        print("STOP: output reserve is outside the allowed range.")
        return

    budget = min(input_limit, window - reserve)
    print("Input budget:", budget)
    if protected > budget:
        print("STOP: protected input cannot fit.")
        return

    kept = history.copy()
    input_tokens = protected
    for group in kept:
        input_tokens = input_tokens + group["tokens"]

    dropped = []
    while input_tokens > budget and kept:
        group = kept.pop(0)
        dropped.append(group["name"])
        input_tokens = input_tokens - group["tokens"]

    policy_kept = False
    for group in kept:
        if group["approved_policy"]:
            policy_kept = True

    print("Dropped groups:", dropped)
    print("Input sent:", input_tokens)
    print("Input headroom:", budget - input_tokens)
    if policy_kept:
        print("Evidence: approved policy retained")
    else:
        print("Evidence: missing approved policy; expect abstention")


window = 60
input_limit = 54
output_limit = 16
reserve = 12
protected = 28
history = [
    {"name": "approved policy exchange", "tokens": 14, "approved_policy": True},
    {"name": "recent chat", "tokens": 10, "approved_policy": False},
```

## Common Mistakes

- **Equating tokens with words.** Use model-specific counts for real requests. The numbers assigned in this lab are for teaching arithmetic.
- **Assuming the whole chat history reaches the model.** Inspect the actual request, including the tool result and any history that was dropped.
- **Keeping all old text at the expense of evidence.** Select history and excerpts for the current question and keep any required call and result pairs.
- **Treating a user guess or old assistant reply as policy.** Check role, source, and date before treating a value as approved evidence.
- **Using a fit calculation as a quality verdict.** Check token headroom and evidence retention separately. The model’s actual reply still requires evaluation.
