## Why This Lesson Matters

A customer asks Harbor Leaf Bank how much money they need to keep in Standard Savings. The bank’s policy says ₹5,000. The chat assistant says it can’t confirm the amount.

Think about what you would do if a colleague gave that answer. You might ask, “Did you have the policy in front of you?” If they didn’t, giving them the right page would help more than telling them to try harder. You can ask the same question about a chat assistant.

An LLM, short for large language model, is the part of this assistant that writes a reply from the information it receives. We’ll follow what the bank sends it. By the end, you’ll be able to tell the difference between a reply that gets the policy wrong and an app that never gives the assistant the policy.

Harbor Leaf is fictional. Its Standard Savings policy sets a ₹5,000 minimum and charges ₹100 per month when the balance is below ₹5,000. The amounts, model limits, and prices are for practice.

## Beginner Explanation

### 1. Read the chat the way a reviewer would

Start with two lines you might see on the screen.

**Customer.** “What is the Standard Savings minimum?”

**Assistant.** “I think it’s ₹10,000.”

Those lines tell you what each person said. They don’t tell you which amount the bank actually requires. That’s why we keep track of where each line came from. Each entry is a **message**. Its **role** tells you who or what supplied it. Its **content** is what it says or carries. Here, the roles are **user** and **assistant**.

Try swapping the speakers. If the customer wrote “I think it’s ₹10,000,” that would be a user guess. If the assistant wrote it, it would be a claim you could check. In neither case would it become bank policy.

There may be instructions the customer never sees. In our example, an instruction saying “You are Harbor Leaf Bank’s assistant” belongs to the **system** role. Another instruction from the people building the app says to use approved policy and speak up if it can’t confirm an answer. We’ll label that one **developer**. Mark these two lines as instructions before you look for the policy. They tell the assistant what to do. Neither gives it the amount.

### 2. Follow the bank policy into the conversation

The assistant can ask a lookup program for the bank’s policy. A program it can use this way is called a **tool**. The assistant’s “Look up the Standard Savings policy” is the **tool call**. The line “Approved Standard Savings minimum: ₹5,000” that comes back is the **tool result**. That result gets the tool role. Its content carries the excerpt. A result could also carry an old draft or an error, so check what the program returned before treating it as evidence.

Put the instructions, the customer’s question, the lookup call, and the result in order on paper. Put the call before the result. If you had two lookups, you’d also need to know which result belonged to which call. A real model service may use a matching ID. Its **API**, the agreed way the app communicates with the service, specifies the roles and any matching fields it expects. The examples here are simplified records you can read by eye.

Now follow what happens when the customer sends a message. The app gathers the instructions and relevant entries and sends them to the model as a **request**. The answer that comes back is the **reply**. We’ll call one such exchange a **turn**. A chat screen can show previous turns that the app leaves out of the new request. You can see the whole conversation on screen without knowing which parts the model saw.

The **message order** is the sequence the app sent. If the result comes before its call, an interface that requires that pairing may reject the request. If the wrong result is attached, the assistant may get the wrong policy. Save the actual ordered entries and what happened when the app sent them. That saved record is a **trace**. In Step 1 you’ll swap two lines of a trace and see why being able to read or print it tells you little about whether a service would accept it.

### 3. Count the pieces the model can use

Look at “balance ₹5,000.” On paper you might mark two groups separated by a space. Try marking five pieces instead. Put boundaries around “balance”, “ ₹”, “5”, “,”, and “000”. The original text is still there. You’ve divided it differently.

A language model works with numbered pieces of text. Each piece is called a **token**, and the program that divides the text and looks up the number for each piece is a **tokenizer**. When the model writes a reply, the numbers it generates can be turned back into text.

Our split is made up to show why words and tokens can have different counts. A real tokenizer can keep a whole word together, split an unfamiliar name, or attach a space to the next piece. Two tokenizers can split the same sentence differently. Try dividing “₹5,000” a different way and keeping every character. You’ll get a different number of pieces without changing the amount.

The splitting and numbering process is called **tokenization**. When a team needs a real count, it uses the tokenizer for the actual model or checks the service’s measured usage. The lab gives you invented counts so you can practice adding them. A word count or a character count in Python doesn’t tell you how this model split the text.

### 4. Leave room for the reply

Suppose the app is ready to send a question that takes eight tokens. It also needs to send instructions and the policy, and it wants the assistant to write an answer. All those pieces have to fit. The total space the model can use for what goes in and what it generates is its **context window**.

The material sent to the model uses **input tokens**. There can be extra tokens for how the request represents messages and roles. We’ll call those extras **overhead**. The text the model generates uses **output tokens**.

Work through one limit at a time. Our teaching model’s window is 60 tokens. Leave 12 for the reply. That planned space is the **output reserve**, and it leaves 48 tokens for input. The model’s separate maximum for output is 16, so reserving 12 fits within it.

Now check the separate **input limit**, which is 54. The app must satisfy both limits, so use the smaller number, 48. That’s the **input budget** for this request. If the material you want to send takes 52 tokens, subtract 52 from 48. The result is −4. This subtraction gives you the **headroom**, or room left for input. A negative result tells you how much you’re over.

Try reserving eight instead of 12. The shared window leaves 52 for input, so the request fits with no input room to spare. The assistant also has less room to answer. In a real service, check how it applies its limits before you choose a reserve. If you need the larger reserve, you can shorten the input or stop before sending.

### 5. Decide what to leave out

Keep the 12-token reserve. The app needs 28 input tokens for its instructions, the current question, and overhead. It has two other groups it could remove. An older exchange contains the policy and takes 14. Some recent small talk takes 10. Together the input takes 52, and you can send only 48.

Try crossing out the older exchange first. You have 38 input tokens left, but you crossed out the policy. Removing older messages to make a request fit is one example of **truncation**. Our app makes this choice because it removes the oldest group first. Other apps might choose what to keep by relevance, summarize earlier turns, or stop when the request is too large.

Now cross out the small talk instead. You have 42 input tokens left, and you still have the policy. So which shortened request would you send? You need to make two checks. It must fit, and it must contain the information that answers the question. Keep the lookup call and its result together when you trim, and keep the remaining messages in their proper order.

### 6. Work out what actually went wrong

With the policy in the request, the assistant can give the approved amount. If it says ₹10,000 even after seeing ₹5,000, you have a contradiction to investigate. Now compare that with a request that lost the policy. “I can’t confirm the minimum” follows the instruction to say when the evidence is missing. Declining to make a claim in that situation is called **abstaining**.

Try making a note for each run. Write what the app meant to send, what it actually sent, and what the assistant said. Where does the bank need to make a change? In the second run, check why the policy was dropped before asking the assistant to reply differently. Keeping the trace makes it possible for someone else to follow your decision.

### 7. Separate space you reserve from tokens you use

Go back to the version that keeps the policy and sends 42 input tokens. The app reserves 12 tokens for the reply, and the reply uses six. Suppose the input costs 2 paise per token and the generated output costs 6 paise per token.

The input costs 42 × 2 = 84 paise. The reply costs 6 × 6 = 36 paise. The total is 120 paise, or ₹1.20. We charged for six generated tokens in this practice bill. The other six tokens were room the app left available. Real billing depends on the service and features in use.

Try the same bill with a ten-token reply. You still had room for it in the same reserve. The extra four output tokens add 24 paise. If the team wants to cut costs, it can measure actual use and remove unnecessary text while checking that the policy is still present.

### Step 2 — Estimate a token budget

You’ll add up the pieces of a request before sending it. Start with one line from the program, `{"name": "system instructions", "tokens": 8}`. It stores the name and its count together. A set of named values inside braces is called a **dictionary**. A name like `"tokens"` is a **key**. A colon joins the key to its value, and commas separate the pairs. Because `8` has no quotes, Python treats it as a number it can add.

The square brackets hold the five rows in order. This is a **list**. Read `groups = [...]` as “give this list the name `groups`.” A name that refers to a value is a **variable**. The sign `=` gives the name on the left the value on the right. The same pattern sets `overhead` to four and starts `input_tokens` at that amount.

Read `for group in groups:` as “take one row at a time and call it `group`.” That’s a **loop**. The colon starts the work to repeat, and the spaces on the left, called **indentation**, keep the two lines inside it. `group["tokens"]` looks up the number in that row. On the first pass, Python prints the row and adds its eight tokens to the four already counted. The `+` sign adds, and `=` saves the new total. Commas between items in `print()` tell Python to show them with spaces between them.

Replace the editor’s contents with this block using **Copy Code**, then select **Run**.

```python
groups = [
    {"name": "system instructions", "tokens": 8},
    {"name": "developer instructions", "tokens": 8},
    {"name": "approved policy exchange", "tokens": 14},
    {"name": "recent chat", "tokens": 10},
    {"name": "current question", "tokens": 8},
]
overhead = 4
reserve = 12
input_tokens = overhead

for group in groups:
    print(group["name"], group["tokens"])
    input_tokens = input_tokens + group["tokens"]

print("Overhead:", overhead)
print("Input total:", input_tokens)
print("Input plus reserved output:", input_tokens + reserve)
```

developer instructions 8
approved policy exchange 14
recent chat 10
current question 8

Read the last three lines of the output. The five groups added up to 48. The running total already includes four extra tokens, so it prints 52 for input. The final line adds the 12-token reply reserve, bringing the space requested to 64. The program only adds the counts supplied in the list.

### Step 3 — Calculate remaining context capacity

You know the request wants 52 input tokens. Before sending it, work out what the model will allow. In `context_window - reserve`, `-` subtracts the room held for the reply. That gives you 48.

`min()` picks the smaller of the two numbers inside its parentheses. Here it compares the input limit of 54 with the 48 tokens left in the window. Once you have the smaller number, the next line subtracts what the request uses. That leaves the room available, or the amount you’re over if the result is negative.

Copy this block into the editor and select **Run**. Compare the two lines with your calculation.

```python
context_window = 60
input_limit = 54
reserve = 12
input_tokens = 52

input_budget = min(input_limit, context_window - reserve)
headroom = input_budget - input_tokens

print("Input budget:", input_budget)
print("Input headroom:", headroom)
```

```text
Input budget: 48
Input headroom: -4
```

With a 12-token reserve, the shared budget allows only 48 input tokens. The saved input needs four more than that.

**Experiment.** Change only `reserve` from `12` to `8` and rerun. Both reserves are allowed in this example. Leaving four fewer tokens for the reply makes the input fit exactly.

### Step 4 — Simulate dropping old history

You’ll make the request smaller and see what the app gives up. The first loop adds the two history groups to the protected 28 tokens. The lookup and its result are one group, so they can’t be separated by the trim.

Start the next loop by asking whether 52 is greater than 48. The sign `>` asks that question. `and` means both checks have to hold, and here `history` counts as true when it still has items. A `while` loop keeps trying its indented steps as long as the checks hold.

`history.pop(0)` takes out the first item. Python numbers list positions from zero. The dot gives you an operation that belongs to the list, and `pop(0)` hands back the row it took out. Save it under `removed` so you can print its name and subtract its tokens. The next time through, the input fits, so there’s nothing more to remove.

Copy the block into the editor and select **Run**. Read what was dropped as well as the new count.

```python
protected = 28
input_budget = 48
history = [
    {"name": "approved policy exchange", "tokens": 14},
    {"name": "recent chat", "tokens": 10},
]

input_tokens = protected
for group in history:
    input_tokens = input_tokens + group["tokens"]
print("Before trimming:", input_tokens)

while input_tokens > input_budget and history:
    removed = history.pop(0)
    input_tokens = input_tokens - removed["tokens"]
    print("Dropped:", removed["name"])

print("Input sent:", input_tokens)
for group in history:
    print("History kept:", group["name"])
```

```text
Before trimming: 52
Dropped: approved policy exchange
Input sent: 38
History kept: recent chat
```

The oldest group is removed as a unit. Removing all 14 tokens leaves more room than the four needed to make the request fit. It also removes the approved amount. “Input sent” describes what the simulated application would send. The program only prints the report.

### Step 5 — See how missing evidence changes evaluation

Read the two saved replies first. Both say ₹5,000. The difference is what the assistant received. The first row has the policy and marks `policy_present` as `True`, which means yes. The second lost it and marks it `False`, or no.

The program makes two decisions for each row. First, `if` runs its indented lines when the policy is present. `else`, which means “otherwise,” chooses the expected reply for a missing policy. That gives the name `expected` a value. Next `==` asks whether the saved reply exactly matches that expected text. One equals sign assigns a value. Two equals signs ask whether values are equal.

### Step 7 — Build an offline context-budget diagnostic

You can now count the pieces, make room, and check that the policy is still there. This program runs those checks together so you can try a different request without rewriting them. Start with the numbers at the bottom. `diagnose(...)` sends those values into the part of the program that does the work.

A named set of instructions like this is a **function**. At the top, `def` gives it the name `diagnose`. The names between the parentheses are **parameters**, the names it gives the values you pass in. The colon and indented lines show which instructions belong to it. Those lines run when you call `diagnose(...)` at the bottom. `return` ends the run early when there’s no useful trim to try.

Read the function from the top. `reserve < 1` checks for fewer than one reserved token. `or` means either check can trigger the stop. A reserve above the output limit also stops the run. The next stop protects the required input. If that much won’t fit, trimming history can’t fix it.

If both checks pass, `history.copy()` makes a separate list. Removing entries from it leaves the original list alone. We don’t edit the dictionaries inside either list. Start with `[]`, an empty list for the removed names. As the loop trims, `dropped.append(...)` adds each removed name to the end of that list.

Start `policy_kept` at `False`, meaning no policy has been found in the kept list yet. The last loop checks `approved_policy` on each remaining row and changes `policy_kept` to `True` if it finds the policy. This lets the final lines show both whether the request fits and whether it still has the evidence.

Copy the whole block into the editor and select **Run**. Read the dropped groups and the final evidence line together.

```python
def diagnose(window, input_limit, output_limit, reserve, protected, history):
    if reserve < 1 or reserve > output_limit:
        print("STOP: output reserve is outside the allowed range.")
        return

    budget = min(input_limit, window - reserve)
    print("Input budget:", budget)
    if protected > budget:
        print("STOP: protected input cannot fit.")
        return

    kept = history.copy()
    input_tokens = protected
    for group in kept:
        input_tokens = input_tokens + group["tokens"]

    dropped = []
    while input_tokens > budget and kept:
        group = kept.pop(0)
        dropped.append(group["name"])
        input_tokens = input_tokens - group["tokens"]

    policy_kept = False
    for group in kept:
        if group["approved_policy"]:
            policy_kept = True

    print("Dropped groups:", dropped)
    print("Input sent:", input_tokens)
    print("Input headroom:", budget - input_tokens)
    if policy_kept:
        print("Evidence: approved policy retained")
    else:
        print("Evidence: missing approved policy; expect abstention")


window = 60
input_limit = 54
output_limit = 16
reserve = 12
protected = 28
history = [
    {"name": "approved policy exchange", "tokens": 14, "approved_policy": True},
    {"name": "recent chat", "tokens": 10, "approved_policy": False},
]

diagnose(window, input_limit, output_limit, reserve, protected, history)
```

```text
Input budget: 48
Dropped groups: ['approved policy exchange']
Input sent: 38
Input headroom: 10
Evidence: missing approved policy; expect abstention
```

The report prints a list of removed names, in square brackets, so you can inspect the trim. The request fits with ten tokens of input room after dropping the group. It has lost the evidence. The diagnostic tells you what to expect under the evidence rule. It does not generate a reply or certify that a real model would follow that rule.

**Experiment.** Change only `reserve` from `12` to `8`. Run again. The input can now use 52 tokens. No group needs to go, so the last line says the policy is still there.

```text
Input budget: 52
Dropped groups: []
Input sent: 52
Input headroom: 0
Evidence: approved policy retained
```

**Checkpoint.** Could you always shrink the output reserve to save an old policy? A reply still needs enough room for its intended job and must respect the model's output settings. Try retaining relevant evidence and dropping unrelated chat before sacrificing room for the answer.

## Common Mistakes

- **Equating tokens with words.** Use model-specific counts for real requests. The numbers assigned in this lab are for teaching arithmetic.
- **Assuming the whole chat history reaches the model.** Inspect the actual request, including the tool result and any history that was dropped.
- **Keeping all old text at the expense of evidence.** Select history and excerpts for the current question and keep any required call and result pairs.
- **Treating a user guess or old assistant reply as policy.** Check role, source, and date before treating a value as approved evidence.
- **Using a fit calculation as a quality verdict.** Check token headroom and evidence retention separately. The model’s actual reply still requires evaluation.
