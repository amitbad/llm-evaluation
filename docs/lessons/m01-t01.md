## Beginner Explanation

### 1. What a token represents

Say you want to count the words in “balance ₹5,000.” You might point to two groups separated by a space. A model works with smaller pieces of text called **tokens**. A piece might be a word, part of a word, a punctuation mark, or a piece that includes a space.

The program that splits text and gives each piece a number from its vocabulary is a **tokenizer**. The model works with those numbers. When it writes a reply, the numbers it generates can be turned back into text.

Try splitting “balance ₹5,000” into “balance”, “ ₹”, “5”, “,”, and “000”. That’s five pieces for two space-separated groups. This is a made-up split. A real tokenizer may split it another way. Try picturing a name you’ve never seen or the same phrase with extra spaces. Spelling, language, and formatting can all change where the pieces fall. Different tokenizers may also count the same text differently.

Why care about the split? Counting the pieces tells you how much information will fit and can help you estimate what a request costs. The splitting and numbering process is called **tokenization**.

A word count is only a rough guide. For a real request, use the model’s tokenizer or the service’s measured usage if you have it. Write down how you got the count. In the lab, you’ll use counts we supplied. Neither Python’s character count nor splitting on spaces can reproduce a model’s tokenizer by itself.

Think of the request and reply as two entries on a bill. **Input tokens** count the pieces sent to the model. **Output tokens** count the pieces it generates.

Suppose input costs 2 paise per token and output costs 6. Sending 42 input tokens costs 84 paise. Generating a six-token reply costs another 36. That’s 120 paise, or ₹1.20. The arithmetic is 42 × 2 plus 6 × 6. Room you leave unused for a longer reply is capacity. Our pretend bill charges for tokens processed or generated. Real billing depends on the service and features in use.

If you want to spend less, start by looking for text the assistant doesn’t need. Removing the policy might save a few tokens and leave the assistant without the answer.

### 2. Conversations are ordered records

Imagine reading a chat transcript where every line starts with the speaker’s name. You need to know who said what. In an app, each entry is a **message**. Its **role** tells you where it came from, and its **content** holds the text or other data.

When the customer asks a question, the app gathers the information it will send. That package is the **request**. What comes back is the **reply**. We’ll call one exchange a **turn**. The chat on your screen may show more history than the app sends on that turn.

Here are five role names you may see in an application. APIs differ in the roles they expose and how they represent instructions and tool calls. These descriptions explain the purpose of each role in the examples.

- **System.** Model-facing instructions for how the assistant should act. In this lesson the system message says it is Harbor Leaf Bank's support assistant.
- **Developer.** Instructions from the application builder. Here the developer says to use approved policy evidence and to say when an answer cannot be confirmed.
- **User.** What the customer asks or supplies. “What is the Standard Savings minimum?” is a user message. If the user guesses ₹10,000, their guess is still user input. It has no policy authority.
- **Assistant.** Text or a structured request produced by the assistant. A prior reply can appear as an assistant message in later requests. Its claim is evidence of what was said in the past. You still need a policy to establish whether the claim is accurate.
- **Tool.** Data returned by a program the assistant or application used. In the example a lookup tool returns an approved policy excerpt. A lookup result can also contain a draft, an error, or text from an untrusted source. Review what it contains and where it came from.

Suppose the assistant asks a lookup program for the savings policy. That request to a program is a **tool call**. The excerpt the program sends back is a **tool result**. A real service interface, or **API**, may use an ID to match the result with the right call. The lab uses short records you can read by eye. Nothing runs a lookup.

Could you file a receipt against the right order if the order number were missing? A program needs the same kind of link between a lookup and its result.

Look at the **message order**, the sequence in which the records appear. In our example, you’ll see the instructions, the customer’s question, the assistant asking for a lookup, then the tool result. The assistant can use that result to answer. On the next turn, the app may include the earlier exchange with the new question.

If the result comes first, belongs to a different call, or is missing, the request can be rejected or the wrong evidence can be used. When you investigate, keep the request or a **trace**, a record that shows what happened.

### 3. Context windows and token budgets

Imagine packing one bag for an outbound trip and leaving space to bring something home. The things you pack and the things you bring back have to fit in the same bag.

In this lesson the shared space is the **context window**, the capacity for information the model can work with in a request and its generation. Instructions, messages, tool results, and the current question take up input space. So can extra pieces used to mark roles or organize a message. We call those extra tokens **overhead**. The reply takes up output space.

Some model interfaces impose a separate **input limit** or **output limit**. An output limit is the largest reply the interface allows. The lab also uses an **output reserve**, the room the application decides to leave for the upcoming reply. Choose a reserve inside the output limit. Actual interfaces differ in how they enforce limits or reserve space. Use their documented rules for real requests.

Let’s check a request before sending it. The model in our example has a 60-token window. Its separate limits are 54 input tokens and 16 output tokens. You leave 12 for the reply.

First subtract the 12 reserved tokens from the 60-token window. That leaves 48. The input has to fit under both 48 and 54, so you have an **input budget** of 48. The unused part of that budget is the **headroom**. With 52 tokens of input, the headroom is 48 − 52 = −4. You need at least four more tokens of room.

You could remove some input, leave a smaller reserve if the answer can still fit, or stop before sending the request. A smaller reserve makes room for input. It can also leave the assistant with too little room for a useful reply.

What can an app do when a conversation is too long? It can drop part of the history to make the request fit. This is called **truncation**. Our example keeps the instructions and the latest question and removes the oldest history it’s allowed to drop first. Other apps might summarize, pick the most useful evidence, or stop. The rule you see here belongs to this fictional app. Check what a real app actually keeps or removes.

Try the budget with three piles of input. The protected pile takes 28 tokens. An older exchange contains the policy and takes 14. Recent small talk takes 10. That’s 52, with room for only 48.

If you remove the oldest pile, you’ll have 38 tokens left and no policy. What if you remove the small talk instead? You’ll have 42 tokens left and still have the answer. Check the order of the kept conversation too. When a lookup call and its result belong together, keep or drop them as a group.

### 4. Diagnose a failure at the stage where it happened

Put yourself in the reviewer’s chair. First ask, “What could the assistant see?” If it had the approved excerpt and said ₹10,000, you can point to a contradiction. If it never received the excerpt and said it couldn’t confirm the amount, the reply followed the instruction to **abstain**, or decline to make a factual claim without enough evidence.

In that second run, the customer still didn’t get the answer. Look at how the app gathered or trimmed the policy before changing the assistant’s wording.

Keep three pieces of information together. Save the intended request and its token budget. Save the messages actually sent or the list of groups dropped before sending. Save the reply and whether it met the expected behavior for that input. This distinguishes a request construction problem from a problem in the reply. It also prevents an old assistant answer or a customer's guess from becoming the policy you grade against.

### Step 1 — Store and inspect the messages

Let’s print the saved chat in order so you can spot a missing or misplaced record before judging the reply. Start with `messages = ...`. The name `messages` is a **variable**, and `=` gives that name the value on its right. The square brackets hold a **list**, a collection that keeps its items in order.

Inside the list, each pair of braces holds a **dictionary**, a record with named fields. Text in quotation marks is a **string**. The names `"role"` and `"content"` are **keys**. A colon joins each key to its value, and commas separate fields and records.

Now read `for message in messages:` as “take each saved message in order and call the current one `message`.” The colon starts the loop’s body. The spaces on the left, called **indentation**, keep the print line inside that body.

On each pass, `message["role"]` and `message["content"]` look up the two fields. `print()` displays the values inside its parentheses. You give it three items separated by commas, so it places a space around the dash.

Copy this block, paste it into the editor or local file, and run it.

messages = [

### Step 2 — Estimate a token budget

Imagine adding the amount on each line of a receipt. Here the items are request groups, and their amounts are **illustrative token counts**. Put the four extra tokens from `overhead` into `input_tokens` first. Digits without quotes, like `4`, are numbers Python can add.

The loop prints one group and adds `group["tokens"]` to the running total. The `+` sign does the addition. After the loop, the program prints the input total, then adds the reply reserve on the final line. That last sum tells you how much shared space you’re asking for.

### Step 3 — Calculate remaining context capacity

Will this request fit? Start with the four numbers at the top of the program. In `context_window - reserve`, `-` subtracts the room you want for the reply. `min()` picks the smaller of that allowance and the separate input limit, because you have to meet both.

Next, subtract `input_tokens` from that budget to find `headroom`. Read the two print lines as “what fits?” and “how much room is left?” A negative result means you need to free space.

Copy the block into a fresh editor or replace the previous file, then run it.

```python
context_window = 60
input_limit = 54
reserve = 12
input_tokens = 52

input_budget = min(input_limit, context_window - reserve)
headroom = input_budget - input_tokens

print("Input budget:", input_budget)
print("Input headroom:", headroom)
```

```text
Input budget: 48
Input headroom: -4
```

With a 12-token reserve, the shared budget allows only 48 input tokens. The saved input needs four more than that.

**Experiment.** Change only `reserve` from `12` to `8` and rerun. Assume the fictional model permits both output settings.

```text

```

**Checkpoint.** What does zero headroom tell you? The input uses its entire allowance. The eight-token output reserve remains available. Any extra input would need to displace something or increase the budget.

### Step 4 — Simulate dropping old history

Suppose you have to make the request smaller. First, add up the protected 28 tokens and the two history groups. The old lookup and its result are one group, so removing them won’t leave an unmatched tool record.

Read `while input_tokens > input_budget and history:` as “keep doing this while the input is too large and there are still groups to try.” A **while loop** repeats while its condition is true. `>` means “greater than,” `and` requires both checks to hold, and a list used this way counts as true when it has items.

The dot in `history.pop(0)` gives you an operation on the list. `pop(0)` takes the first item out, at position zero, and hands it back. Save it as `removed` so you can subtract its tokens and print its name. At the end, read the new total and the names in the list that remains. This lets you see what you gave up to fit the budget.

Copy the block into a fresh editor or replace the previous file, then run it.

```python
protected = 28
input_budget = 48
history = [
    {"name": "approved policy exchange", "tokens": 14},
    {"name": "recent chat", "tokens": 10},
]

input_tokens = protected
for group in history:
    input_tokens = input_tokens + group["tokens"]
print("Before trimming:", input_tokens)

while input_tokens > input_budget and history:
    removed = history.pop(0)
    input_tokens = input_tokens - removed["tokens"]
    print("Dropped:", removed["name"])

print("Input sent:", input_tokens)
for group in history:
    print("History kept:", group["name"])
```

```text
Before trimming: 52
Dropped: approved policy exchange
Input sent: 38
History kept: recent chat
```

The oldest group is removed as a unit. Removing all 14 tokens leaves more room than the four needed to make the request fit. It also removes the approved amount. “Input sent” describes what the simulated application would send. The program only prints the report.

### Step 5 — See how missing evidence changes evaluation

What if you keep the reply the same and change only what the assistant could read? The first row has the policy. The second lost it. `True` and `False` mean yes and no here.

The first `if` runs its indented block when the policy is present. Its `else` gives you the expected reply when the policy is missing. The second `if` uses `==` to compare the saved reply with the expected text, then prints a label with the case name. For these exact, pre-reviewed replies, a text comparison is enough to let you practice reading the two results. A policy check that needs to accept new wording would need to look at meaning.

Copy this block into a fresh editor or replace the previous file, then run it.

### Step 7 — Build an offline context-budget diagnostic

Let’s put the budget checks in one place so you can try new values without rewriting the checks. A **function** is a named block you can run whenever you need it. `def` defines it. The names between the parentheses are **parameters**, the names it uses for the values you give it. The lines indented after the colon belong to the function.

Python saves those instructions when it reads them. The `diagnose(...)` line at the bottom actually runs them with this example’s numbers and history. A plain `return` ends the current run of the function early, which is useful when the request can’t fit.

Read the function from the top. `reserve < 1` checks for fewer than one reserved token. `or` means either check can trigger the stop. A reserve above the output limit also stops the run. The next stop protects the required input. If that much won’t fit, trimming history can’t fix it.

If both checks pass, `history.copy()` makes a separate list. Removing entries from it leaves the original list alone. We don’t edit the dictionaries inside either list. As the loop trims, `dropped.append(...)` adds each removed name to the end of the report list. The last loop checks each kept group’s `approved_policy` flag. The function reports whether the request still has the evidence, as well as whether it fits.

Copy the whole block into a fresh editor or replace the previous file, then run it.

```python
def diagnose(window, input_limit, output_limit, reserve, protected, history):
    if reserve < 1 or reserve > output_limit:
        print("STOP: output reserve is outside the allowed range.")
        return

    budget = min(input_limit, window - reserve)
    print("Input budget:", budget)
    if protected > budget:
        print("STOP: protected input cannot fit.")
        return

    kept = history.copy()
    input_tokens = protected
    for group in kept:
        input_tokens = input_tokens + group["tokens"]

    dropped = []
    while input_tokens > budget and kept:
        group = kept.pop(0)
        dropped.append(group["name"])
        input_tokens = input_tokens - group["tokens"]

    policy_kept = False
    for group in kept:
        if group["approved_policy"]:
            policy_kept = True

    print("Dropped groups:", dropped)
    print("Input sent:", input_tokens)
    print("Input headroom:", budget - input_tokens)
    if policy_kept:
        print("Evidence: approved policy retained")
    else:
        print("Evidence: missing approved policy; expect abstention")


window = 60
input_limit = 54
output_limit = 16
reserve = 12
protected = 28
history = [
    {"name": "approved policy exchange", "tokens": 14, "approved_policy": True},
    {"name": "recent chat", "tokens": 10, "approved_policy": False},
]

diagnose(window, input_limit, output_limit, reserve, protected, history)
```

```text
Input budget: 48
Dropped groups: ['approved policy exchange']
Input sent: 38
Input headroom: 10
Evidence: missing approved policy; expect abstention
```

The report prints a list of removed names, in square brackets, so you can inspect the trim. The request fits with ten tokens of input room after dropping the group. It has lost the evidence. The diagnostic tells you what to expect under the evidence rule. It does not generate a reply or certify that a real model would follow that rule.

**Experiment.** Change only `reserve` from `12` to `8`. Run again.

```text

Dropped groups: []
Input sent: 52
Input headroom: 0
Evidence: approved policy retained
```

**Checkpoint.** Could you always shrink the output reserve to save an old policy? A reply still needs enough room for its intended job and must respect the model's output settings. Try retaining relevant evidence and dropping unrelated chat before sacrificing room for the answer.

2. **It remains a user message.** The customer supplied that text. Check the approved policy for the account and date to establish the amount.

## Common Mistakes

- **Equating tokens with words.** Use model-specific counts for real requests. The numbers assigned in this lab are for teaching arithmetic.
- **Assuming the whole chat history reaches the model.** Inspect the actual request, including the tool result and any history that was dropped.
- **Keeping all old text at the expense of evidence.** Select history and excerpts for the current question and keep any required call and result pairs.
- **Treating a user guess or old assistant reply as policy.** Check role, source, and date before treating a value as approved evidence.
- **Using a fit calculation as a quality verdict.** Check token headroom and evidence retention separately. The model’s actual reply still requires evaluation.
