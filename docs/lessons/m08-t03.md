## Beginner Explanation

### Follow the handoffs

Imagine a customer receives the wrong product. Check the order sheet, the packing slip, and the parcel. A correct item on the order sheet and the wrong item on the slip point you toward the handoff that copied the order. The parcel shows the outcome. The other records help explain where it started.

Open Northstar’s saved query and reply. From the reply alone, you know the customer got the wrong deadline. You do not yet know whether the assistant read the wrong policy or misread the right one. Start with three handoffs. What did search find? What did the writer actually receive? What did the writer say? The answer the customer sees is a **symptom**. Working back through these handoffs is **failure attribution**.

Ask which record would distinguish a missing policy from a bad decision using the right policy. A ranked list can show that the refund rule existed among the candidates. Only the selected context shows whether the assistant saw it. If the selected context contained the full current rule, compare its wording with the answer and citations. A candidate list is only one stage of the investigation.

### Inspect the pipeline in order

A **trace** is the saved record of a case as it passes through the system. Start with the exact query, requested effective date, caller’s allowed role, expected answer facts, and authoritative policy version. Follow the same case ID through these stages.

- **Ingestion.** Policy files enter the system and become source records with IDs, versions, status, and access labels. Compare the approved manifest, or version register, with the import log. Missing documents, duplicate IDs, bad metadata, broken links, or a missing access label can make later searches wrong or unsafe.
- **Cleaning.** Raw text becomes searchable text. Compare the original with the cleaned text. Check whether a negation, decimal, or section boundary disappeared.
- **Chunking.** Documents become small passages. Open neighboring chunks and check their source IDs. “A photo is required” and “except for a damaged sealed parcel” could get separated. Too little overlap can lose the exception. Excessive overlap or overly large chunks can duplicate material and consume input space. Too-small chunks can lose the subject of a rule.
- **Indexing.** Chunks become searchable entries. Compare the chunk inventory with the indexed IDs. If a current chunk exists but the index missed it or kept an old revision, ranking never gets a fair chance.
- **Retrieval.** A query gives a set of eligible candidates. Check expected evidence IDs and which chunks were eligible. A query saying “proof of purchase” can miss a passage that only says “receipt.” Filter by the caller’s permissions before ranking or displaying results.
- **Ranking.** Matched candidates get scores and an order. Inspect scores, tie rules, and which passages fell below top-k. A high overlap on “45 days” can favor shipping over refunds.
- **Context selection.** The ranked list becomes the passages inserted into the prompt. Inspect the actual selected IDs and text. A word or token budget, first-slot policy, duplication, competing versions, or truncation can drop the needed rule even when it ranked in the search results.
- **Answer generation.** The query and delivered passages become the reply. Compare its atomic claims and decision against the approved policy and context. Look for unsupported claims, missing conditions, a wrong application of a rule, or an unnecessary refusal.
- **Citation generation.** Claims get references to source spans. Inspect whether a citation is missing, unknown, unrelated, stale, or restricted. A working link can still fail to support its claim.
- **Evaluation.** The saved trace and gold labels become a verdict. Check the case IDs, expected policy version, annotator notes, and denominators. A broken or outdated answer key can manufacture a “regression.”

If a record is missing, mark the gap. “No trace was saved” and “this passage was absent from a complete trace” are different observations. Inspect the first supported defect and keep downstream effects in the report. A **contributing factor** is one condition that helped produce the outcome, such as taking only the first passage. A **root cause** is an upstream condition you can change and test. Call a result confirmed only within the tested setting. A theory such as “the model prefers long passages” remains a **hypothesis** until a comparison isolates it. More than one cause can matter.

Use familiar labels in the case log. `INGESTION` for absent or malformed sources, `CHUNKING` for lost conditions at a boundary, `RETRIEVAL` for candidate or ranking failures (including a missing index entry if documented), `CONTEXT_SELECTION` for delivery failures, `GENERATION` for wrong use of sufficient evidence, `CITATION` for reference defects, `AUTHORIZATION` for a breached boundary, and `EVALUATION_DATA` for evidence that is too incomplete or inconsistent to score. Write the evidence beside every label. The lab can surface several at once and uses Step 2 to illustrate a chunking gap the main fixture does not simulate.

### Make one controlled change

Place two copies of the saved prompt side by side. Keep the customer’s question identical. In the first copy, leave the old 90-day passage. In the second, replace just that passage with the approved 30-day rule and receipt condition. Keep the generator setup and scoring rules fixed. Before running the comparison, predict which error a change to the passage could fix and which error might persist. A reviewer-supplied context replacement is an **oracle context swap**. Compare baseline and oracle at both retrieval and answer stages. If the error persists with good evidence, inspect answer use. If it disappears, test the retrieval or selection hypothesis with a normal run. An oracle skips search selection, so it cannot establish that production search found the policy.

Try a realistic ranking change next. Freeze the case set, source versions, answer rubric, and all unrelated settings. Record the experiment ID and the baseline and candidate manifests. Include the dataset and corpus versions, chunk settings, retriever and ranking settings, selector budget, prompt version, model or capture version, rubric, and run timestamp if using live traces. If answer behavior is represented by prewritten captures, explain how each capture is keyed to the case and selected context. Changing which fixture is read lets you test reporting and comparison. It does not predict a new model reply.

Think about a current refund question and one about a historical shipping rule. A blanket penalty on old passages can help the current question and break the historical one. The correct historical version is determined by the approved effective date, independently of the search score. Test new thresholds and ranking weights on development cases. Reserve some cases in each important group for a later check. Once you use a held-out case to tune the change, it becomes a regression case. Keep it, and gather fresh held-out evidence.

### Count changes on the same cases

A **regression** is a case that used to pass and now fails. A **fix** moves the other way. In a three-case example, refund fails and two other cases pass. The candidate fixes refund, breaks shipping, and keeps warranty passing. Both runs pass two of three. The paired counts expose one fix and one regression. Fix rate is `1/1` previously failing paired case. Regression rate is `1/2` previously passing paired cases. An unchanged failure also matters and stays visible. An unscored pair belongs in the coverage report, outside the fix and regression denominators.

A **golden regression dataset** stores approved expectations for each case. Keep query ID and wording, required passages and expected facts, expected citation versions, policy segment, as-of date, authorization role, and criticality. Treat it as versioned evidence. When policy changes, preserve old verdicts with the old labels and add reviewed expectations for the new version. Re-run on the same IDs before interpreting a difference.

Compute the following by hand for a case with two required chunks. Suppose the top two contain only one of them and the context has only one passage. Hit@2 is 1 because at least one gold chunk was retrieved. Recall@2 is `1/2`. Context sufficiency is false because the complete answer needs both. If the reply makes two claims and only one is supported, claim support is `1/2`. If it provides two claim–citation links and one is valid, citation validity is `1/2`. By contrast, a case that refuses to guess provides zero links. Report the absent links and the failed answer separately. Zero links cannot certify good citations.

For the suite, average recall across judged cases and divide successful case outcomes by the number of scorable cases. Coverage uses all planned cases as its denominator. Divide supported claims by evaluated claims and valid links by supplied distinct claim–reference links. Show all numerator and denominator counts. When comparing runs, count fixes against previously failing matched cases and regressions against previously passing matched cases. No eligible cases yields N/A. When comparing groups such as refunds, missing receipts, shipping, warranties, account access, and restricted information, show the individual rows as well as any mean. A large group can hide a small critical group’s failure.

### Write a decision that follows the evidence

A **gate** is a condition the candidate must satisfy, such as zero unauthorized disclosures. A **guardrail** limits an operational cost, such as latency. If a candidate adds two fixed cases while introducing an unauthorized citation, hold it even if the average goes up.

Tradeoffs deserve a controlled comparison. Larger top-k can improve recall at the cost of latency and context space. More overlap can preserve exceptions and increase duplicate text. Longer answers can cover more requirements and create more unsupported claims. Forcing higher answer coverage can encourage guessing. Finer citations can make verification easier and annotation slower. The lab uses illustrative latency computed from the candidate count and number of selected words. It does not measure a service.

On eight handpicked cases a one-case gain is `1/8` of the suite. That describes these cases and is too little evidence for a broad reliability claim. Keep case pairs intact for statistical comparisons. If a broader sample supports a gain, still check policy and authorization gates independently. RELEASE, HOLD, and REVIEW in this chapter are decisions under a documented fictional test policy.

## Worked Demonstration

### Example 1. Find where the 90-day error started

**User question.** “Can I get a refund after 45 days without a receipt?”

**Approved reference.** The 2026 register selects RF version 2. “Refund requests require a valid receipt and must be filed within 30 days of purchase.” Version 1, saved as `DOC-REFUND-OLD`, allowed 90 days and is retained for archival use. The expected answer is no, with both requirements explained.

Follow the saved baseline trace in order. The import includes RF versions 1 and 2 with correctly labeled provenance. Both policy paragraphs became intact chunks with their original source versions. The ranked list is `DOC-REFUND-OLD (6), RF-v2:c01 (4)`. The selector takes one passage, so only the old policy enters the prompt. Pause and predict which of the current requirements the writer can justify.

**Actual LLM response.** Fictional capture, “Yes. Refunds are available within 90 days. [DOC-REFUND-OLD]”

**Assessment.** Check the intake records first. Version 2 made it through import and chunking, and you can see it at rank 2. The first defect you can point to is that the archived version wins the ranking. Check the next record. The selector takes only the first result, so the writer never sees the approved rule. The 90-day claim and its stale citation follow that missing handoff.

**Failure classification.** Ranking, context selection, and a stale citation contribute. The reply’s wrong deadline fails the critical policy gate. The trace does not establish that the generator would ignore the approved rule if it saw it. In the oracle swap, hold these ranks and the rubric fixed, deliver `RF-v2:c01`, and score the prewritten answer associated with that context. Both required facts now match and cite the current passage. Hit@2 remains 1 in both. That supports a context-delivery explanation on these fixtures.

### Example 2. A ranking fix harms a historical query

**User question.** Compare Q1’s current refund question, Q2’s missing-receipt question, and Q3’s “In 2025, when could I contact Support for a shipping delay?”

**Approved reference.** Q1 needs `RF-v2:c01`. Q2 needs `MR-v1:c01`, which says to download receipts in Orders. Q3 needs `SH-v1:c01`, the approved 2025 source with 45 days. `SH-v2:c01` begins in 2026 and says 60 days.

Calculate a three-point penalty on older versions. Q1 starts with archive 6 and current 4. The archive drops to 3 and the current chunk wins 4 to 3. In Q2, receipt help stays 5 and the refund distractor stays 2, so nothing changes. Q3 starts with 2025 shipping 5 and 2026 shipping 4. The penalty makes the historical passage 2, so the future passage wins 4 to 2. Predict what the selector delivers on each case.

**Actual LLM response.** Three fictional captures in the penalized run give the current refund requirements, send the receipt user to Orders, and tell the 2025 shipping user the threshold was 60 days.

**Assessment.** Q1 is fixed, Q2 stays passing, and Q3 regresses. Hit@2 stays 3/3 on these three cases because their expected passages remain among the two ranked results. Supplying the correct passage first is the change that matters to this selector.

**Failure classification.** The global penalty causes a wrong-version selection for Q3. Apply the penalty only to current-policy requests, using the saved as-of date to recognize historical questions. Compare normal ranked runs on all cases and keep a separate check that an archive selected for a current request still fails.

### Example 3. Decide whether an apparent improvement can ship

**User question.** The support team asks whether the global freshness change is safe on the eight matched lab queries.

**Approved reference.** The release policy requires eight scorable cases, complete evidence and supported citations, no new regressions, no critical policy, source-version, or authorization failures, at least one confirmed fix on a paired replay, and maximum illustrative latency at or below 55 ms. An oracle-only result is diagnostic evidence.

**Actual LLM response.** The baseline gives the 90-day reply on Q1 and Q7. With the first change, both refund replies use 30 days. Q3 changes from “The threshold was 45 days” to “The threshold was 60 days.” The other five captures stay the same.

**Assessment.** Baseline sufficiency and correctness are both 6/8, and citation validity is 6/8. The first candidate improves those counts to 7/8, 7/8, and 8/9 respectively. Coverage stays 8/8. The expected evidence remains in the top two for all eight. The second fix makes all eight correct, with 9/9 valid links. Maximum illustrative latency is 37 ms before any change and 41 ms after each change.

**Failure classification.** Candidate one is HOLD because of one new regression and one inappropriate source version, despite more passing answers. The scoped second repair clears the lab’s gates. Compare the final report with the original baseline as well as the immediately preceding run to see which cases changed and which historical failures remain in the audit. These results concern the eight fixtures.

### Step 4 — Rerank a small lexical search

Award one point per distinct shared term, with an optional extra weight for matching `refund`. A set intersection `&` gives the overlap. The sort key `(-row[1], row[0])` orders by decreasing score, then ID for ties. The same query and chunk strings are compared in both runs.

[Open Python Editor](https://www.online-python.com/)

```python
chunks = {
    "RF": "refund policy requires receipt",
    "SH": "shipping delay 45 days",
}
queries = {
    "Q1": "refund 45 days",
    "Q2": "shipping delay refund",
}
gold = {"Q1": "RF", "Q2": "SH"}
refund_weight = 1
for question, text in queries.items():
    results = []
    for key, passage in chunks.items():
        shared = set(text.split()) & set(passage.split())
        score = sum(refund_weight if word == "refund" else 1 for word in shared)
        results.append((key, score))
    ranked = sorted(results, key=lambda row: (-row[1], row[0]))
    print(question, ranked, "hit" if ranked[0][0] == gold[question] else "miss")
```

```text
Q1 [('SH', 2), ('RF', 1)] miss
Q2 [('SH', 2), ('RF', 1)] hit
```

### Step 7 — Preserve a failed trace while testing a repair

Build a small report that records the different layers. A frozen dataclass is a record whose fields cannot be reassigned. `replace` returns a new version of a record. Keep the baseline and append a candidate only when the repair is enabled.

[Open Python Editor](https://www.online-python.com/)

```python
from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Run:
    id: str
    selected: str
    days: int
    citation: str

dataset = "northstar-v1"
case_id = "Q1"
gold = "RF-v2:c01"
ranked = ("DOC-REFUND-OLD", gold)
baseline = Run("baseline", ranked[0], 90, ranked[0])
repair = False
history = (baseline,)
if repair:
    history += (replace(baseline, id="oracle", selected=gold, days=30, citation=gold),)

print(f"NS-mini | {dataset} | {case_id} | pool={ranked}")
for row in history:
    sufficient = row.selected == gold
    correct = row.days == 30
    cited = sufficient and correct and row.citation == gold
    blocked = not correct
    findings = []
    if not sufficient:
        findings.append("CONTEXT_SELECTION")
    if not cited:
        findings.append("CITATION")
    print(f"{row.id}: {row.selected}, {row.days} days, cite={row.citation}")
    print(f"  Hit@2={int(gold in ranked)} context={int(sufficient)} correct={int(correct)} citations={int(cited)}")
    print(f"  stage={','.join(findings) or 'clear'} critical={int(blocked)}",
          "HOLD" if blocked else "REVIEW: diagnostic only")
print("Fixed:", int(len(history) == 2 and history[0].days != 30 and history[-1].days == 30))
print("New regressions:", int(history[0].days == 30 and history[-1].days != 30))
```

```text

  Hit@2=1 context=0 correct=0 citations=0
  stage=CONTEXT_SELECTION,CITATION critical=1 HOLD

New regressions: 0
```

def validate(records, source_rows):
    # Validate the original rows while duplicates are still observable.
    ids = [key for key, _ in source_rows]
    if len(set(ids)) != len(ids) or len({c.id for c in records}) != len(records):
        raise ValueError("Duplicate passage or case ID")
    for key, chunk in source_rows:
        if (not chunk.text or chunk.audience not in {"public", "staff"}
                or chunk.version not in manifest.get(chunk.source, {}).values()):
            raise ValueError(f"Invalid ingestion record: {key}")

def authorized(case, key):
    return key in chunks and chunks[key].audience in {"public", case.audience}

def approved(case, key):
    chunk = chunks[key]
    year = case.as_of if case.as_of is not None else 2026
    versions = manifest[chunk.source]
    published = [date for date in versions if date <= year]
    return bool(published) and chunk.version == versions[max(published)]

def replay(case, config):
    eligible = [(key, score) for key, score in case.pool if authorized(case, key)]
    blocked = sum(key in chunks and not authorized(case, key) for key, _ in case.pool)
    scored = []
    for key, score in eligible:
        versions = manifest[chunks[key].source]
        older = chunks[key].version != versions[max(versions)]
        if older and not (config.preserve_history and case.as_of is not None):
            score -= config.penalty
        scored.append((key, score))
    ranked = tuple(sorted(scored, key=lambda row: (-row[1], row[0]))[:config.k])
    oracle = config.oracle == case.id
    if oracle:
        selected = tuple(key for key in case.gold if authorized(case, key) and approved(case, key))
    else:
        # The fictional selector has one passage slot and a word budget.
        selected = tuple(key for key, _ in ranked[:1] if len(chunks[key].text.split()) <= config.words)
    reply = captures.get((case.id, selected[0])) if selected else abstention
    # Fixture cost in milliseconds, not a benchmark.
    latency = 20 + 3 * len(ranked) + sum(len(chunks[key].text.split()) for key in selected)
    return Trace(ranked, selected, reply, latency, blocked, oracle)

def assess(case, config, trace):
    findings = set()
    critical = set()
    ranked = {key for key, _ in trace.ranked if authorized(case, key)}
    visible = {key for key in trace.selected if authorized(case, key)}
    gold = set(case.gold)
    if any(key not in chunks for key in gold):
        findings.add("INGESTION")
    invalid_trace = (any(key not in chunks for key, _ in case.pool)
                     or any(key not in chunks for key, _ in trace.ranked)
                     or any(key not in chunks for key in trace.selected)
                     or (not trace.oracle and not visible <= ranked))
    if invalid_trace:
        findings.add("EVALUATION_DATA")
    if any(key in chunks and not authorized(case, key)
           for key in trace.selected + tuple(key for key, _ in trace.ranked)):
        findings.add("AUTHORIZATION")
        critical.add("authorization")
    if gold <= chunks.keys():
        if not gold <= ranked and not trace.oracle:
            findings.add("RETRIEVAL")
        elif not gold <= visible and not trace.oracle:
            findings.add("CONTEXT_SELECTION")
    stale = any(not approved(case, key) for key in visible)
    if stale:
        critical.add("source version")
        if not trace.oracle and not gold.intersection(key for key, _ in trace.ranked[:1]):
            findings.add("RETRIEVAL")
    available = {fact for key in visible if approved(case, key) for fact in chunks[key].facts}
    expected = set(case.expected)
    sufficient = gold <= visible and expected <= available
    if not gold or not expected:
        findings.add("EVALUATION_DATA")
    if trace.reply is None or not trace.reply.text.strip():
        findings.add("EVALUATION_DATA")
        return Result(case, config, trace, bool(gold & ranked),
                      len(gold & ranked) / len(gold) if gold else 0,
                      sufficient, None, 0, 0, 0, tuple(sorted(findings)),
                      tuple(sorted(critical)), "FAIL" if critical else "UNKNOWN")

    claims = {(key, value) for key, value, _ in trace.reply.claims}
    correct = claims == expected
    if sufficient and not correct:
        findings.add("GENERATION")
    if case.critical and any(
        key in dict(expected) and dict(expected)[key] != value for key, value in claims
    ):
        critical.add("critical policy")
    supported = sum(fact in available for fact in claims)
    valid = links = 0
    citation_failure = False
    for key, value, ref in dict.fromkeys(trace.reply.claims):
        links += bool(ref)
        if ref in chunks and not authorized(case, ref):
            findings.add("AUTHORIZATION")
            critical.add("authorization")
        passes = ref in visible and approved(case, ref) and (key, value) in chunks[ref].facts
        valid += passes
        citation_failure |= not passes
    if citation_failure:
        findings.add("CITATION")
    status = ("FAIL" if critical else "UNKNOWN" if "EVALUATION_DATA" in findings else
              "PASS" if sufficient and correct and not citation_failure else "FAIL")
    return Result(case, config, trace, bool(gold & ranked),
                  len(gold & ranked) / len(gold) if gold else 0,
                  sufficient, correct, supported, valid, links, tuple(sorted(findings)),
                  tuple(sorted(critical)), status)

def ratio(numerator, denominator):
    return f"{numerator}/{denominator}" if denominator else "N/A"

def summarize(rows, previous):
    a = {row.case.id: row for row in previous if row.status != "UNKNOWN" and row.correct is not None}
    scored = [row for row in rows if row.status != "UNKNOWN" and row.correct is not None]
    pairs = [(a[row.case.id].status, row.status) for row in scored if row.case.id in a]
    fixed = pairs.count(("FAIL", "PASS"))
    regressions = pairs.count(("PASS", "FAIL"))
    failures = sum(bool(row.critical) for row in rows)
    passes = sum(row.status == "PASS" for row in scored)
    guardrail = max((row.trace.latency for row in rows), default=None)
    valid = sum(row.valid_refs for row in scored)
    links = sum(row.links for row in scored)
    support = sum(row.supported for row in scored)
    claims = sum(len({(key, value) for key, value, _ in row.trace.reply.claims})
                 for row in scored if row.trace.reply)
    count = len(scored)
    mean_recall = (f"{sum(row.recall for row in scored) / count:.3f}" if count else "N/A")
    print(f"  Hit@2={ratio(sum(row.hit for row in scored), count)} Recall@2={mean_recall}"
          f" Context={ratio(sum(row.sufficient for row in scored), count)}"
          f" Correct={ratio(sum(row.correct is True for row in scored), count)}"
          f" Support={ratio(support, claims)} Citations={ratio(valid, links)}")
    print(f"  Pass={ratio(passes, count)} Coverage={ratio(count, len(rows))}"
          f" Fixed={ratio(fixed, sum(old == 'FAIL' for old, _ in pairs))}"
          f" Regressions={ratio(regressions, sum(old == 'PASS' for old, _ in pairs))}"
          f" Critical={failures} Max-ms={guardrail if guardrail is not None else 'N/A'}")
    if failures or regressions or (guardrail is not None and guardrail > 55):
        return "HOLD"
    if count < 8 or count != len(rows) or not links or valid != links or passes != count:
        return "REVIEW"
    if len(pairs) != len(rows) or not fixed or any(row.trace.oracle for row in rows):
        return "REVIEW"
    return "RELEASE"

def show(config, rows, previous):
    print(f"{config.id} | penalty={config.penalty} historical scope={config.preserve_history}"
          f" | k={config.k} words={config.words} oracle={config.oracle or 'none'}")
    prior = {row.case.id: row.status for row in previous}
    print("Case | Ranked candidates(scores) | Selected | Previous -> result | Findings | Critical")
    for row in rows:
        case, trace = row.case, row.trace
        ranked = ", ".join(f"{ref}({score})" for ref, score in trace.ranked if authorized(case, ref))
        chosen = ", ".join(ref for ref in trace.selected if authorized(case, ref))
        print(f"{case.id} | {ranked or '-'} | {chosen or '-'} | {prior.get(case.id, '-')} -> {row.status}"
              f" | {','.join(row.stages) or '-'} | {','.join(row.critical) or '-'}")
        if case.id in {"Q1", "Q3", "Q7"} and "authorization" not in row.critical:
            print(f"  reply: {trace.reply.text if trace.reply else '(missing)'}")
        if trace.blocked:
            print(f"  excluded before ranking: {trace.blocked} unauthorized candidate")
    decision = summarize(rows, previous)
    print("  Decision:", decision)

## Common Mistakes

- Treating a correct search result as proof it reached the writer.
- Changing scoring, chunking, and prompt instructions in the same experiment and attributing the outcome to one component.
- Calling a historical source stale without checking which date the user asked about.
- Counting missing traces as passes or discarding them from planned coverage.
- Counting a repaired case while ignoring a regression or critical authorization gate.
