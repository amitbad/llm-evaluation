## Why This Lesson Matters

Northstar wants a refund calculator for a fictional help desk. If a customer paid 1,200 cents and an approved fee is 200 cents, the calculator should return 1,000 cents. What if the fee is greater than the payment? What if the requester owns a different order? A calculator can be correct and the workflow that calls it can still make the wrong decision.

## Beginner Explanation

**Code generation** means producing code from a task description. A **specification** is the approved description of what the code should do. For Northstar, every payment and fee is a nonnegative integer number of cents. Boolean values and strings are rejected. A fee above the payment produces zero. Invalid types raise TypeError and negative cents raise ValueError. The calculator returns an integer and performs no other action.

A **function** is a named piece of code that takes inputs and can return a value. Allowing only whole cents avoids differences in rounding for this task. A **test case** gives the function specific inputs and checks its actual result against an independently defined expected result. An **assertion** checks that a condition holds. A failed assertion identifies the case and the expectation that was violated. Use real tests to enforce rules. An assertion inside a production function may be disabled, so use ordinary validation for the function's input contract.

### Experiment A — Find the first failing stage

Parsing turns text into a tree of Python constructs. Compilation checks additional rules and prepares instructions for the interpreter. Execution actually calls a function. Correctness compares a returned value or exception with the expectation. An expression can compile and still raise an exception when called. Python's parser can even accept a statement that compilation rejects, such as a return outside a function. [Python AST reference](https://docs.python.org/3/library/ast.html)

This exercise parses and compiles the displayed source, then calls its matching, already defined teaching function. The strings are never loaded as executable code. Each is one fixed fixture. A row without a callable stops before execution.

[Open Python Editor](https://www.online-python.com/)

```python
import ast


def wrong(price, fee):
    return price + fee


def correct(price, fee):
    return max(0, price - fee)


def crashes(price, fee):
    return price // (fee - fee)


fixtures = (
    ("A01", "def candidate(price, fee)\n    return price - fee", None),
    ("A02", "return 1000", None),
    ("A03", "def wrong(price, fee):\n    return price + fee", wrong),
    ("A04", "def correct(price, fee):\n    return max(0, price - fee)", correct),
    ("A05", "def crashes(price, fee):\n    return price // (fee - fee)", crashes),
)
for case_id, source, function in fixtures:
    try:
        tree = ast.parse(source)
    except SyntaxError:
        print(case_id, "PARSE_ERROR")
        continue
    try:
        compile(tree, "<teaching fixture>", "exec")
    except SyntaxError:
        print(case_id, "COMPILE_ERROR")
        continue
    try:
        actual = function(1200, 200)
    except ZeroDivisionError:
        print(case_id, "RUNTIME_ERROR ZeroDivisionError")
        continue
    print(case_id, "PASS" if actual == 1000 else "WRONG_ANSWER", f"actual={actual}")
```


### Experiments B and C — Make a small suite earn its confidence

A **unit test** exercises one component. Start with two public cases, including an equal fee and payment. Then score five additional held-out cases. **Held out** means these inputs are kept outside the candidate-facing prompt or development examples. Both sets are visible to you as the evaluator in this lesson.

Python's unittest module can record failed comparisons. assertEqual compares a result with a value. assertRaises expects a particular exception during the function call. Each tuple below pairs the test ID, arguments and oracle, the independently chosen correct outcome. A TestResult records a failure when an assertion disagrees and an error when execution raises unexpectedly.

[Open Python Editor](https://www.online-python.com/)

```python
import unittest


def subtraction(price, fee):
    return price - fee


def checked_refund(price, fee):
    if type(price) is not int or type(fee) is not int:
        raise TypeError("whole cents required")
    if price < 0 or fee < 0:
        raise ValueError("cents cannot be negative")
    return max(0, price - fee)


VISIBLE = (("B01 ordinary", (1200, 200), 1000), ("B02 equal", (400, 400), 0))
HELD_OUT = (
    ("C01 no payment", (0, 1), 0),
    ("C02 one cent over", (400, 401), 0),
    ("C03 negative", (400, -1), ValueError),
    ("C04 text input", ("400", 1), TypeError),
    ("C05 boolean fee", (400, True), TypeError),
)


def check_case(function, args, expected):
    check = unittest.TestCase()
    if isinstance(expected, type):
        check.assertRaises(expected, function, *args)
    else:
        actual = function(*args)
        check.assertIs(type(actual), int)
        check.assertEqual(actual, expected)


for name, function in (("subtraction", subtraction), ("checked", checked_refund)):
    for split, cases in (("visible", VISIBLE), ("held-out", HELD_OUT)):
        passed = 0
        for case_id, args, expected in cases:
            run = unittest.TestResult()
            unittest.FunctionTestCase(lambda: check_case(function, args, expected)).run(run)
            status = "ERROR" if run.errors else "FAIL" if run.failures else "PASS"
            passed += status == "PASS"
            print(name, case_id, status)
        print(name, split, f"{passed}/{len(cases)}")
```

### Experiment D — Check relationships between outputs

A **property** is a rule that should hold for many inputs. This bounded grid checks the permitted range, repeatability, and when the fee stays fixed, whether increasing the payment can reduce the refund. That last check is **metamorphic testing**. It changes one input in a controlled way and compares two outputs. Formatting cents as text should also preserve the amount without floating-point rounding.

[Open Python Editor](https://www.online-python.com/)

```python
def refund(price, fee):
    return max(0, price - fee)


def off_by_one(price, fee):
    return max(0, price - fee - 1)


def format_cents(amount):
    dollars, cents = divmod(amount, 100)
    return f"USD {dollars}.{cents:02d}"


def read_cents(displayed):
    dollars, cents = displayed.removeprefix("USD ").split(".")
    return int(dollars) * 100 + int(cents)


for name, function in (("refund", refund), ("off-by-one", off_by_one)):
    results = {"range": 0, "repeat": 0, "monotonic": 0, "round-trip": 0, "zero-fee": 0}
    for price in (0, 1, 99, 100):
        for fee in (0, 1, 100):
            amount = function(price, fee)
            results["range"] += 0 <= amount <= price
            results["repeat"] += amount == function(price, fee)
            results["monotonic"] += amount <= function(price + 1, fee)
            results["round-trip"] += read_cents(format_cents(amount)) == amount
            if fee == 0:
                results["zero-fee"] += amount == price
    for label, passed in results.items():
        print(name, label, f"{passed}/{4 if label == 'zero-fee' else 12}")
    print(name, "format(101):", format_cents(101))
```

### Experiment F — Separate comparable work from elapsed time

Suppose Northstar builds a list of unique order IDs, preserving their first occurrence. A list scan compares the current ID with every previously accepted ID until it finds a match. A set tracks membership separately while the list retains order. The supplied sizes contain only distinct fictional IDs, so the list always scans all earlier IDs. The work counter compares explicit comparisons with membership queries. It cannot tell you the cost of each underlying operation.

Run the core block in the editor. For local elapsed time, allocation and subprocess evidence, paste the same trusted block into a file named `northstar_performance.py`. Set RUN_LOCAL to True and run `python3 northstar_performance.py` from the directory containing the file. The local path uses a temporary working directory, an explicit command list, a minimal empty environment, and a wall-clock timeout. The child commands are fixed arithmetic and a short sleep. They have no file or network operations. Temporary directories, timeouts and Python isolated mode are process hygiene. Untrusted code requires an approved isolated worker with denied network access, no secrets, a least-privilege identity, read-only inputs, and CPU, memory, time, process and output limits. Do not accept candidate source in this exercise's child commands.

```python
RUN_LOCAL = False


def scan(ids):
    unique = []
    work = 0
    for order in ids:
        for known in unique:
            work += 1
            if known == order:
                break
        else:
            unique.append(order)
    return unique, work


def track(ids):
    seen = set()
    unique = []
    for order in ids:
        if order not in seen:
            seen.add(order)
            unique.append(order)
    return unique, len(ids)


def measure(function, ids):
    from statistics import median
    from timeit import repeat
    import tracemalloc

    milliseconds = [round(seconds * 1000, 3) for seconds in repeat(lambda: function(ids), repeat=5, number=1)]
    tracemalloc.start()
    try:
        result = function(ids)
        _, peak = tracemalloc.get_traced_memory()
    finally:
        tracemalloc.stop()
    print(f"local {function.__name__} n={len(ids)} ms={milliseconds} median={median(milliseconds)} peak_bytes={peak}")
    return result


def observe_timeout():
    import subprocess
    import sys
    from tempfile import TemporaryDirectory

    jobs = (("fast", "print(20 - 5)", 5), ("slow", "import time\ntime.sleep(2)", 0.25))
    with TemporaryDirectory() as workspace:
        for label, snippet, seconds in jobs:
            command = [sys.executable, "-I", "-B", "-c", snippet]
            try:
                result = subprocess.run(command, cwd=workspace, env={}, stdin=subprocess.DEVNULL, capture_output=True,
                                        text=True, check=True, timeout=seconds)
                print(label, "COMPLETED", result.stdout.strip())
            except subprocess.TimeoutExpired:
                print(label, "TIMEOUT", f"budget={seconds}s")


duplicates = ["NS-0100", "NS-0200", "NS-0100"]
print("duplicate order preserved:", scan(duplicates)[0] == track(duplicates)[0] == duplicates[:2])
for size in (50, 200, 800):
    ids = [f"NS-{n:04d}" for n in range(size)]
    old, comparisons = scan(ids)
    new, queries = track(ids)
    print(f"n={size} equal={old == new} list_comparisons={comparisons} set_queries={queries}")
    if RUN_LOCAL:
        measure(scan, ids)
        measure(track, ids)
if RUN_LOCAL:
    observe_timeout()
```

```python
def refund(price, fee):
    if type(price) is not int or type(fee) is not int:
        raise TypeError("whole cents required")
    if price < 0 or fee < 0:
        raise ValueError("cents cannot be negative")

def workflow(calculator, *, check_authority=True, write_notice=False):
    def decide(request, verified_order, notices):
        order = request["order_id"]
        if not isinstance(order, str) or not re.fullmatch(r"NS-[0-9]{4}", order):

        if check_authority and order != verified_order:

        return ("PROPOSE", amount)

    return decide


# Each row carries an independent expected outcome and its requirement.
# Unit rows take calculator arguments. Workflow rows take requested and verified IDs.
CASES = [

def evaluate(case, calculator, decide, missing_case):
    case_id, split, requirement, args, expected, critical = case
    row = {"id": case_id, "split": split, "requirement": requirement,
           "inputs": args, "expected": expected, "critical": critical}
    if case_id == missing_case:
        return dict(row, status="MISSING", actual=None, performed=False)

    if requirement in ("calculate-cents", "floor-zero", "reject-negative"):
        try:
            actual = calculator(*args)
        except (ValueError, TypeError, ArithmeticError) as error:
            actual = type(error).__name__
            status = "PASS" if actual == expected else "RUNTIME_ERROR"
        else:
            status = "PASS" if type(actual) is type(expected) and actual == expected else "WRONG_ANSWER"
    else:
        order, scope = args
        request = {"order_id": order, "price": 1000, "fee": 200}
        before = request.copy()
        notices = []
        try:
            actual = decide(request, scope, notices)
        except (ValueError, TypeError, ArithmeticError) as error:
            actual = type(error).__name__
            status = "RUNTIME_ERROR"
        else:
            valid_output = type(actual) is tuple and len(actual) == 2 and type(actual[1]) is int
            status = "PASS" if valid_output and actual == expected else "WRONG_ANSWER"
        if notices or request != before:
            return dict(row, status="UNAUTHORIZED_EFFECT", actual=actual, performed=True,
                        observed_effects=notices, input_changed=request != before)
    return dict(row, status=status, actual=actual, performed=True)


def assess(name, calculator, decide, review, missing_case=None):
    rows = [evaluate(case, calculator, decide, missing_case) for case in CASES]
    known = [row for row in rows if row["status"] != "MISSING"]
    observed = [row for row in known if row["status"] != "RUNTIME_ERROR"]
    failures = [row for row in known if row["status"] != "PASS"]
    hits = {row["requirement"] for row in observed}
    critical = [row["id"] for row in failures if row["critical"]]
    pending = [row["id"] for row in rows if row["status"] == "MISSING"]
    if not review:
        pending.append("human-review-receipt")
    decision = "BLOCK" if failures else "REVIEW" if pending else "PASS"
    by_split = {}
    for split in ("unit", "holdout", "contract", "integration"):
        group = [row for row in rows if row["split"] == split]
        by_split[split] = {"passed": sum(row["status"] == "PASS" for row in group), "planned": len(group)}
    return {"candidate": name, "syntax": "valid program", "planned": len(rows),
            "passed": len(known) - len(failures), "evaluated": len(observed),
            "coverage": len(hits), "requirements": len(REQUIREMENTS), "by_split": by_split,
            "security": {"unauthorized": next(row["status"] for row in rows if row["id"] == "I-02"),
                         "no_effects": next(row["status"] for row in rows if row["id"] == "C-01")},
            "critical": critical, "pending": pending, "review_receipt": review,
            "decision": decision, "cases": rows}


def compare(baseline, candidate):
    before = {row["id"]: row["status"] for row in baseline["cases"]}
    after = {row["id"]: row["status"] for row in candidate["cases"]}
    if before.keys() != after.keys():
        raise ValueError("compare the same frozen case IDs")
    paired = [key for key in before if "MISSING" not in (before[key], after[key])]
    return {"paired": len(paired), "baseline_passed_pairs": sum(before[key] == "PASS" for key in paired),
            "regressions": [key for key in paired if before[key] == "PASS" and after[key] != "PASS"],
            "fixes": [key for key in paired if before[key] != "PASS" and after[key] == "PASS"],
            "unpaired": [key for key in before if key not in paired]}


receipt = {"status": "teaching fixture only", "rubric": "review-v1"}
repaired = workflow(refund)
runs = [
    assess("previous", previous_refund, workflow(previous_refund), receipt),
    assess("regressed", refund, workflow(refund, check_authority=False), receipt),
    assess("extra-effect", refund, workflow(refund, write_notice=True), receipt),
    assess("repaired", refund, repaired, receipt),
    assess("review-missing", refund, repaired, None),
    assess("capture-missing", refund, repaired, receipt, missing_case="I-02"),
]
comparisons = {row["candidate"]: compare(runs[0], row) for row in runs[1:]}
for row in runs:
    held = row["by_split"]["holdout"]
    print(f"{row['candidate']}: {row['passed']}/{row['planned']} tests, "
          f"{held['passed']}/{held['planned']} held-out, {row['coverage']}/{row['requirements']} requirements, "
          f"{row['decision']}")
    details = [f"{case['id']}={case['status']}" for case in row["cases"]
               if case["status"] not in ("PASS", "MISSING")]
    if details or row["pending"]:
        print(" ", ", ".join(details + [f"{item}=MISSING" for item in row["pending"]]))
paired = comparisons["regressed"]
print("paired:", paired["paired"], "fixes:", paired["fixes"], "regressions:", paired["regressions"])
if EXPORT_JSON:
    print(json.dumps({"spec": SPEC, "runs": runs, "comparisons": comparisons, "resource": RESOURCE},
                     sort_keys=True))
```

## Evaluation Metrics

**Pass rate** asks how many planned tests passed. When evidence is missing, also publish the number of evaluable tests. **Requirement coverage** asks whether the test plan gathered usable evidence for each named requirement. **Statement coverage** asks which executable statements ran. **Branch coverage** asks whether each possible outcome of a decision was taken. A fee-floor implementation using a conditional needs both below-floor and above-floor cases. Reaching the final return can give statement credit while leaving a branch untested. Code coverage tools are useful for finding gaps. The lab computes requirement coverage from explicit case links.

**Mutation testing** deliberately introduces a small bug and asks whether the suite notices. For instance, changing equality behavior at the fee boundary tests whether that boundary has a sensitive expectation. Exclude equivalent mutations because no permitted observation distinguishes them. A failing test catches, or kills, a mutant. The off-by-one candidate in D was caught by the zero-fee check after surviving the other properties.

**Pass@k** measures whether at least one of k candidate samples solves a task under a fixed generation and test protocol. In a toy sample of four candidates with one correct answer, picking two without replacement leaves six possible pairs. Three contain only incorrect candidates. Subtract three out of six from one to get 0.5. HumanEval uses this combinatorial calculation per task from n samples with c fully passing candidates, then averages across tasks. Use n at least k, treat zero possible all-fail groups as zero probability, and record the model, prompt, decoding, sampling and test protocol. A pass@k estimate applies to comparable samples under that protocol. Repeated duplicates, shared failures, curated candidate sets and exposed holdouts limit what it says about a model. [HumanEval paper](https://arxiv.org/abs/2107.03374)

### Calculate the denominators

Execution success counts calls that completed with a gradeable result, including a wrong answer. A prescribed exception matched by the oracle is a completed case. The operational log below has three gradeable results in five attempts. One times out and one crashes. The security denominator counts completed, planned security probes here. Repeated-test flakiness counts checks that changed verdict per repeated check under the same declared conditions. Investigate environment, test state and model sampling before attributing instability to code. The comb function counts unordered choices. For example, comb(4, 2) counts the six possible pairs.

[Open Python Editor](https://www.online-python.com/)

```python
from math import comb

samples = {
    "refund": ["FAIL", "PASS", "FAIL", "FAIL"],
    "order-id": ["PASS", "FAIL", "PASS", "FAIL"],
}
k = 2
scores = []
for task, outcomes in samples.items():
    n = len(outcomes)
    failures = outcomes.count("FAIL")
    all_fail = comb(failures, k)
    possible = comb(n, k)
    score = 1 - all_fail / possible
    scores.append(score)
    print(f"{task} pass@{k}: 1 - {all_fail}/{possible} = {score:.3f}")
print(f"mean pass@{k}: {sum(scores) / len(scores):.3f}")

attempts = ["PASS", "WRONG_ANSWER", "PASS", "TIMEOUT", "RUNTIME_ERROR"]
gradeable = sum(status in ("PASS", "WRONG_ANSWER") for status in attempts)
security = ["PASS", "WRONG_ANSWER"]
repeated = {"fixed": ["PASS", "PASS"], "unstable": ["PASS", "FAIL"]}
flaky = sum(len(set(outcomes)) > 1 for outcomes in repeated.values())
before = {"floor": "FAIL", "authorize": "PASS", "format": "PASS"}
after = {"floor": "PASS", "authorize": "FAIL", "format": "PASS"}
previous_passes = [key for key, status in before.items() if status == "PASS"]
regressions = sum(after[key] == "FAIL" for key in previous_passes)
print(f"execution success: {gradeable}/{len(attempts)}")
print(f"test pass: {attempts.count('PASS')}/{len(attempts)} planned")
print(f"security failures: {security.count('WRONG_ANSWER')}/{len(security)} completed probes")
print(f"flaky tests: {flaky}/{len(repeated)} repeated tests")
print(f"regressions: {regressions}/{len(previous_passes)} previously passing paired tests")
```

## Evaluation Dimensions and Code Review

| Code quality dimension | Example evidence of a pass | Example failure | Method and limit |
| --- | --- | --- | --- |
| Syntax and compilation | A refund function parses and compiles under the target Python version. | The definition has a missing colon or a return appears at module scope. | Parse and compile known fixtures. Neither stage exercises the function. |
| Functional correctness | A 1,200-cent price with a 200-cent fee returns 1,000. | It returns 1,400. | Compare with a versioned oracle. Each observed result covers one case. |
| Test coverage | Each required behavior has an independently observed case, including denial. | Only normal approved requests ran. | Trace cases to requirements and inspect branch coverage. Executed lines do not prove strong assertions. |
| Edge cases | A fee one cent above the price returns zero. | The amount becomes negative. | Pick values on both sides of boundaries. The chosen boundaries require review. |
| Robustness | A Boolean fee raises the declared error. | It is treated as 1 cent. | Run malformed contract cases in a controlled runner. The fixture covers only selected types. |
| Security | An unverified order is denied without further action. | The order gets a proposal. | Pair static review with independently authorized denial and effect checks. Both have scope limits. |
| Reliability | The same fixed inputs produce the same result over repeated equivalent runs. | The verdict flips without a contractual reason. | Repeat and retain raw results. A small sample gives limited evidence about rare failures. |
| Performance | The approved workload stays inside its time and memory budgets. | Larger inputs exceed the worker budget. | Measure representative sizes and record the runner. Local microbenchmarks cannot predict tail latency in production. |
| Maintainability | A reviewer can identify the policy rules in one obvious place. | Two copies of the rule disagree at a boundary. | Examine the diff and explain a future edit. Some judgments depend on repository conventions. |
| Integration | The trusted order match and calculator work together. | Correct cents are proposed for a different order. | Run with surrounding components or explicit test doubles. Assess production infrastructure separately. |
| Regression safety | The matched baseline denial still passes after the fee fix. | A previously passing denial now fails. | Compare frozen IDs and track missing pairs. A changed oracle needs its own review. |
| Specification adherence | The output is a typed decision and the recorder stays empty. | The output is correct and a diagnostic message is emitted. | Review the diff and observe interfaces and effects. A fake recorder covers its own seam. |

Use a review record with the candidate digest, repository version, reviewer role, finding, severity, evidence and disposition. Reviewers independently mark **Accept**, **Needs revision**, or **Evidence missing** per dimension. A critical disagreement stays unresolved until a separate reviewer adjudicates it against the approved specification. Calibrate with one clearly acceptable example and one clearly unacceptable example before comparing real patches. The following notes are illustrative.

| --- | --- | --- |

## Knowledge Check

- A snippet parses and compiles, then returns a wrong value. Which stage supplies the evidence of failure?
- A trusted child exceeds 0.25 seconds. What outcome do you report, and what evidence would distinguish worker startup delay from slow candidate behavior?
- You sample four candidates and two are fully correct on the same task. What is pass@2 under the stated protocol? Why would a strong result still need review?

## Knowledge Check Answers

- The functional test supplies a wrong-answer result. Syntax, compilation and execution all succeeded for this case.
- Record TIMEOUT with the budget, runner version and stage. Measure a known fast control under the same runner, repeat, and inspect where time was spent before blaming the candidate.
- There is one all-fail pair out of six. Pass@2 is five sixths. The estimate depends on the samples, task set, tests and protocol. A release also needs integration, security and review evidence.

## Common Mistakes

- Treating one public example as a specification. Write testable requirements and hold out meaningful edge cases.
- Turning missing outcomes into scored zeros. Record where execution stopped and publish coverage.
- Equating a static warning or clean scan with a security verdict. Check runtime authorization and effects in an approved setting.
- Comparing runs that used different cases, budgets or dependency versions. Make the experiment comparable before interpreting a change.
- Giving a high pass rate authority to waive a critical defect. Retain severity and authorization checks as separate gates.
