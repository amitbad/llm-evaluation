## What You Will Learn

- Read a saved fee reply as JSON and identify a broken record or a record with the wrong overall shape.
- Check required fields, distinguish a missing value from an explicit null, and test allowed choices, types, and ranges.
- Check the format version first and verify that fields agree with one another.
- Compare a usable reply with the approved fee policy and decide what to do with an invalid or unscorable result.
- Build a small set of saved tests with known outcomes and run the same checks on every case.

## Why This Lesson Matters

Imagine the same fee printed in two boxes on a bank form. One box says the customer owes a fee. The other says the amount is zero. The amounts may be legible and every box may be filled in, but the teller still needs to stop and find out which box is right.

A Harbor Leaf Bank app has a similar problem. It asks its assistant to return a record it can use to display a Standard Savings fee. For a customer with ₹4,999, the approved monthly fee is ₹100. The app receives a record showing “fee due” with zero rupees. Before showing it to the customer, the app needs to check whether the record can be read, whether the fields make sense together, and whether the claim agrees with the policy.

The bank, policy, records, and judgments are fictional. Allow about 4.5 hours for the demonstrations, seven short Python activities, and independent practice.

## Beginner Explanation

### 1. Start with the format a computer can read

Imagine you have to copy the fee from “You’ll pay one hundred rupees each month.” You can read that sentence, but a program would have to work out which words tell it the amount. Give the program a labelled box instead. In `{"amount_rupees": 100}`, the quotation marks mark the field name, the colon connects the name and value, and the braces enclose the record.

This text format is **JSON**. The app’s request for a predictable record is a request for **structured output**. When Python reads the JSON text and turns it into a value it can work with, it is **parsing**. For this example, the result is a **dictionary**, Python’s collection of named values. Leaving off the closing brace makes the text unreadable as JSON. That’s a parsing error.

Try putting square brackets around the whole record. In JSON, the brackets make an **array**, a list of values. Python can read that JSON as a list containing one dictionary. The fee screen expects just the dictionary, so it should check the overall shape before it tries to read a named field.

### 2. Agree on what belongs in the record

Suppose the app receives the status “needs review” and an amount of `null`. The reply explicitly says there’s no amount it can give. If the amount box is absent, the app can’t tell whether the assistant deliberately left it unknown or simply forgot the box.

Write the rules the app expects in one place. This agreement about a record’s shape, fields, and values is its **schema**. Checking a record against those rules is **schema validation**. The bank’s practice agreement uses three fields, all required.

- **Version.** `schema_version` must be the whole number 1. Check the version before interpreting the other fields. A later format might store paise instead of rupees, so an unfamiliar version goes for review.
- **Status.** `status` must be one of `fee_due`, `no_fee`, or `needs_review`. This closed set of choices is called an **enum**.
- **Amount.** `amount_rupees` must be a whole number from 0 to 1000 inclusive, or `null`. That makes the field **nullable** even though its name is required. The range is a made-up limit for the app’s record format. It does not set the bank’s actual fee.

A value’s **type** tells the program what kind of value it is. `100` is a number, `"100"` is text, and `true` is a yes-or-no value called a **boolean**. A format that requires a whole number should catch the other two. In Python, JSON `null` becomes `None`, and JSON `true` becomes `True`. Use an exact integer type check in this lab because Python also treats booleans as a kind of integer in some checks.

### 3. Ask whether the fields agree

Put a valid status of `fee_due` next to a valid amount of 0. Each field satisfies its own rule, but together they contradict the definition of “fee due.” The app needs one more check.

When the status is `fee_due`, the amount must be greater than zero. When it is `no_fee`, the amount must be zero. When it is `needs_review`, the amount must be null. A rule that must hold across fields is a **cross-field invariant**. Try changing only the status from `fee_due` to `no_fee` while the amount is 0. The fields now agree. The app still needs the customer’s balance and the approved policy to decide whether zero is correct.

### 4. Check the claim against the evidence

Keep the record at version 1 with a positive amount of 80 and a status of `fee_due`. The agreed format can represent this claim. Now read the bank’s approved policy for the exercise, SV-2 §2 (section 2). On July 15, 2026, Standard Savings had a ₹5,000 minimum, and a ₹100 monthly fee applied below that minimum. At exactly ₹5,000, no below-minimum fee applied. With a verified balance of ₹4,999, the claim of ₹80 is wrong.

The last check compares the claim with a rule for the actual task. This is a **business rule** check. This lab supplies the applicable policy and the verified balance separately from the reply. A balance claimed by the assistant would be another piece of output to check.

When there’s a broken or inconsistent record, keep the failure reason and hold the reply back from the fee screen. A business mismatch also calls for review before showing a charge. A reply with missing policy evidence may be readable and usable in shape, but its claim still needs review. A timeout gives you no reply to check. Keep these outcomes separate so the team can tell which part of the app to investigate. The practice checker is scoped to saved records and the July policy it was given.

## Worked Demonstration

### Example 1. Read one fee record

**User question.** “What’s the monthly Standard Savings fee at ₹4,999 on July 15?” Check that the saved reply can be read as one fee record.

**Approved reference.** The app expects one JSON object. SV-2 §2 specifies a ₹100 monthly fee at that balance.

**Actual LLM response.** The saved text is `{"schema_version": 1, "status": "fee_due", "amount_rupees": 100`.

**Assessment.** Find the opening brace and look for its closing partner. It’s missing. Parsing stops, so you can’t read any field from a reliable record. Add a closing brace to a copy. Python can now read it as a dictionary. Try enclosing the entire repaired record in square brackets. Python still reads the text, and the result is now a list.

**Failure classification.** Hold the original reply for a parsing error. Mark the array variant as the wrong shape. A successful parse only gets you to the point where you can start checking the fields.

### Example 2. Compare a missing field with a null field

**User question.** “Can you confirm my fee?” The app hasn’t verified the balance. It wants a record that can represent that gap.

**Approved reference.** Version 1 requires the amount field on every reply. For `needs_review`, its value must be null.

**Actual LLM response.** The saved reply is `{"schema_version": 1, "status": "needs_review"}`.

**Assessment.** Read the record as JSON and confirm it’s one object. The status is allowed. Now check whether the amount field exists. It doesn’t, so the record fails the schema. Add `"amount_rupees": null` to a copy. The field is now present, and the status and value agree. Try changing null to 100. The number fits the range, but the pair is inconsistent.

**Failure classification.** Report a missing field in the original and a cross-field failure in the 100-rupee variant. The null version describes an unresolved case. Keep it in review until the balance and applicable policy can be verified.

### Example 3. Compare a usable record with policy

**User question.** “What fee applies at a Standard Savings balance of ₹4,999 on July 15?” The app has independently verified the balance.

**Approved reference.** Version 1’s format permits the status `fee_due` and a positive whole-rupee amount up to 1000. SV-2 §2 requires ₹100 per month at this balance.

**Actual LLM response.** The assistant returns `{"schema_version": 1, "status": "fee_due", "amount_rupees": 80}`.

**Assessment.** Parse the reply and check its shape and version. All fields are present. The status is allowed, 80 is in range, and the positive amount agrees with the status. Now compare the fee with the applicable policy. The balance is one rupee below the minimum, so the expected fee is ₹100. Change 80 to 100 in a copy. The first checks still pass, and the policy check now agrees.

**Failure classification.** Record the original as a business mismatch. Keep the policy excerpt and verified balance with the example. This test supports a verdict for this record on this date. It gives little evidence about how the assistant will handle another account or policy.

### Step 1 — Read JSON text

Start with one record containing an amount. The amount is written inside a string, which is a piece of text. The outer single quotes tell Python where the JSON text starts and ends. The inner double quotes belong to the JSON field name. The `=` sign stores the text under the name `raw`.

`import json` makes Python’s built-in JSON tools available. `json.loads(raw)` reads the text stored in `raw`. Python tries the indented lines under `try`. If the JSON reader reports `JSONDecodeError`, the `except` block handles that specific error. Copy the block and click **Run**.

```python
import json

raw = '{"amount_rupees": 100}'
try:
    record = json.loads(raw)
    print("Read:", record)
except json.JSONDecodeError:
    print("PARSE ERROR")
```

```text
Read: {'amount_rupees': 100}
```

The printed value uses Python’s dictionary display. Its single quotes show how Python displays the field name after reading it.

**Experiment.** Remove the closing `}` inside the text, keeping the outer quotes. Run again.

```text
PARSE ERROR
```

The incomplete JSON can’t be read. Python follows the error branch instead of printing a record.

**Checkpoint.** Does the original result verify ₹100? It verifies that the text can be read. You still need the customer’s applicable policy.

### Step 2 — Check the overall shape before reading a field

An app that wants one dictionary should check the shape before asking for its amount. `isinstance(record, dict)` asks whether the value Python read is a dictionary. `if` runs its indented lines when that check succeeds. `else` handles the other outcome.

Copy the block and click **Run**. Both versions of this activity use deliberately readable JSON.

```python
import json

raw = '{"amount_rupees": 100}'
record = json.loads(raw)

if isinstance(record, dict):
    print("Shape: one record")
else:
    print("SHAPE ERROR: expected one object")
```

```text
Shape: one record
```

The braces gave Python a dictionary, so it takes the first branch.

**Experiment.** Replace the value of `raw` with `'[{"amount_rupees": 100}]'`. Run again.

```text
SHAPE ERROR: expected one object
```

The square brackets give Python a list, even with only one item. The shape check stops it before any field lookup.

**Checkpoint.** Did parsing fail in the experiment? Python successfully read a list. The app’s requirement for one object is what failed.

### Step 3 — Distinguish null from a missing field

A reviewer needs to know whether the reply reported an unknown amount or omitted the field. `"amount_rupees" not in record` checks whether that field name is missing. `record["amount_rupees"]` reads the value only after the first condition rules out a missing field. `elif` means “otherwise, check this condition,” and `is None` checks for Python’s value representing JSON null.

Copy the block and click **Run**.

```python
import json

raw = '{"status": "needs_review", "amount_rupees": null}'
record = json.loads(raw)

if "amount_rupees" not in record:
    print("SCHEMA ERROR: missing amount_rupees")
elif record["amount_rupees"] is None:
    print("Amount: present, unknown")
else:
    print("Amount:", record["amount_rupees"])
```

```text
Amount: present, unknown
```

The amount field exists. The value explicitly records that the amount is unknown.

**Experiment.** Change `raw` to `'{"status": "needs_review"}'` and run again.

```text
SCHEMA ERROR: missing amount_rupees
```

The first check finds that the key is absent. It reports the missing field before attempting to read a value.

**Checkpoint.** Why keep these outcomes separate? A null can be allowed by the format. A missing required field means the app never received the box it asked for.

### Step 4 — Check the version, status, and amount

Check version 1 before interpreting its fields. `type(amount) is int` checks for a Python whole number, including zero but excluding booleans. `and` requires both checks to succeed, so Python tests the range only after it knows the value is an integer. `0 <= amount <= 1000` includes both endpoints. The parentheses around the three status strings keep them together as a group of allowed values.

Copy the block and click **Run**. These examples supply all three required fields so you can focus on the values.

```python
import json

raw = '{"schema_version": 1, "status": "fee_due", "amount_rupees": "100"}'
record = json.loads(raw)
version = record["schema_version"]

if type(version) is int and version == 1:
    status = record["status"]
    amount = record["amount_rupees"]
    print("Status allowed:", status in ("fee_due", "no_fee", "needs_review"))
    print("Amount allowed:", amount is None or (type(amount) is int and 0 <= amount <= 1000))
else:
    print("SCHEMA ERROR: unsupported version")
```

```text
Status allowed: True
Amount allowed: False
```

The status is in the allowed group. The amount is text because the JSON quotes surround it. The `or` condition accepts null by itself. Otherwise it requires the amount to pass both numeric checks.

**Experiment.** Remove the quotes around the JSON value `"100"` in `raw`. Keep the quotes around the field name. Run again.

```text
Status allowed: True
Amount allowed: True
```

Python now reads an integer and checks that it’s in range. Its printed appearance alone wouldn’t tell you whether the original was a number.

**Checkpoint.** If the value were JSON `true`, would it pass? Python would read `True`. Its exact type is a boolean, so the numeric branch would reject it.

Use two cases whose records passed the earlier checks. Compare an amount of 100 with what the bank charges at two different balances. ### Step 7 — Put each failure in the right place

Run all the checks in a function, a named block that Python can run for each case. `def check_reply(raw, balance):` gives names to two inputs. Each `return` ends the check for that case and hands the first outcome back to the reporting loop. Fixing that first problem may reveal another. The loop prints one outcome per case.

A balance of `None` means the trusted balance was unavailable. A raw reply of `None` means the request returned no text. Python treats them separately because one leaves an unresolved fact while the other leaves no reply to check. In the schema checks, `!=` means “is different from.” Use `not (...)` to reverse the outcome of the condition inside the parentheses. This lab version checks required fields and ignores extra fields. Its JSON parser is used with the supplied examples. A stricter application may need to reject duplicate field names and nonstandard values such as `NaN`, which Python’s default reader can accept.

Copy the full block and click **Run**.

```python
import json


def check_reply(raw, balance):
    if raw is None:
        return "UNSCORABLE: no reply"
    try:
        record = json.loads(raw)
    except json.JSONDecodeError:
        return "PARSE ERROR"
    if not isinstance(record, dict):
        return "SHAPE ERROR: expected one object"

    if "schema_version" not in record:
        return "SCHEMA ERROR: missing schema_version"
    version = record["schema_version"]
    if type(version) is not int or version != 1:
        return "SCHEMA ERROR: unsupported version"
    for field in ("status", "amount_rupees"):
        if field not in record:
            return "SCHEMA ERROR: missing " + field

    status = record["status"]
    amount = record["amount_rupees"]
    if status not in ("fee_due", "no_fee", "needs_review"):
        return "SCHEMA ERROR: unknown status"
    if amount is not None and not (type(amount) is int and 0 <= amount <= 1000):
        return "SCHEMA ERROR: amount type or range"

    if status == "needs_review":
        if amount is not None:
            return "SCHEMA ERROR: status and amount disagree"
    elif (
        amount is None
        or (status == "fee_due" and amount == 0)
        or (status == "no_fee" and amount != 0)
    ):
        return "SCHEMA ERROR: status and amount disagree"

    if balance is None:
        return "REVIEW: no verified balance"
    if status == "needs_review":
        return "BUSINESS MISMATCH: expected a fee answer"

    if balance < 5000:
        expected = 100
    else:
        expected = 0
    if amount != expected:
        return "BUSINESS MISMATCH: wrong fee"
    return "PASS: agrees with July policy"


cases = [
    ("A", '{"schema_version": 1, "status": "fee_due", "amount_rupees": 100}', 4999),
    ("B", '{"schema_version": 1, "status": "no_fee", "amount_rupees": 0}', 5000),
    ("C", '{"schema_version": 1, "status": "needs_review"}', None),
    ("D", '{"amount_rupees": 100', 4999),
    ("E", '[]', 4999),
    ("F", '{"schema_version": 1, "status": "fee_due", "amount_rupees": true}', 4999),
    ("G", '{"schema_version": 1, "status": "fee_due", "amount_rupees": 0}', 4999),
    ("H", '{"schema_version": 1, "status": "fee_due", "amount_rupees": 80}', 4999),
    ("I", '{"schema_version": 1, "status": "needs_review", "amount_rupees": null}', None),
    ("J", None, 4999),
]

for case_id, raw, balance in cases:
    print(case_id, check_reply(raw, balance))
```

```text
A PASS: agrees with July policy
B PASS: agrees with July policy
C SCHEMA ERROR: missing amount_rupees
D PARSE ERROR
E SHAPE ERROR: expected one object
F SCHEMA ERROR: amount type or range
G SCHEMA ERROR: status and amount disagree
H BUSINESS MISMATCH: wrong fee
I REVIEW: no verified balance
J UNSCORABLE: no reply
```

A and B agree with the policy on opposite sides of its fee rule. H passes the earlier checks and reaches a business mismatch. I can represent its unknown amount in the schema, so its next step is review. J never reaches parsing because it has no reply.

**Experiment.** In row H only, change `schema_version` from `1` to `2`. Keep the amount at 80 and run again.

```text
A PASS: agrees with July policy
B PASS: agrees with July policy
C SCHEMA ERROR: missing amount_rupees
D PARSE ERROR
E SHAPE ERROR: expected one object
F SCHEMA ERROR: amount type or range
G SCHEMA ERROR: status and amount disagree
H SCHEMA ERROR: unsupported version
I REVIEW: no verified balance
J UNSCORABLE: no reply
```

H now stops at the version check. The checker needs a rule for version 2 before it can interpret its amount. The other rows are unchanged.

**Checkpoint.** Why keep the three outcomes in H, I, and J separate? H needs a compatible record or a supported version. I needs trusted evidence. J needs an investigation into why the app got no reply.

## Common Mistakes

- **Reading fields before checking the shape.** A valid JSON list or null can still be unusable as a fee record.
- **Treating missing, null, and zero as interchangeable.** Check whether the field exists, then check what the value means in the agreed format.
- **Checking fields in isolation.** Test incompatible pairs as well as values outside the allowed choices or range.
- **Equating a valid form with a correct charge.** Compare the claim with the policy and facts supplied independently.
- **Counting every error as a wrong fee.** Report missing replies, parsing errors, schema problems, business mismatches, and unresolved evidence separately.
