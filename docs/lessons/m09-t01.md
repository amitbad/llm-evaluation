## Beginner Explanation

### Start with the saved reply

“Can I get a refund after 45 days?” is a question, while “Refunds are available within 90 days” is a particular reply. Give the question a stable **case ID** and each saved reply a stable **response ID**. A case contains the task and the references needed to check it. The **evaluation input** is the record you actually hand to a grader. An **evaluator** applies one rule and returns an **evaluation result**. The **runner** sends cases to evaluators and the **report** shows their results and summaries.

Two scripts can expect the same text under different argument names. One might call it `actual` and another `answer`. Even if you manage to run both, `False` could mean a valid failing verdict or a script’s fallback after an exception. A result without IDs or a scoring version is hard to join back to the original capture. Take the result shapes above and predict which values Python would treat as true. A nonempty dictionary and even the string `"FAIL"` are truthy. Their truthiness says nothing about evaluation success.

A **contract** says which fields to send and how to read what comes back. Put the question and answer under stable names. Attach both IDs when you return a result. Record how the metric was computed and what failure means. This gives different implementations a common format without forcing the metrics to agree.

### Choose the fields for one neutral input

Start with `case_id`, `response_id`, `question`, and `answer`. These required fields identify the task and reply. An empty captured answer can be graded as empty. A missing answer field gives the runner no input. Optional fields carry evidence for particular graders.

- `expected_answer` gives a reviewed text reference. Exact match needs it. Keyword checks can run without it.
- `context` holds ordered supplied passage IDs in this fixture. The source manifest resolves those IDs to versioned text.
- `expected_sources` lists reviewed reference IDs, while `citations` records the references attached to the actual reply. An explicit empty list means the reviewer recorded no citations. A missing list means there is no annotation to inspect.
- `required_words` and `metadata` carry rule-specific inputs. Metadata can store segment, capture information, and an annotated deadline.

A **schema** specifies the expected types and fields. An input schema checks that `answer` is text. A grading rule checks whether the text meets a requirement. Skip a grader that lacks its optional reference, continue the other checks, and report the gap. If a required ID is missing or duplicated, the lab stops at preflight, the validation step before grading. This prevents rows from being attributed to the wrong reply.

### Make every outcome readable

Use `case_id` and `response_id` to join back to the capture. Use `evaluator_id` and `evaluator_version` to identify the rule and implementation. The report should carry dataset, source, and capture versions and the rule’s effective settings. These details record **provenance**, where the result came from and how it was made.

Put three cards on the table. The first says the saved text differs from the reference. The second says the keyword script reported three matches out of two terms. The third says no reviewed text reference exists.

The first card gets `OK`, a verdict of `False`, and score `0`. A check ran and found a real mismatch. The second gets `ERROR` because the reported measurement is impossible. The third gets `SKIPPED` because exact match needs a reference it was never given. A reader can now tell which reply failed and which checks need engineering or data work. Both non-OK outcomes have `None` for `passed` and `score`. Keep a human-readable `reason`, a list of `evidence`, and an `error` code on error rows. An unknown requested evaluator ID can have no resolved version, while the requested ID still identifies the configuration problem.

A result shape also needs a **metric definition**. A keyword score of `0.5` means one of two requested terms appeared. Higher is better under that rule. A latency score of 120 ms measures time and lower may be better. Exact match is binary, either zero or one. A reviewer may use categories such as “supported” and “unsupported,” with no numeric score. If you extend the contract for these kinds of metrics, declare the scale, unit, direction, and threshold before aggregating. The lab schema intentionally accepts only finite 0–1 scores on valid deterministic rows. It never treats Booleans, NaN, or out-of-range numbers as scores.

### Translate an evaluator without changing its meaning

Exact match compares the untouched strings. Normalized match can ignore changes the rubric explicitly allows. The lab folds case, collapses whitespace, and removes trailing periods. The original reply stays in the record. Keyword coverage checks required whole tokens. It can pass a false statement that uses the right words. Citation ID validation checks the expected supplied references. Whether the passages actually support the claims requires a separate claim-level review.

You can preserve a legacy check and write an **adapter**, a small function that translates its inputs and outputs. For example, pass the neutral `expected_answer` and `answer` into the Boolean function. Convert `True` to score 1 and pass `True`. For a count result, divide matched by total only after validating the counts. If a field is renamed, accept the documented alias deliberately and version that adapter change. A dictionary lookup of a saved human or large language model (LLM) judgment can replay a decision, but it cannot recreate the reviewer’s reasoning. Keep its rubric and judge version alongside the saved evidence.

Test **parity**, agreement on the same exact case and metric, before swapping implementations. If both count two terms out of two with the same token rules, both should report 1.0. If one ignores capitalization and the other checks exact text, a lowercase reply can pass one and fail the other. That difference is intentional. Record it instead of comparing the scores as if the rules were identical. A registry maps evaluator names to implementations and versions. The runner validates the dataset, looks up each requested evaluator, records its result or error, then continues the remaining checks.

### Calculate a report before choosing a tool

Take four planned checks for one evaluator. The first passes, the second fails, the third times out, and the fourth lacks a reference. Pass rate is `1/2` because only two checks produced valid verdicts. Coverage is `2/4` and the error rate is `1/4`. One was skipped. If the two valid scores are 1 and 0, their mean is `(1 + 0)/2 = 0.5`. If all checks are errors or skips, the pass rate is N/A. Keep the rows by case and by evaluator so a high keyword score cannot hide a critical refund finding. Count confirmed critical cases separately.

Northstar’s old scripts make it hard to tell which tool produced a result, what version ran, or what input left the team’s environment. Keep cases, labels, output formats, and evidence independent of any vendor. During a migration, map one frozen case into both interfaces, run matching definitions, and verify identity, errors, skips, and intended divergences before changing the default runner. The saved Test 11 walkthrough is a historical example of why this matters. It shows a case object with separate question, reply and retrieval fields, and describes timeouts that were represented as zero scores in that run. Treat timeouts as execution evidence in this lesson. The walkthrough does not establish how current framework versions handle them.

### Choose according to the work you need to do

If the job is to catch wrong dates in saved replies and keep a few checks repeatable in continuous integration (CI), a plain Python harness can be enough. A harness is the runner, fixtures, and report together. If the team needs experiment comparisons, trace inspection, human review queues, or many reusable metrics, a library or platform may save integration work. Compare the work it removes with the work it introduces. A hybrid can keep the authoritative evaluator contract and CI checks local while sending approved, minimized data to a specialized review workflow.

Product categories overlap. A Python evaluation library provides callable metrics or tests. A command-line tool runs a configuration or test matrix. A hosted platform may operate shared datasets or experiment records. An observability system collects traces and other measurements, called telemetry, from running applications. Human review workflows capture independent judgments and disagreements. RAG-focused metric suites concentrate on retrieval, evidence and generation. Treat these as capability categories and verify a tool’s actual fit. The repository’s historical tests include DeepEval and Ragas. The next chapter examines saved adapter records. This lesson compares generic approaches and makes no claims about current product features, prices or terms.

Ask which tasks a candidate supports. Verify deterministic rules, judge-based checks, RAG measures, dataset and experiment comparison, tracing, human review, and CI integration where required. Check reproducibility by replaying a known case with agreed versions on the intended operating system. A **lockfile** records the exact dependency versions to reinstall. Check runtime and training effort, deployment ownership, support costs and monitoring.

Check where evaluation records, telemetry, raw inputs, judge requests and backups go. Set a mandatory data boundary first. An unapproved external service fails Northstar’s boundary regardless of its weighted score. Verify data retention, credentials, redaction, approved endpoints, and whether the team can export records without losing IDs or versions. Hosted service costs can include computation, model calls, storage, or review seats. Local costs include setup, operational ownership and migration effort. A good memo names what was checked and who would validate what remains. Give a tied matrix to reviewers for a pilot rather than letting option names break the tie.

A **weighted matrix** multiplies each requirement’s importance by an illustrative fit rating, then adds the products. For example, Python gets ratings 5 for privacy-control fit, 2 for workflow fit, and 5 for ease of operation. With weights 2, 4, and 3, the total is `2×5 + 4×2 + 3×5 = 33`. A higher score indicates a stronger match to these assumptions. Apply mandatory constraints first. Recommend **ADOPT** for an eligible, verified approach, **PILOT** for a promising eligible approach that still has important unverified requirements, or **REJECT** if a mandatory constraint fails. This selection decision concerns the evaluation setup. Track model policy findings separately.

## Worked Demonstration

### Example 1. Three graders return three different shapes

**User question.** “How long do I have to request a refund?”

**Approved reference.** “Refunds within 30 days with a valid receipt.” Required terms are `30` and `receipt`. In this small example the authorized evidence list contains only `DOC-SHIPPING-02`.

**Actual LLM response.** Fictional capture, “Refunds within 30 days with a valid receipt. [DOC-REFUND-01]”

- `exact_match(expected, actual)` evaluates `expected == actual` and returns `False` because of the extra citation.
- `keyword_check(answer, required_words)` counts terms that appear as substrings and returns `{"matched": 2, "total": 2}`.
- `citation_check(answer, allowed_sources)` returns `"PASS"` whenever it finds `"[DOC-REFUND-01]"` in the answer. It deliberately ignores `allowed_sources`. It is a flawed teaching example.

**Assessment.** Predict what `bool(...)` would return for each raw output. The Boolean stays false, and both nonempty objects are truthy. Attach Q1 and R1 to all rows, then translate the first into `OK, 0, False` and the second into `OK, 1.0, True`. A valid source rule fails the citation here because the ID is outside the allowed list. The legacy string gives no evidence it checked the boundary.

**Failure classification.** Inconsistent shapes and a bad citation rule are separate defects. A field adapter fixes the first. Replace the citation rule and version it to fix the second.

### Example 2. Check the runner on three replies

**User question.** Three saved tasks ask where to find a receipt (Q2), where a warranty claim starts (Q4), and where to reset a password (Q5).

**Approved reference.** Q2 has “Download receipts in Orders.” Q4 has “Start a claim from your order.” Q5 has no reviewed text reference. Its required term is `sign-in`. The dataset and lab preserve separate response IDs for all three.

**Actual LLM response.** Q2 says “download   receipts in orders”. Q4 repeats its reference. Q5 says “Reset from the sign-in page.” These are fictional captures.

- **Q2.** Exact match returns an OK failure. Normalized match returns an OK pass. Keyword returns `2/2` in the legacy counts and 1.0 in the translated record. Hand-count `receipts` and `orders` to reproduce the value.
- **Q4.** Both text checks pass. Keyword returns `{"hits": 2, "total": 2}`. Version 1 expects `matched` and records ERROR. Version 2 accepts the documented alias and validates the resulting counts before scoring 1.0.
- **Q5.** The two text checks are SKIPPED. The independent token check runs and passes at 1.0.

**Assessment.** For exact match, Q4 passes and Q2 fails. Q5 has no text reference. Count one pass out of two valid verdicts and show that those verdicts cover two of the three planned cases. Normalized match passes both scored replies. For the keyword check, Q2 and Q5 pass while Q4 errors, giving `2/2` pass rate and `2/3` coverage. After the adapter repair, Q4 adds one pass and one valid execution, giving `3/3` for both measures. Compare Q2’s direct `2/2` token count with its adapter score of `1.0`. That is parity for the keyword rule, even though exact and normalized match disagree.

**Failure classification.** Q4 is an adapter error, Q5 lacks a reference for two checks, and Q2’s exact-match failure is a valid result for that rule. Preserve all three in the report.

### Example 3. Compare approaches under a mandatory boundary

**User question.** “What evaluation setup should we use for our saved support replies?”

**Approved reference.** Northstar requires local replay, portable results and no transfer to an unapproved external service. Use weights `2, 4, 3` for privacy-control fit, workflow fit, and ease of operation.

**Actual LLM response.** The saved fictional review memo recommends the hosted option because its illustrative score is 42.

- Python rates `(5, 2, 5)` for a weighted total of `33`. It meets the boundary and has completed the fixture trial.
- A local library rates `(4, 5, 3)` for `37`. Its proposed architecture meets the boundary in the example. Compatibility and telemetry checks still need a pilot.
- The hosted option rates `(5, 5, 4)` for `42`. Its strong privacy-control rating represents assumed controls. It still fails the actual approval requirement for this deployment.

**Assessment.** Compare only eligible options for the recommendation. The initial winner is the local library, so recommend PILOT. Raise the privacy-control weight alone from 2 to 7. Compute `58` for Python and `57` for the library. The hosted option’s `67` still cannot enter the eligible comparison. Python leads and earns ADOPT under the fictional criteria.

**Failure classification.** The memo treated preference points as proof of permission. Record the rejection reason before comparing weights, and include local replay, lockfile and platform checks, approved data paths, and migration effort in the decision.

### Step 3 — Adapt two legacy formats

One evaluator returns a Boolean and the other returns counts. A local adapter translates each. `type(x) is int` deliberately excludes Booleans. The range check prevents an impossible count from entering the report.

[Open Python Editor](https://www.online-python.com/)

```python
answer = "contact support"
words = ("contact", "support")
malformed = False
legacy_exact = answer == "contact support"
legacy_keywords = {"matched": 3 if malformed else sum(word in answer.split() for word in words),
                   "total": len(words)}

def adapt_count(result):
    hits, total = result.get("matched"), result.get("total")
    if type(hits) is not int or total != len(words) or not 0 <= hits <= total:
        return ("ERROR", None, None)
    return ("OK", hits / total, hits == total)

print("exact:", ("OK", int(legacy_exact), legacy_exact))
print("keywords:", adapt_count(legacy_keywords))
```

```text
exact: ('OK', 1, True)
keywords: ('OK', 1.0, True)
```

**Experiment.** Set `malformed` to `True`. Would three matches out of two describe a bad answer or a bad evaluator output?

```text

keywords: ('ERROR', None, None)
```

The impossible count produces an error with no score. The exact-match result still exists. The tuple here is a small preview of the full lab’s result record.

**Checkpoint.** Would changing the malformed count into zero preserve evidence? No. Zero is a legitimate score for zero matches and would hide the defect.

### Step 4 — Run evaluators by registered ID

A dictionary can store functions as values. The runner looks up each requested name before calling it. `str.casefold` removes case differences for this Latin-script example, and `f` strings place the result into the printed line.

[Open Python Editor](https://www.online-python.com/)

```python
def exact(case):
    return case["answer"] == case["expected_answer"]

def normalized(case):
    return case["answer"].casefold() == case["expected_answer"].casefold()

case = {"answer": "ORDERS", "expected_answer": "Orders"}
registry = {"exact": exact, "normalized": normalized}
requested = ("exact", "normalized")
for name in requested:
    evaluator = registry.get(name)
    if evaluator is None:
        print(f"{name}: ERROR unknown evaluator")
    else:
        print(f"{name}: OK passed={evaluator(case)}")
```

### Step 6 — Apply mandatory constraints before comparing scores

The numbers are fictional ratings for approaches. A larger effort-fit rating means easier for Northstar. `zip` pairs each rating with its weight. The sum of their products is the weighted score. An option that cannot meet the data boundary is rejected before choosing a winner.

[Open Python Editor](https://www.online-python.com/)

```python
privacy_weight = 2
weights = (privacy_weight, 4, 3)
options = (
    ("Python", (5, 2, 5), True),
    ("Local library", (4, 5, 3), True),
    ("Hosted service", (5, 5, 4), False),
)
eligible = []
for name, ratings, approved in options:
    score = sum(weight * rating for weight, rating in zip(weights, ratings))
    print(f"{name}: {score} {'eligible' if approved else 'REJECT'}")
    if approved:
        eligible.append((score, name))
print("Selected:", max(eligible)[1])
```

```text

Hosted service: 42 REJECT
Selected: Local library
```

### Step 7 — Keep evaluator versions in a portable report

The same capture is checked by exact and normalized rules. A function returns text in the form its version compares. `json.dumps` serializes Python values to JSON, a portable text format. `sort_keys=True` prints field names in a stable order.

[Open Python Editor](https://www.online-python.com/)

```python
import json

version = "1"
case = {"case_id": "Q2", "response_id": "R2",
        "expected_answer": "Download receipts in Orders.", "answer": "download receipts in orders"}

def prepare(text):
    return text if version == "1" else text.casefold().rstrip(".")

passed = prepare(case["answer"]) == prepare(case["expected_answer"])
report = {
    "dataset": "northstar-v1", "case_id": case["case_id"], "response_id": case["response_id"],
    "evaluator_id": "text-match", "evaluator_version": version, "status": "OK",
    "score": int(passed), "passed": passed,
    "reason": "Exact text" if version == "1" else "Ignore case and final periods",
    "evidence": [case["answer"], case["expected_answer"]], "error": None,
    "approach": "Python",
}
print(json.dumps(report, sort_keys=True))
```

### Run the versioned harness

The case validator checks IDs, types, optional annotation fields, and expected source references. The **registry** maps each requested name to a version and function. The runner unpacks the evaluator’s returned tuple as score, verdict, reason, and evidence. Returning `None` marks a skipped check. An exception or invalid tuple becomes ERROR. If the registry cannot resolve an ID, it records an error row and continues. `isfinite` rejects non-finite scores. The code preserves an exception’s class name without emitting raw provider messages.

Each evaluator in this fixture uses a 0–1 scale where higher scores are better under that evaluator’s declared rule. Exact, normalized, citation, and deadline checks use binary scores. Keyword uses the fraction of required whole terms found and passes only at 1.0. The tokenizer uses `re.findall` to collect words and keeps a hyphen between word groups. That lets `sign-in` remain one term. The report displays one column per evaluator and stores full result records. Per-evaluator pass rate and mean use OK rows. Coverage and error rate use all planned rows. Old results stay in an audit tuple of JSON snapshots. A tuple groups the immutable strings, and `json.dumps` captures the complete input and output record at the moment of the run. An in-memory snapshot demonstrates reproducible history.                     if (type(score) not in (int, float) or not isfinite(score) or not 0 <= score <= 1
                            or type(passed) is not bool or not isinstance(reason, str) or not reason
                            or not isinstance(evidence, list) or any(not isinstance(item, str) for item in evidence)):
                        raise ValueError("invalid result")
                    row = result(case, name, version, "OK", score, passed, reason, evidence)
            except Exception as exc:
                # Preserve the safe error class without printing raw provider messages.
                row = result(case, name, version, "ERROR", reason="Evaluator could not produce a valid verdict",
                             error=type(exc).__name__)
            rows.append(row)
    return rows

def fraction(n, d):
    return f"{n}/{d}" if d else "N/A"

def summarize(rows, name):
    group = [row for row in rows if row["evaluator_id"] == name]
    valid = [row for row in group if row["status"] == "OK"]
    errors = sum(row["status"] == "ERROR" for row in group)
    skipped = sum(row["status"] == "SKIPPED" for row in group)
    passed = sum(row["passed"] for row in valid)
    mean = f"{sum(row['score'] for row in valid) / len(valid):.3f}" if valid else "N/A"
    return (f"pass={fraction(passed, len(valid))} coverage={fraction(len(valid), len(group))} "
            f"error={fraction(errors, len(group))} skipped={skipped} mean={mean}")

options = (
    ("Python", (5, 2, 5), True, True),
    ("Local library", (4, 5, 3), True, False),
    ("Hosted service", (5, 5, 4), False, False),
)

def select(privacy, candidates=options):
    weights = (privacy, 4, 3)
    comparison = []
    for name, ratings, boundary_ok, pilot_complete in candidates:
        score = sum(weight * rating for weight, rating in zip(weights, ratings))
        decision = "REJECT" if not boundary_ok else "ADOPT" if pilot_complete else "PILOT"
        comparison.append((name, score, decision))
    eligible = [(score, name, decision) for name, score, decision in comparison if decision != "REJECT"]
    if not eligible:
        return comparison, ("none", "REJECT")
    best = max(score for score, _, _ in eligible)
    leaders = [(name, decision) for score, name, decision in eligible if score == best]
    return comparison, leaders[0] if len(leaders) == 1 else ("tie", "PILOT")

def label(row):
    if row["status"] != "OK":
        return row["status"]
    return "PASS" if row["passed"] else "FAIL"

def report(name, records, allow_alias, privacy, extra=()):

def replay(choice):

## Common Mistakes

- Counting errors as zero scores or allowing every nonempty result to pass.
- Treating a missing reference as an empty reference.
- Averaging incompatible metrics because their numbers share a range.
- Changing an evaluator version without keeping the original capture and scoring settings.
- Letting a weighted score override a data-boundary requirement.

## Lesson Summary and Next Step

Keep the case and response IDs stable, define what each evaluator receives and returns, and validate the output before aggregating. Check that equivalent metric definitions produce equivalent results across adapters. Use documented requirements and data boundaries to choose a tool, with a local replay that can verify the decision.
