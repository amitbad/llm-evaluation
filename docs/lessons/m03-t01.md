## Why This Lesson Matters

A customer with ₹4,999 in Harbor Leaf Bank’s Standard Savings account asks what fee applies on July 15, 2026. Now read “Monthly fee: ₹1000.” The same test still finds “100,” even though the fee is ten times too large. Make the rule stricter and another problem appears. A reply that says “You pay one hundred rupees each month” may fail an exact text check even though it communicates the approved fee.

## Beginner Explanation

### 1. Start with text you can compare

Suppose the bank asks for the fee in a fixed format so another program can read it. If the expected text is “Monthly fee: ₹100.” and the actual text is the same, a character-by-character check passes. That’s an **exact match**. A missing period or an extra space would make it fail. The check is **deterministic**, meaning the same text and rule give the same result each time.

An exact match makes sense if the period is part of the format the bank requires. If the customer simply wants a clear answer, both versions can convey the same fee. Decide which behaviour the check is measuring before treating a mismatch as a wrong answer.

### 2. Agree which differences can be ignored

A teammate types “  STANDARD   SAVINGS  ” in a field for the account name. It looks like the same account. You can trim the extra spaces at the ends, collapse repeated spaces inside, and make the comparison ignore capital letters. Applying agreed changes before comparing is **normalization**.

Do this only where the change preserves the information you need. For an account-name field, repeated spaces may be harmless. For a money field, removing every mark can change the value. “₹1.00” and “₹100” become the same text if you blindly delete the period.

Computers use a standard called **Unicode** to represent text characters. For example, the full-width letter “Ｓ” takes up more space on the page and has a different stored representation from “S.” Python’s Unicode normalization form called **NFKC** can turn that full-width letter into the ordinary one. It can also fold other characters, such as turning “²” into “2.” Apply it only when your field’s rules permit those changes. In the lab, you’ll try it on the account name. The fee reader uses its own separate format.

The bank may also accept “Standard Savings Account” as a name for the same product. An **alias** is another approved name for the same thing. Pick one **canonical name**, meaning the name you store as the standard, and map reviewed aliases to it. If a name is unfamiliar, leave it for review. A similar-looking product could carry different fees.

### 3. Find complete numbers, then read the claim

A **substring** is a piece of text that appears inside a larger string. “100” is a substring of “1000.” It also appears in “The fee is ₹80, not ₹100.” The substring check answers whether some characters occur. The fee question asks what the reply actually says the customer must pay.

A **regular expression**, or **regex**, describes a text pattern. A boundary in that pattern can help you find “100” as a separate number in the examples above. It keeps “100” inside “1000” from matching. The separate number still matches in “not ₹100.” A boundary test tells you where the number occurs, while the neighbouring words tell you what the reply claims.

If the bank asks for exactly one field such as “Monthly fee: ₹100.”, check the full format and read the digits as a Python integer, a whole number. Compare the resulting number with the approved 100 rupees. This is a **typed check** because it compares numbers after reading the text. The word “Monthly” in the agreed format establishes the time period. The pattern in this lesson accepts only whole, nonnegative rupee amounts in that format, with an optional final period. Natural customer replies outside the format still need a reviewer.

### 4. Test your checker with replies someone has already reviewed

Write a row for each saved reply before running a rule. Include the policy, the reply, and whether a reviewer says the reply gives the right monthly fee. Then add the rule’s result. A table like this is a **truth table** for your checks. It shows where the rule agrees with your expected judgments and where it gets them wrong.

Suppose a rule marks four replies correct and a reviewer agrees on two of them. Its **precision** is two out of four, or 50%. Precision asks how many of the rule’s passes were deserved. If the reviewer found three correct replies in all, the rule’s **recall** is two out of three, or about 66.7%. Recall asks how many of the correct replies the rule found.

The passes a reviewer agrees with are **true positives**. A wrong reply that the rule passes is a **false positive**, or false pass. A correct reply the rule rejects is a **false negative**, or false failure. If a conservative rule sends a correct reply to review, it has yet to find that pass automatically. Report pending reviews separately. If a request never returned a reply, mark it UNSCORABLE. There’s no text to check, and it should stay visible as an execution outcome.

### Step 2 — Ignore agreed differences in an account name

The same account name can arrive in capital letters or with repeated spaces. Use `split()` to split the name into pieces at whitespace, the spaces and similar gaps in text. In `" ".join(words)`, the quoted space is the separator that goes between those pieces. `casefold()` prepares text for a comparison that ignores differences in letter case.

Copy the block into the editor and click **Run**. The function starts with `def` and takes one name each time you call it. `return` hands the cleaned name back.

```python
def normalize_name(name):
    words = name.split()
    return " ".join(words).casefold()


expected = "Standard Savings"
reply = "  STANDARD   SAVINGS  "

print("Exact match:", reply == expected)
print("Cleaned reply:", normalize_name(reply))
print("Normalized match:", normalize_name(reply) == normalize_name(expected))
```

```text
Cleaned reply: standard savings
Normalized match: True
```

Splitting and rejoining removes the outside gaps and leaves one space inside. The cleaned versions use the same case.

### Step 3 — Use a reviewed list of aliases

The bank accepts the text “Standard Savings Account” as an alias. A dictionary stores a name and its associated value in curly braces. `aliases.get(key)` retrieves the value for the supplied key and gives `None` when it cannot find one. Here `None` means the list contains no approved match.

The line `from unicodedata import normalize` makes Python’s standard Unicode helper available. Use NFKC on the account field before cleaning spaces and case. The `if account is None` condition handles a name the dictionary couldn’t find. The indented `else` block handles a name it found. Copy the block and click **Run**.

```python
from unicodedata import normalize


def account_key(name):
    name = normalize("NFKC", name)
    return " ".join(name.split()).casefold()


aliases = {
    "standard savings": "Standard Savings",
    "standard savings account": "Standard Savings",

reply = "Ｓtandard Savings Account"
account = aliases.get(account_key(reply))

if account is None:
    print("Review: account name not recognized")
else:
    print("Canonical account:", account)
```


NFKC changes the full-width “Ｓ” to “S.” Cleanup turns the name into a dictionary key that already exists, so the program prints the canonical name saved under that key.

### Step 4 — Check the number’s boundaries

A substring search with `in` finds literal text wherever it appears. Import Python’s standard `re` module to try a pattern instead. In `r"\b100\b"`, `r` tells Python to keep the backslashes for the regex, and `\b` means a boundary between a word character and a non-word character or the start or end of text. Digits are word characters, so there is no boundary between “100” and the last “0” in “1000.” `re.search()` returns `None` if it finds no match. `is not None` checks for a match.

Copy the complete block and click **Run**.

```python
import re

reply = "Monthly fee: ₹1000."

print("Substring found:", "100" in reply)
print("Number pattern found:", re.search(r"\b100\b", reply) is not None)
```

```text
Substring found: True
Number pattern found: False
```

The substring occurs inside 1000. The pattern requires the boundary after 100, so it rejects this occurrence.

**Experiment.** Set only `reply` to `"The fee is ₹80, not ₹100."` and run again.

```text

Number pattern found: True
```

Now the number is separate, and the pattern matches. The word “not” tells you that the reply denies this amount.

**Checkpoint.** Did the pattern verify the monthly fee? It found “100” with a boundary on each side. To check which amount the reply asserts, read the words around it. This pattern can also find “100” inside “100.50” because the decimal point marks a boundary.

### Step 5 — Read a whole-rupee fee from a fixed format

Ask Python to match the entire field. `re.fullmatch()` requires a match from start to finish. In the pattern below, `[0-9]+` means one or more digits from 0 through 9. Parentheses keep those digits as a group you can read back. `[.]?` makes a literal final period optional. `match.group(1)` reads the first group, and `int()` changes that string of digits into a whole number. `strip()` trims whitespace from the outside of the field.

Copy the block and click **Run**. Compare the displayed amount with the approved fee.

```python
import re

expected_rupees = 100
reply = "Monthly fee: ₹1000"

match = re.fullmatch(r"Monthly fee: ₹([0-9]+)[.]?", reply.strip())
if match is None:
    print("Review: could not read the fee field")
else:
    actual_rupees = int(match.group(1))
    print("Read rupees:", actual_rupees)
    print("Fee matches:", actual_rupees == expected_rupees)
```

```text
Read rupees: 1000
Fee matches: False
```

The full field matches the format, so Python compares 1000 and 100 as numbers.

**Experiment.** Change only `reply` to `"Monthly fee: ₹100"` and run again.

```text

Fee matches: True
```

The pattern accepts the field without a period and the amounts now agree. Step 1’s literal check would reject the missing period.

**Checkpoint.** What if the reply says “You pay one hundred rupees each month”? This pattern would ask for review. The typed check measures the agreed field, so a reviewer must judge replies outside it.

### Step 6 — Measure the substring rule against reviewed replies

Use the five replies from Example 3 that arrived. A reviewer has already judged each one. Put the replies and their expected judgments into pairs, then use `for reply, correct in reviewed:` to give the two values in each pair names. `predicted` holds what the substring rule says. Each pair is written in parentheses. The `and` test requires both conditions. `elif` tries the next condition when the one above didn’t run.

Copy the block and click **Run**. Divide the correct automatic passes by all automatic passes for precision. Divide the same correct automatic passes by all replies the reviewer accepted for recall. Multiply by 100 for a percentage. `round(value, 1)` gives one decimal place. Both denominators are positive in this lesson.

```python
reviewed = [
    ("Monthly fee: ₹100.", True),
    ("Monthly fee: ₹100", True),
    ("The fee is ₹80, not ₹100.", False),
    ("Monthly fee: ₹1000.", False),
    ("You pay one hundred rupees each month.", True),
]

true_passes = 0
false_passes = 0
missed_passes = 0
needle = "100"

for reply, correct in reviewed:
    predicted = needle in reply
    if predicted and correct:
        true_passes = true_passes + 1
    elif predicted:
        false_passes = false_passes + 1
    elif correct:
        missed_passes = missed_passes + 1

print("True passes:", true_passes)
print("False passes:", false_passes)
print("Missed passes:", missed_passes)
print("Precision (%):", round(100 * true_passes / (true_passes + false_passes), 1))
print("Recall (%):", round(100 * true_passes / (true_passes + missed_passes), 1))
```

```text
False passes: 2
Missed passes: 1
Precision (%): 50.0
Recall (%): 66.7
```

### Step 7 — Compare the rules and retain cases for review

Put both rules beside the same reviewed judgments. Run the format check in a function and `return` a result for each reply. `None` stands for a timeout with no saved text. The first condition returns UNSCORABLE before the code tries to read the text. An unfamiliar format returns REVIEW. A readable field returns PASS or FAIL according to its amount.

Copy the full block and click **Run**. The loop unpacks each case’s ID, reply, and reviewer judgment, then prints the two rule outcomes beside that judgment. `expected` is a policy value, while `human` holds the result of a review already performed for the example.

```python
import re


def typed_fee(reply, expected):
    if reply is None:
        return "UNSCORABLE"
    match = re.fullmatch(r"Monthly fee: ₹([0-9]+)[.]?", reply.strip())
    if match is None:
        return "REVIEW"
    if int(match.group(1)) == expected:
        return "PASS"
    return "FAIL"


expected = 100
cases = [
    ("A", "Monthly fee: ₹100.", "PASS"),
    ("B", "Monthly fee: ₹100", "PASS"),
    ("C", "The fee is ₹80, not ₹100.", "FAIL"),
    ("D", "Monthly fee: ₹1000.", "FAIL"),
    ("E", "You pay one hundred rupees each month.", "PASS"),
    ("F", None, "UNSCORABLE"),
]

print("Case | Human | Substring | Typed")
for case_id, reply, human in cases:
    if reply is None:
        substring = "UNSCORABLE"
    elif "100" in reply:
        substring = "PASS"
    else:
        substring = "FAIL"
    print(case_id, "|", human, "|", substring, "|", typed_fee(reply, expected))
```

```text
Case | Human | Substring | Typed
A | PASS | PASS | PASS
B | PASS | PASS | PASS
C | FAIL | PASS | REVIEW
D | FAIL | PASS | FAIL
E | PASS | FAIL | REVIEW
F | UNSCORABLE | UNSCORABLE | UNSCORABLE
```

The typed check makes three automatic decisions about written replies, all in agreement with the reviewer. It leaves two to review and records one execution outcome.

**Experiment.** In row D only, change `"Monthly fee: ₹1000."` to `"A ₹100 fee applies every day."`. Keep its human label as FAIL because the frequency is wrong. Run again.

```text
Case | Human | Substring | Typed
A | PASS | PASS | PASS
B | PASS | PASS | PASS
C | FAIL | PASS | REVIEW
D | FAIL | PASS | REVIEW
E | PASS | FAIL | REVIEW
F | UNSCORABLE | UNSCORABLE | UNSCORABLE
```

The substring rule still finds 100. The typed check now sees an unfamiliar format and asks for review. The human label stays FAIL because the bank charges monthly.

**Checkpoint.** Does the typed rule understand daily and monthly fees? It recognizes the word “Monthly” in one format. Keep the reviewer’s result and the rule’s result side by side when you decide how much to automate.

## Common Mistakes

- **Treating a substring as a fact.** Check which amount the reply asserts, alongside its currency and frequency.
- **Cleaning every field the same way.** Choose normalization for each field. Check a counterexample before ignoring a character.
- **Counting unresolved or absent replies as accepted.** Report pending reviews and unscorable requests separately.
- **Reporting precision without coverage.** Keep the number of correct replies the rule missed and the size of the review queue visible.
- **Changing the examples when changing the rule.** Compare both rules on the same saved replies and reviewed judgments.
