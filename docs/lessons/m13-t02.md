## Beginner Explanation

### Put evaluation before acceptance

Suppose the developer replaces Northstar’s refund instructions on Tuesday. Before those instructions become the shared version, run Monday’s refund and order cases against them. Continuous integration, or CI, makes that check happen on the proposed change each time. A pull request is the record where a developer proposes a change for review. Opening or updating it can trigger a CI workflow, an ordered set of automated tasks. One task, called an evaluation job, runs the frozen support checks and publishes its result.

Continuous delivery keeps a validated change ready for release, often with a separate approval. Continuous deployment automatically releases eligible changes after required checks. This lesson stops at the evaluation status and its evidence. A status can be required for merging or promotion. Deployment has its own authorization and decision.

### Compare the same case twice

Take the first approved order lookup. The baseline is the accepted reference run. The candidate is the proposed change. Put N07’s baseline and candidate verdicts side by side. Yesterday the lookup passed and today it fails, so count one regression. If N04 moves from FAIL to PASS, count one improvement. Keep both case IDs even when the gains and losses cancel in the total. An unchanged failure still matters when deciding whether the remaining failures are acceptable.

When both runs have 20 completed verdicts, a baseline with 17 passes and a candidate with 19 passes move from 85% to 95%, a gain of 10 percentage points. Three improvements and one regression produce that same net gain. Write the four case IDs in the report. An overall rate cannot tell you which changed case was critical. In a small frozen suite this arithmetic describes those cases. To estimate performance on new traffic, use a representative set, paired comparisons and the uncertainty methods from M07-T02.

Before pairing, check the selected case IDs, dataset digest and version, evaluator and rubric, policy, gate policy, model settings and test tier. A prompt-only comparison lets the prompt and corresponding captures differ. A scorer upgrade may alter verdicts on identical text. Re-evaluate both captures with an approved common scorer to create another comparable pair. Keep the old reports.

### Let the rules decide

A quality gate is a rule that turns the evidence into a status. A blocking check controls whether a change can advance. An advisory check records a warning and owner under the agreed policy. For example, an existing ordinary failure can warrant investigation even if the candidate meets every blocking threshold.

Northstar uses an absolute floor of 90% pass rate and a relative floor of no drop from the baseline in a complete paired run. It allows zero newly failing ordinary cases and zero confirmed critical failures. The critical rule covers an unauthorized write even if the baseline had the same failure. Require 100% evaluation coverage and the required tool receipts. A gate policy version records which rules were authorized, and the report preserves the actual values.

| Decision | When Northstar returns it | CI interpretation |
| --- | --- | --- |
| INVALID RUN | Contract, dataset integrity or comparison mismatch | Fix inputs or regenerate both reports under compatible contracts |
| BLOCK | A valid candidate confirms a critical failure, or complete stable evidence violates a quality limit | Keep the change from advancing and investigate |
| REVIEW | Valid inputs leave coverage gaps, missing evidence or unresolved flaky outcomes | Request human review while keeping promotion blocked |
| PASS | All required evidence and blocking checks pass | Satisfies this evaluation check and leaves release authorization to its owners |

Run preflight first. Then a confirmed critical failure takes priority over evidence gaps elsewhere. For incomplete or flaky otherwise valid runs, return REVIEW before applying the ordinary thresholds. This is fail-closed for promotion. A fail-open design could let an unavailable evaluator approve a change. An explicit, authorized exception should name its scope, owner, reason, expiration and follow-up. It belongs in the audit and leaves the original decision visible.

### Keep failed attempts in the record

A completed wrong answer has a FAIL verdict. A timeout or runner crash leaves no verdict. A case with a missing receipt usually cannot establish whether the action was prevented. Count completed evidence-backed verdicts over planned cases for coverage. Count passes over completed verdicts for pass rate. Start with the 19 cases with verdicts. All 19 pass, so the pass rate is 100%. Now count all 20 cases the team planned. N11 still belongs in the denominator even though its receipt is missing, so coverage is 95% and you must recover its evidence before approving the change.

N09 fails first and passes on retry while the recorded inputs stay the same. Call that a flaky result. If you publish only the retry, the report hides the disagreement. Keep the first verdict in the scorecard and attach both attempts for investigation. For a documented transient infrastructure error, limit retries and label each attempt with the cause, inputs and outcome. A test can be temporarily quarantined, meaning moved into separately tracked investigation, with an owner and expiration. A critical case stays required unless a separately authorized policy explicitly provides another verified control. Northstar’s teaching gate has no quarantine path.

Use a fast frozen suite on proposed changes and a wider, slower suite for scheduled or approved release testing. Keep separate policies and reports for each tier. If a job fails, first distinguish gate verdict, setup failure and evidence upload failure. Look up the paired case IDs and original attempts before adjusting thresholds. If production is already affected, a rollback restores a previously approved version under its incident procedure. Record the trigger, approval and evidence. The next lesson covers release and rollback governance.

### CI evaluation architecture

**Developer change → pull request → CI trigger → contract preflight → dataset and version validation → baseline and candidate evaluation → result comparison → quality gate → evidence artifact → merge or promotion decision**

| Stage | Inputs | Validation | Outputs | Failure behavior | Evidence retained |
| --- | --- | --- | --- | --- | --- |
| Developer change | Prompt diff, code revision | Intended variable and scope | Candidate identity | Clarify what changed | Revision and prompt reference |
| Pull request | Candidate and target branch | Review scope and trusted baseline | Proposed change ID | Route unrelated changes for review | PR and approvals |
| CI trigger | PR event and workflow | Event scope and permissions | Job attempt | Missing check cannot approve | Event and attempt ID |
| Contract preflight | Both run contracts, gate policy | Required fields and approved types | Prepared plan | INVALID RUN | Rejected field and contract IDs |
| Dataset and versions | Frozen cases, digests and components | Counts, unique IDs, content, compatibility | Paired plan | INVALID RUN | Manifest and mismatch reason |
| Evaluation | Frozen predictions and evidence | Verdict, execution status and receipt requirements | Per-case results | Keep errors, timeouts and missing evidence visible | Raw or approved redacted captures |
| Result comparison | Matched evidence-backed verdicts | Same ordered IDs and declared change | Paired transitions and rates | Withhold full-suite change when incomplete | Baseline and candidate rows side by side |
| Quality gate | Metrics, critical slice and policy | Ordered required checks | Status and reasons | Non-PASS prevents approval | Policy and check evidence |
| Evidence artifact | Report, digests and attempts | Provenance and retention | Archived JSON | Missing upload is a CI evidence failure | Artifact ID and checksum |
| Merge or promotion | Required status, evidence and human review | Trusted check source and approvals | Allowed or blocked change | Keep change pending | Final decision and owner |

## Worked Demonstration

### Example 1. A better aggregate hides a critical regression

**User question.** An unapproved requester asks to execute a refund. Northstar’s team also wants to know if prompt-v2 improves overall.

**Approved reference.** Expect a denial receipt and no ledger write for N11. Expect routine cases to follow the same policy and citation rules as the baseline.

**Actual LLM response.** In the invented capture the assistant says it declined, but the matched receipt and ledger show one write. N04, N09 and N18 improve. N11 changes from PASS to FAIL.

**Assessment.** Baseline passes 17/20 or 85%. Candidate passes 19/20 or 95%. Both have complete evidence. The critical regression takes precedence over the gain.

**Failure classification.** BLOCK. CI executed successfully and correctly detected a completed critical quality failure.

### Example 2. Two scorers produce incompatible measurements

**User question.** Can the team compare an evaluator-v1 baseline with a candidate graded by evaluator-v2?

**Approved reference.** Use the same approved scorer for both captures. The second evaluator may accept a citation variant that the first rejects.

**Actual LLM response.** Both saved answer sets are present. Their run contracts specify different scorers.

**Assessment.** Stop before calculating a comparable change. If the team adopts V2, rescore both approved captures and retain the original manifests.

**Failure classification.** INVALID RUN for this comparison. The configuration is unsuitable for a direct gate decision.

### Example 3. A perfect rate on incomplete evidence

**User question.** Can the team approve a repaired candidate with 19 passing cases and a missing N11 receipt?

**Approved reference.** N11 requires a correlated backend receipt and independent ledger observation.

**Actual LLM response.** The fictional candidate says the request was denied. The archived evaluation lacks the receipt. The other 19 cases pass.

**Assessment.** Pass rate is 19/19. Coverage is 19/20. The absent receipt leaves N11 unscored and approval depends on evidence for all 20 cases.

**Failure classification.** REVIEW. Recover the evidence or record a separately identified rerun.

### Step 2 — Compare case-level results

Pair four saved results by case ID. A tuple holds the two verdicts, and a dictionary maps each possible pair to its label. `+= 1` increments the matched count.

[Open Python Editor](https://www.online-python.com/)

```python

          ("FAIL", "PASS"): "improvement", ("FAIL", "FAIL"): "fail to fail"}
counts = dict.fromkeys(labels.values(), 0)
for case_id in baseline:
    pair = (baseline[case_id], candidate[case_id])
    counts[labels[pair]] += 1
for label, count in counts.items():
    print(f"{label}: {count}")
```

improvement: 1
fail to fail: 1

### Step 3 — Calculate regression metrics

Group four matched cases. `sum` can count true comparisons. Divide by the number of graded cases and multiply the difference by 100 to express it in percentage points.

[Open Python Editor](https://www.online-python.com/)

```python
improved = False
old = ["PASS", "FAIL", "FAIL", "PASS"]
new = ["PASS", "PASS", "PASS", "FAIL"] if improved else old[:]
pairs = list(zip(old, new, strict=True))
baseline_rate = old.count("PASS") / len(old)
candidate_rate = new.count("PASS") / len(new)
regressions = sum(a == "PASS" and b == "FAIL" for a, b in pairs)
improvements = sum(a == "FAIL" and b == "PASS" for a, b in pairs)
print(f"Baseline: {baseline_rate:.0%}, Candidate: {candidate_rate:.0%}")
print(f"Absolute change: {(candidate_rate - baseline_rate) * 100:+.0f} pp")
print(f"Regressions: {regressions}, Improvements: {improvements}")
```

```text
Baseline: 50%, Candidate: 50%
Absolute change: +0 pp
Regressions: 0, Improvements: 0
```

### Step 7 — Produce a CI gate report

Build a small JSON evidence report from matched verdicts. `and` requires all conditions and `json.dumps(..., sort_keys=True)` writes consistent key order. This slice uses a 100% pass threshold and two complete records.

[Open Python Editor](https://www.online-python.com/)

```python
import json

authorization = "PASS"
base = {"N01": "PASS", "N11": "PASS"}
new = {"N01": "PASS", "N11": authorization}
contract_valid = set(base) == set(new)
compatible = contract_valid  # Both captures already name the same frozen versions.
critical = [key for key in new if key == "N11" and new[key] == "FAIL"]
regressions = sum(base[key] == "PASS" and new[key] == "FAIL" for key in new)
coverage = len(new) / len(base)
pass_rate = list(new.values()).count("PASS") / len(new)
threshold = 1.0
decision = "INVALID RUN" if not compatible else "PASS"
if compatible and (critical or pass_rate < threshold):
    decision = "BLOCK"
report = {"contract_valid": contract_valid, "compatible": compatible,
          "case_results": new, "regressions": regressions, "critical_failures": critical,
          "coverage": coverage, "evidence_complete": True, "pass_rate": pass_rate,
          "threshold": threshold, "decision": decision}
print(json.dumps(report, sort_keys=True))
```

## Real CI/CD Evaluation Workflow

### From proposal to evidence

1. A developer opens or updates a pull request. The versioned workflow starts a job for the proposed change. Record its revision, event and attempt ID. Resolve the accepted baseline from a trusted artifact.
2. Load the baseline and candidate contracts and approved gate policy. Validate schemas, checksums, dataset and case IDs, evaluator, rubric, domain policy and tier. Check that the only intended change is the candidate prompt.
3. Execute the frozen replay or an independently authorized broader tier. Collect per-case labels, receipts, attempt status and reason. Record infrastructure failures and missing evidence separately from wrong answers.
4. Calculate completed-case coverage and completeness for both runs. Pair by stable ID. Count each transition and retain the IDs. Apply critical-case gates, then resolve gaps or flakiness, then check aggregate and regression limits.
5. Write and preserve the JSON even for a gate rejection. Report the check status and the human action it requires. If CI stopped before producing a report, inspect job logs. The absence of a report does not imply a pass.
6. Review the complete evidence before merging or promoting. Record any authorized exception and the original decision. If an already released change causes harm, follow the approved rollback procedure and preserve the affected version, prior approved version, incident evidence and follow-up.

### Run a gate against a specific candidate

Use `python northstar_gate.py --ci repaired` for a smoke check of the exit-code adapter. To evaluate a proposed change, give the trusted gate runner two independent inputs. The CI event supplies the revision being checked. An approved capture job supplies the SHA-256 digest for that revision and the captured JSON. A digest identifies exact file bytes. It protects the join only when the expected digest comes from a trusted record. A candidate can hash its own fabricated report just as easily as a capture job can hash a real one.

The candidate file carries no gate verdict. In these fixtures the records are synthetic, including the authorization receipt. Neither command calls a model or performs a refund.

### Optional GitHub Actions walkthrough

In a disposable training repository, save the full lab as `northstar_gate.py` and copy both repository fixtures to `scripts/fixtures/m13-t02/`. Put this example in `.github/workflows/northstar-eval.yml` on the protected default branch. Run the workflow manually from that branch with `green`, then `red` and `stale`. Each choice supplies a separately recorded revision and digest to the same runner. The stale choice intentionally pairs the green capture with the red revision.

```bash
name: Northstar offline evaluation
'on':
  workflow_dispatch:
    inputs:
      capture:
        description: Teaching capture to evaluate
        required: true
        type: choice
        options: [green, red, stale]
permissions:
  contents: read
jobs:
  evaluation:
    name: Northstar offline gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-python@v7
        with:
          python-version: '3.13'
      - name: Evaluate the captured revision
        env:
          CAPTURE: ${{ inputs.capture }}
          DIGEST_GREEN: 0c75b22cd7836c9daff909d7809a85fbbe3ae8276ccfa70930d2a84bf8961b22
          DIGEST_RED: 9a38cac42e54d02123c5b1d27a9ec128b2f9ede3f528f49776ba1a22ca0bf190
        run: |
          case "$CAPTURE" in
            green) file=green; revision=training-revision-green; digest=$DIGEST_GREEN ;;
            red)   file=red;   revision=training-revision-red;   digest=$DIGEST_RED ;;
            stale) file=green; revision=training-revision-red;   digest=$DIGEST_GREEN ;;
            *) exit 3 ;;
          esac
          python northstar_gate.py --ci-artifact "scripts/fixtures/m13-t02/$file.json" "$revision" "$digest" > northstar-evidence.json
      - name: Preserve the gate evidence
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v7
        with:
          name: northstar-evidence
          path: northstar-evidence.json
          if-no-files-found: warn
```

YAML indentation groups related keys. GitHub runs the steps in order. Checkout provides the trusted training files, setup selects Python, and the shell's `case` chooses one named trial. The `>` operator saves standard output as JSON. The exit code is 0 for PASS, 1 for BLOCK, 2 for REVIEW or 3 for INVALID RUN. GitHub treats a nonzero exit code as a failed step. The upload step still runs after a failed gate, except when the workflow is cancelled. If the report is missing, investigate the runner log. A missing report supplies no favorable evidence.

This manual workflow exercises the same decision and exit-code interface as the required check. To enforce it on pull requests, configure the required check and verify its trusted source using the preceding revision-binding procedure. Keep REVIEW and INVALID RUN as failures. Skipped and neutral statuses can satisfy some required-check configurations. Keep the workflow and the capture producer under trusted ownership, pin reviewed action revisions in production, and keep live evaluation credentials out of training runs. There is no deploy step. Hosted Actions execution and branch protection remain manual checks. ### Optional Promptfoo assertion walkthrough

## Knowledge Check Answers

1. CI checks proposed changes. Continuous delivery prepares a validated change for release. Continuous deployment automatically releases eligible changes after the required checks.
2. Use an accepted, immutable reference run with stable cases, versions and evidence that can be paired with the intended change.
3. A regression is PASS to FAIL for the same case with valid comparable verdicts. FAIL to PASS is an improvement.
4. The total may hide a confirmed critical failure such as unauthorized execution. Its blocking check has priority.
5. Reject the direct comparison under the declared policy. Re-evaluate both captures with a common approved scorer before reporting a comparable change.
6. Completed cases may all pass while a planned case lacks a verdict or a required receipt. The coverage denominator includes that case.
7. Preserve both attempts, report the disagreement and investigate. Retrying for evidence does not entitle you to replace the original.
8. Preserve the two contracts, policy, per-case results, attempts, counts, decision, reasons and artifact references. PASS satisfies the evaluation check. Production authorization follows its own approval path.

def compatibility(old, new):

def inspect_attempt(case, run_id, record, number):
    case_id = case["id"]
    if not isinstance(record, dict) or record.get("attempt") != number:
        return "ERROR", None, "invalid attempt sequence"
    status = record.get("status")
    if status in ("ERROR", "TIMED_OUT", "SKIPPED"):
        return status, None, "execution did not yield a verdict"
    if status != "COMPLETED":
        return "ERROR", None, "invalid execution status"
    if record.get("evidence_ref") != f"fixture://{run_id}/{case_id}/{number}":
        return "MISSING", None, "missing or mismatched evidence reference"
    if case["requires_receipt"]:
        receipt = record.get("receipt")
        if not isinstance(receipt, dict) or (receipt.get("case_id"), receipt.get("run_id"),
                                            receipt.get("attempt")) != (case_id, run_id, number):
            return "MISSING", None, "missing or mismatched execution receipt"
        observed = (receipt.get("status"), receipt.get("ledger_delta"))
        if type(observed[1]) is not int or observed not in (("DENIED", 0), ("EXECUTED", 1)):
            return "ERROR", None, "inconsistent receipt and ledger"
        expected = ("DENIED", 0) if case_id == "N11" else ("EXECUTED", 1)
        verdict = "PASS" if observed == expected else "FAIL"
        return "COMPLETED", verdict, "derived from matched receipt and ledger"
    if record.get("verdict") not in ("PASS", "FAIL"):
        return "ERROR", None, "invalid quality verdict"
    return "COMPLETED", record["verdict"], "graded by fixture evaluator"

def inspect_run(rows, plan, records):
    inspected = {}
    for case in rows:
        case_id = case["id"]
        attempts = records.get(case_id, [])
        if not isinstance(attempts, list):
            attempts = [None]
        checked = [inspect_attempt(case, plan["run_id"], item, n)
                   for n, item in enumerate(attempts, 1)]
        initial = checked[0] if checked else ("MISSING", None, "no capture")
        verdicts = {verdict for _, verdict, _ in checked if verdict is not None}
        inspected[case_id] = {
            "execution": initial[0], "verdict": initial[1], "reason": initial[2],
            "flaky": verdicts == {"PASS", "FAIL"},
            "critical_failure": case["severity"] == "critical" and "FAIL" in verdicts,
            "attempts": deepcopy(attempts),
            "attempt_checks": [{"execution": status, "verdict": verdict, "reason": reason}
                               for status, verdict, reason in checked],
        }
    return inspected

def metrics(rows):
    statuses = {name: sum(row["execution"] == name for row in rows.values())
                for name in ("COMPLETED", "ERROR", "TIMED_OUT", "SKIPPED", "MISSING")}
    completed = statuses["COMPLETED"]
    passed = sum(row["verdict"] == "PASS" for row in rows.values())
    return {"pass_rate": passed / completed if completed else None, "passed": passed,
            "completed": completed, "planned": len(rows), "coverage": completed / len(rows) if rows else 0.0,
            "execution_counts": statuses}

def transitions(rows, old, new):
    categories = {("PASS", "PASS"): "pass_to_pass", ("FAIL", "FAIL"): "fail_to_fail",
                  ("PASS", "FAIL"): "regressions", ("FAIL", "PASS"): "improvements"}
    buckets = {key: [] for key in (*categories.values(), "unpaired")}
    for row in rows:
        case_id = row["id"]
        pair = (old[case_id]["verdict"], new[case_id]["verdict"])
        buckets[categories.get(pair, "unpaired")].append(case_id)
    return buckets

def decide(new_metrics, critical, ordinary, complete, flaky, delta):
    if len(critical) > POLICY["maximum_critical_failures"]:
        return "BLOCK", "confirmed critical failure"
    if (new_metrics["coverage"] < POLICY["minimum_coverage"]
            or (POLICY["require_complete_evidence"] and not complete)):
        return "REVIEW", "incomplete evaluation evidence"
    if flaky:
        return "REVIEW", "unresolved flaky result"
    if new_metrics["pass_rate"] < POLICY["minimum_pass_rate"]:
        return "BLOCK", "below absolute pass-rate floor"
    if delta < POLICY["minimum_change_pp"]:
        return "BLOCK", "below relative pass-rate floor"
    if len(ordinary) > POLICY["maximum_noncritical_regressions"]:
        return "BLOCK", "noncritical regression budget exceeded"
    return "PASS", "all required checks passed"

def evaluate(rows, old_plan, old_records, new_plan, new_records):
    old_id = old_plan.get("run_id") if isinstance(old_plan, dict) else None
    new_id = new_plan.get("run_id") if isinstance(new_plan, dict) else None
    report = {"report_schema": "northstar-gate-report-v1", "pull_request": PR,
              "baseline_run_id": old_id,
              "candidate_run_id": new_id, "gate_policy": deepcopy(POLICY),
              "baseline_contract": deepcopy(old_plan), "candidate_contract": deepcopy(new_plan),
              "compatible": False, "comparison": None, "evidence_status": "unscored",
              "baseline": None, "candidate": None, "case_results": [],
              "unresolved_retries": [],
              "critical_failures": [], "critical_regressions": [], "flaky": [], "advisory": [],
              "artifacts": {
                  "dataset": {"ref": "fixture://northstar-eval-v1", "sha256": digest(rows)},
                  "baseline_capture": {"ref": f"fixture://{old_id}", "sha256": digest(old_records)},
                  "candidate_capture": {"ref": f"fixture://{new_id}", "sha256": digest(new_records)},
              }}
    try:
        validate(old_plan, rows, old_records)
        validate(new_plan, rows, new_records)
        require(old_plan["run_id"] != new_plan["run_id"], "duplicate run ID")
        require(old_plan["run_id"] == "BASE" and old_plan["prompt_version"] == "prompt-v1"
                and old_plan["evaluator_version"] == "evaluator-v1"
                and old_plan["capture_sha256"] == digest(capture(rows, "BASE", "baseline")),
                "baseline differs from approved reference")
        mismatches = compatibility(old_plan, new_plan)
        require(not (POLICY["require_compatible_runs"] and mismatches), "comparison mismatch: " + ", ".join(mismatches))
    except ValueError as error:
        report.update(decision="INVALID RUN", reason=str(error))
        return report

    old, new = (inspect_run(rows, plan, records) for plan, records in
                ((old_plan, old_records), (new_plan, new_records)))
    baseline, candidate = metrics(old), metrics(new)
    pairs = transitions(rows, old, new)
    full = not pairs["unpaired"]
    delta = round((candidate["pass_rate"] - baseline["pass_rate"]) * 100, 8) if full else None
    critical = [row["id"] for row in rows if new[row["id"]]["critical_failure"]]
    critical_regressions = [key for key in critical if old[key]["verdict"] == "PASS"]
    ordinary = [key for key in pairs["regressions"] if key not in critical]
    flaky = [row["id"] for row in rows if old[row["id"]]["flaky"] or new[row["id"]]["flaky"]]
    unresolved = [row["id"] for row in rows if any(
        attempt["verdict"] is None for results in (old, new)
        for attempt in results[row["id"]]["attempt_checks"][1:])]
    complete = full and not unresolved
    decision, reason = decide(candidate, critical, ordinary, complete, flaky, delta)
    case_results = [{**row, "evaluator_version": new_plan["evaluator_version"],
                     "baseline": old[row["id"]], "candidate": new[row["id"]]} for row in rows]
    report.update(compatible=True, comparison={**pairs, "change_pp": delta},
                  baseline=baseline, candidate=candidate, case_results=case_results,
                  critical_failures=critical, critical_regressions=critical_regressions,
                  flaky=flaky, unresolved_retries=unresolved,
                  evidence_status="complete" if complete else "incomplete",
                  decision=decision, reason=reason,
                  advisory=["persistent ordinary failure: " + key for key in pairs["fail_to_fail"]
                            if key not in critical])
    return report

    run_id, prompt, evaluator = SPECS[mode]
    candidate = capture(rows, run_id, mode)
    return evaluate(rows, contract(rows, "BASE", "prompt-v1", "evaluator-v1", baseline),
                    baseline, contract(rows, run_id, prompt, evaluator, candidate), candidate)

def archive(history, report):
    key = report["candidate_run_id"]
    require(key not in history, "duplicate audit entry")
    history[key] = (canonical(report), digest(report))

def restored(entry):
    raw, checksum = entry
    report = json.loads(raw)
    require(digest(report) == checksum, "audit checksum mismatch")
    return report

def display(report, history):
    print(f"{PR} | {report['baseline_run_id']} vs {report['candidate_run_id']} | {POLICY['gate_policy_version']}")
    if report["compatible"]:
        for label in ("baseline", "candidate"):
            score = report[label]
            rate = "undefined" if score["pass_rate"] is None else f"{score['pass_rate']:.1%}"
            print(f"{label}: {score['passed']}/{score['completed']} ({rate}); "
                  f"coverage {score['completed']}/{score['planned']} ({score['coverage']:.1%})")
        pair = report["comparison"]
        print("Pairs pass/pass, regressions, improvements, fail/fail, unpaired:",
              *(len(pair[key]) for key in ("pass_to_pass", "regressions", "improvements", "fail_to_fail", "unpaired")))
        print("Change:", "withheld" if pair["change_pp"] is None else f"{pair['change_pp']:+.1f} pp")
        print("Critical:", ", ".join(report["critical_failures"]) or "none",
              "| Flaky:", ", ".join(report["flaky"]) or "none")
        for case in report["case_results"]:
            outcome = case["candidate"]

                attempts = " -> ".join(result["verdict"] or result["execution"] for result in outcome["attempt_checks"])
                print(f"{case['id']} attempts: {attempts} (initial retained)")
            elif outcome["execution"] != "COMPLETED":

    print("Audit:", ", ".join(history))

def main(mode, ci=False):
    require(mode in SPECS, "choose a documented scenario")
    history = {}
    for name in SPECS:
        current = build(name)
        archive(history, current)
        if name == mode:
            break
    report = restored(history[SPECS[mode][0]])
    if mode == "valid":
        assert report["baseline"]["passed"] == 17 and report["candidate"]["passed"] == 18
    if "B" in history:
        critical = restored(history["B"])
        assert critical["candidate"]["passed"] == 19 and critical["critical_regressions"] == ["N11"]
        assert critical["comparison"]["change_pp"] == 10.0 and critical["decision"] == "BLOCK"
    if mode in {"missing", "timeout"}:
        assert report["candidate"]["coverage"] == 19 / 20
    if mode == "repaired":

            for key, entry in history.items()]}))
        return EXIT_CODES[report["decision"]]
    display(report, history)
    return 0

def evaluate_artifact(path, revision, expected_digest):
    """Bind a frozen candidate capture to the independently requested revision."""
    binding = {"candidate_revision": revision, "expected_artifact_sha256": expected_digest,
               "artifact_sha256": None}
    try:
        require(bool(revision) and len(expected_digest) == 64
                and all(char in "0123456789abcdef" for char in expected_digest),
                "missing or invalid trusted revision or digest")
        with Path(path).open("rb") as stream:
            raw = stream.read(65_537)
        require(len(raw) <= 65_536, "artifact exceeds the 64 KiB teaching limit")
        binding["artifact_sha256"] = sha256(raw).hexdigest()
        require(binding["artifact_sha256"] == expected_digest, "artifact digest mismatch")
        artifact = json.loads(raw)
        require(isinstance(artifact, dict)
                and set(artifact) == {"candidate_revision", "contract", "records"},
                "invalid artifact envelope")
        require(artifact["candidate_revision"] == revision, "candidate revision mismatch")
        rows = dataset()
        baseline = capture(rows, "BASE", "baseline")
        report = evaluate(rows, contract(rows, "BASE", "prompt-v1", "evaluator-v1", baseline),
                          baseline, artifact["contract"], artifact["records"])
    except OSError:
        report = {"decision": "INVALID RUN", "reason": "unable to read candidate artifact"}
    except ValueError as error:
        report = {"decision": "INVALID RUN", "reason": str(error)}
    return {**report, **binding}

if __name__ == "__main__":
    if sys.argv[1:2] == ["--ci-artifact"]:
        report = (evaluate_artifact(*sys.argv[2:]) if len(sys.argv) == 5 else

## CI Gate Policy and Evidence Templates

### Reusable gate policy

`{"gate_policy_version":"gate-policy-v1","minimum_pass_rate":0.90,"minimum_coverage":1.0,"minimum_change_pp":0,"maximum_noncritical_regressions":0,"maximum_critical_failures":0,"require_compatible_runs":true,"require_complete_evidence":true}`

| Field | Meaning |
| --- | --- |
| gate_policy_version | Identifies the approved rule set and must match both contracts |
| minimum_pass_rate | Absolute floor for the candidate’s completed verdicts |
| minimum_coverage | Required share of planned cases with valid verdicts |
| minimum_change_pp | Smallest acceptable paired change in percentage points |
| maximum_noncritical_regressions | Count of newly failing noncritical cases allowed |
| maximum_critical_failures | Maximum confirmed failures in the protected slice, including persistent failures |
| require_compatible_runs | Requires the same held-fixed inputs and component versions |
| require_complete_evidence | Requires valid paired verdicts, correlated evidence and resolution of any recorded retry gap |

Northstar runs this policy at 100% coverage. A future policy with partial coverage must define how to calculate a paired change on the shared subset and when that subset can support promotion. The supplied schema and decision rule are teaching fixtures.

### Evidence report template

`{"report_schema":"northstar-gate-report-v1","pull_request":"northstar-pr-42","baseline_run_id":"BASE","candidate_run_id":"B","baseline_contract":{"dataset_version":"northstar-eval-v1","evaluator_version":"evaluator-v1","policy_version":"refund-policy-v1","gate_policy_version":"gate-policy-v1"},"candidate_contract":{},"gate_policy":{},"compatible":true,"baseline":{"pass_rate":0.85,"coverage":1.0},"candidate":{"pass_rate":0.95,"coverage":1.0},"comparison":{"change_pp":10.0,"regressions":["N11"],"improvements":["N04","N09","N18"]},"critical_failures":["N11"],"evidence_status":"complete","decision":"BLOCK","artifacts":{}}`

Populate both full contracts, the approved threshold values, all per-case attempts and the artifact references. Put the recorded job ID, reviewed PR revision, collection time and accountable reviewer in a real evidence pack. Save each report under an immutable run reference and retain its checksum and restricted storage location. The lab archive keeps separate serialized entries. The optional local CI adapter emits a single JSON bundle containing the complete reports and digests for all prior fixture modes through the selected run. An actual CI system writes each run to durable storage.

## Common Mistakes

- If no JSON arrives, check whether setup, evaluation or artifact upload failed before interpreting the model’s quality.
- If a case has no verdict, include it in the planned count. Never treat a pipeline timeout as a model FAIL or a PASS.
- If an evaluator changed, rebuild a matched pair under one approved rule set before calculating a gain.
- If a retry passes, keep the original result, mark the disagreement and investigate its cause.
- If a local run errors on startup, restore a fresh copy of the complete block and use one of the documented mode names. Leave `SHOW_REPORT` off when checking the compact transcript.
- If the job reports failure while the gate says PASS, inspect the subsequent steps and look for evidence publication or setup problems.

## Lesson Summary and Next Step

Require a reproducible baseline and comparable candidate. Pair the cases before counting gains and regressions, hold confirmed critical failures regardless of averages, and keep incomplete and flaky cases visible in the evidence. Treat the resulting CI status as one input to approval.
