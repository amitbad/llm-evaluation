## What You Will Learn

- Turn a small worksheet into JSON Lines, with a clear agreement about the fields and types.
- Keep a case ID attached to the same question and a response ID attached to one captured reply.
- Check required fields, value ranges, unique IDs, and source references.
- Preserve old replies and scores when a verified label changes.
- Create a version manifest that explains why the same replies can receive a different score.

## Why This Lesson Matters

A teammate brings two reports to a Harbor Leaf Bank review. Yesterday one of two replies passed. Today both passed. You put the replies side by side and see the exact same wording in both reports. In the worksheet, though, the expected June fee changed from ₹80 to ₹0. Before crediting the chatbot, find out which policy supports that correction.

The question asks whether a customer with exactly ₹4,000 in Standard Savings owed a fee on June 30, 2026. The saved reply says no. The old answer key says ₹80, but the approved June policy charges ₹80 only below ₹4,000. Before the correction, the right reply failed the check.

## Beginner Explanation

### 1. Give each question a name that survives sorting

Suppose the June question sits on row 2. You sort the sheet by date, and now row 2 is a July question. A reviewer who wrote “row 2 failed” may now point to the wrong question. Give the June question its own name, `FEE-001`, and keep that name when you reorder the sheet or correct its answer key. That name is a **stable case ID**.

The same case can receive a different reply each time the team runs the assistant. Give each captured reply its own **response ID**. `R-001` and `R-003` can both refer back to `FEE-001`. Each response ID identifies only one capture. Store the question and expected behaviour in the dataset. In a separate run record, save the response ID, case ID, exact reply, assistant version, and dataset version used. A captured reply may include prose even if the scorer reads a numeric amount from it. Keep the full reply with the amount the scorer used.

The worksheet you deliberately maintain and check against sources is your **golden dataset**, or reference set. That name means reviewers intend to use it as the answer key. The mistake in the June case shows why the answer key still needs review.

### 2. Agree what every row means

A spreadsheet cell may show 80 as text. The scorer needs a whole number of rupees. If two people treat that cell differently, they can end up comparing different things.

Write down the required field names, their types, and the limits you expect. This agreement is a **data contract**. Its field layout is the **schema**. In this lesson each case has an ID, task, question, date, balance, source reference, and expected fee. The date and task are **metadata**, or details about the case that help you interpret the question and label. Balance and expected fee must be whole numbers. The practice limits are 0 through 1,000,000 rupees for balance and 0 through 1,000 rupees for expected fee.

To exchange the worksheet, write each case as one JSON object on its own line. This format is **JSON Lines**, or **JSONL**. The converter must turn the two numeric cells into integers. Once they’re JSON numbers, a later validator can detect a bad string, a missing field, or a value outside the agreed range.

### 3. Record where a label came from

A label of 80 in a cell is hard to trust if you don’t know which fee rule was used. Keep the source reference and the date beside the label. The record of where your evidence came from is called **provenance**.

- **SV-1#2.** Section 2 of the approved Standard Savings policy in effect January 1 through June 30, 2026. The minimum was ₹4,000. An ₹80 monthly fee applied below that balance.
- **SV-2#2.** Section 2 of the approved policy effective July 1, 2026. The minimum is ₹5,000. A ₹100 monthly fee applies below that balance.

Read the two policy dates before you read either amount. June 30 is the last day of SV-1. A balance of exactly ₹4,000 is at that policy’s minimum, so the expected fee is zero. Now try citing SV-2#2 instead. The section exists in the register, but its July start date rules it out for this question. A reference check can find a section. A reviewer still needs to check that it applied and supports the label.

### 4. Keep a record of changes

Save the original dataset as `fees-v1` and the corrected copy as `fees-v2`. Store a short note with the new version listing its name, its parent, the schema version, what changed, and why. This note is a **version manifest**. For the June correction it should name `FEE-001`, the old value 80, the new value 0, and the source section that explains the change.

The original run belongs with the dataset and scorer it actually used. Keep it and add a separate report for scoring the same saved replies against the corrected labels. Saving new entries without rewriting past entries is called **append-only**. Keeping the artifacts separate lets a teammate answer two questions. What did we report then? What would those exact replies score with the corrected answer key?

In the two-case example, the June reply fails against 80 and the July reply passes against 100. That gives one pass out of two. Correct the June label to zero and both replies pass. The change from one of two to two of two comes from the label correction. Use one reviewed dataset version and one scoring rule for both assistants before trying to compare their performance.

**Assessment.** Start with the cell under the balance heading. The program reads it as the text `"4999"`. ### Example 2. Find a problem that valid JSON can hide

**User question.** “Did a fee apply at exactly ₹4,000 on June 30?” It appears in case FEE-001.

**Approved reference.** SV-1#2 was in effect on that date. The team has an approved source register with that exact section reference.

**Actual LLM response.** The saved reply says “No below-minimum fee applies.” In a practice copy, a second case uses FEE-001 again and cites SV-X#9.

### Example 3. Explain a score change without a new reply

**User question.** Compare the saved June and July replies after auditing the answer key. The June balance is exactly ₹4,000 and the July balance is ₹4,999.

**Approved reference.** SV-1#2 gives zero at the June minimum. SV-2#2 gives ₹100 below the July minimum.

**Actual LLM response.** R-001 says “No below-minimum fee applies.” R-002 says “A ₹100 monthly fee applies.” The scorer uses amounts of 0 and 100 recorded from those replies.

**Assessment.** On fees-v1, compare 0 with the old June label of 80 and 100 with the July label of 100. Only July passes. Keep both replies and the same comparison rule. On fees-v2, change the June label to 0. The June comparison now passes, and July stays a pass.

### Step 2 — Convert worksheet cells to JSONL

The worksheet slice below is in **CSV**, text with a header row and comma-separated cells. Triple quotes hold the whole worksheet as one string. `StringIO` lets the CSV reader read that string as if it were an open sheet of text. `csv.DictReader` uses the header names as dictionary keys. The loop uses `int()` to convert the two numeric cells. `json.dumps()` makes JSON text from one record. Each `print()` writes one whole JSON object on a line.

```python
import csv
import json
from io import StringIO

sheet = """case_id,task,question,as_of,balance_rupees,source_ref,expected_fee_rupees
FEE-001,monthly_fee,June boundary fee?,2026-06-30,4000,SV-1#2,80
FEE-002,monthly_fee,July fee?,2026-07-15,4999,SV-2#2,100

for row in csv.DictReader(StringIO(sheet)):
    row["balance_rupees"] = int(row["balance_rupees"])
```

### Step 3 — Check field types and ranges

The `<=` comparison includes each endpoint.

### Step 6 — Rescore the same replies against two versions

The saved June amount is 0 and the July amount is 100. Compare each with the original labels. June fails and July passes, giving one of two. On the corrected copy, change just the June label to zero and both pass. The loop below counts those passes. A function is a named block of work. `def score(labels, replies):` accepts a label dictionary and a reply list. Each time the amount matches, add one to `passes`. `return` hands back the count.

Select **Copy Code**, paste the block into the editor, and click **Run**.

[Open Python Editor](https://www.online-python.com/)

```python
def score(labels, replies):
    passes = 0
    for case_id, amount in replies:
        if amount == labels[case_id]:
            passes = passes + 1
    return passes


replies = [("FEE-001", 0), ("FEE-002", 100)]
old_labels = {"FEE-001": 80, "FEE-002": 100}
new_labels = old_labels.copy()
new_labels["FEE-001"] = 0

print("fees-v1:", score(old_labels, replies), "of", len(replies))
print("fees-v2:", score(new_labels, replies), "of", len(replies))
```

```text
fees-v1: 1 of 2
fees-v2: 2 of 2
```

`copy()` makes a separate dictionary here, where both values are integers. `len(replies)` gives the size of the same saved reply list. Only the June label changes which comparison succeeds.

### Step 7 — Validate a revision and explain its score change

Start from two converted cases and two captured replies. Copy each case dictionary before editing the June label. Check required types and ranges, duplicate IDs, and whether every source reference is in the register. Save a manifest only for the valid revision. In this exercise the register is embedded in the program, and a reviewer has already checked the June policy.

In `sorted(required - row.keys())`, the minus sign finds required fields that are missing. Sorting makes the reported order predictable. `continue` moves to the next row if a field is missing, so the program doesn’t read it. `errors.append(...)` adds a message to the end of a list. A loop builds a lookup from case ID to expected fee, then the scorer compares only the numeric amounts supplied with the saved replies. It uses exactly the same replies for both versions.

Select **Copy Code**, paste the block into the editor, and click **Run**.

[Open Python Editor](https://www.online-python.com/)

```python
import json


def validate(rows, sources):
    required = {"case_id", "task", "question", "as_of", "balance_rupees",
                "source_ref", "expected_fee_rupees"}
    errors = []
    seen = set()
    for row in rows:
        missing = sorted(required - row.keys())
        if missing:
            errors.append("Missing fields: " + ", ".join(missing))
            continue
        case_id = row["case_id"]
        for field in ("case_id", "task", "question", "as_of", "source_ref"):
            if type(row[field]) is not str or not row[field].strip():
                errors.append("Expected non-empty text: " + field)
        if type(case_id) is str:
            if case_id in seen:
                errors.append("Duplicate case ID: " + case_id)
            seen.add(case_id)
        source_ref = row["source_ref"]
        if type(source_ref) is str and source_ref not in sources:
            errors.append("Unknown source: " + source_ref)
        for field, maximum in (("balance_rupees", 1_000_000),
                               ("expected_fee_rupees", 1000)):
            value = row[field]
            if type(value) is not int or not 0 <= value <= maximum:
                errors.append("Invalid whole-rupee field: " + field)
    return errors


def score(rows, captured):
    labels = {}
    for row in rows:
        labels[row["case_id"]] = row["expected_fee_rupees"]
    passes = 0
    for response_id, case_id, reply, amount in captured:
        if amount == labels[case_id]:
            passes = passes + 1
    return passes


sources = {"SV-1#2", "SV-2#2"}
original = [
    {"case_id": "FEE-001", "task": "monthly_fee", "question": "June boundary fee?",
     "as_of": "2026-06-30", "balance_rupees": 4000, "source_ref": "SV-1#2",
     "expected_fee_rupees": 80},
    {"case_id": "FEE-002", "task": "monthly_fee", "question": "July fee?",
     "as_of": "2026-07-15", "balance_rupees": 4999, "source_ref": "SV-2#2",
     "expected_fee_rupees": 100},
]
captured = [
    ("R-001", "FEE-001", "No below-minimum fee applies.", 0),
    ("R-002", "FEE-002", "A ₹100 monthly fee applies.", 100),
]
revised = []
for row in original:
    revised.append(row.copy())
first = revised[0]
first["expected_fee_rupees"] = 0

errors = validate(original, sources) + validate(revised, sources)
if errors:
    for error in errors:
        print(error)
    print("Revision rejected before scoring")
else:
    old_passes = score(original, captured)
    new_passes = score(revised, captured)
    manifest = {
        "dataset": "fees-v2", "parent": "fees-v1", "schema": 1,
        "case_id": first["case_id"], "old_fee_rupees": original[0]["expected_fee_rupees"],
        "new_fee_rupees": first["expected_fee_rupees"], "source": first["source_ref"],
        "reason": "June boundary is at the minimum", "replay": "saved R-001 and R-002",
    }
    print(json.dumps(manifest))
    print("fees-v1:", old_passes, "of", len(captured))
    print("fees-v2:", new_passes, "of", len(captured))
```

```text
{"dataset": "fees-v2", "parent": "fees-v1", "schema": 1, "case_id": "FEE-001", "old_fee_rupees": 80, "new_fee_rupees": 0, "source": "SV-1#2", "reason": "June boundary is at the minimum", "replay": "saved R-001 and R-002"}
fees-v1: 1 of 2
fees-v2: 2 of 2
```

The manifest points to the original version, evidence, and saved replies. Both scores stay visible. Passing the field and reference checks allows this replay. The labels depend on the reviewer’s separate reading of the policy.

**Experiment.** Change only `first["expected_fee_rupees"] = 0` to `first["expected_fee_rupees"] = -1` and run again.

```text
Invalid whole-rupee field: expected_fee_rupees
Revision rejected before scoring
```

The integer −1 fails the range rule. The program stops before emitting a successful manifest or a revised score. Keep the old report and correct the proposed revision before comparing scores.

**Checkpoint.** What is the limit of this validator? It checks the named fields and references. It assumes the captured replies are correctly linked to known cases and leaves policy applicability and label accuracy to the reviewer.

## Common Mistakes

- **Using row position as identity.** Store stable case and response IDs before anyone sorts or filters the worksheet.
- **Treating valid JSON as a valid dataset.** Check the fields, types, ranges, IDs, and references before scoring.
- **Treating a known source as the right source.** Verify the account, effective date, and rule it supplies.
- **Replacing old records with corrected data.** Preserve the earlier report and record the reason for the new version.
- **Calling a corrected score a model improvement.** Compare assistants against the same reviewed answer key and scoring rule.

## Lesson Summary and Next Step

Use stable IDs to connect named cases with exact captured replies. Convert worksheet records under a clear data contract and validate the result before scoring. Keep each label traceable to its source. When a label changes, record why in a new manifest and preserve earlier reports and captures. Replaying the same replies makes the effect of the revision visible.
